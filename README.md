# Kafka Study — 포인트 지갑 원장

Kafka의 기초를 **단계적으로, 눈으로 확인하며** 익히기 위한 학습용 프로젝트.

## 한 문장

> **같은 사용자의 거래 순서는 지키면서 여러 사용자를 동시에 처리하고,
> 워커가 죽어도 자동으로 이어받으며, 과거 거래까지 다시 읽어야 해서 Kafka를 쓴다.**

이 문장을 **코드로 확인하는 것**이 목적이다.

## 왜 포인트 원장인가

**순서가 결과를 결정적으로 바꾸는 도메인**이어야 순서 보장이 진짜 요구사항이 된다.

```
잔액 1,000원
① 5,000원 적립   ② 3,000원 사용

①→② :  1,000 → 6,000 → 3,000   ✅
②→① :  1,000 → [잔액부족, 거절] → 6,000   ❌ 결과가 다르다
```

**순서가 뒤바뀌면 잔액이 틀리고, 그것이 화면에 숫자로 보인다.**
4단계에서 파티션 키를 랜덤으로 바꿔 이것을 직접 목격한다.

## 정직한 주장

이 프로젝트는 **"Kafka가 아니면 불가능하다"고 주장하지 않는다.** 아래를 전부 만들면 DB로도 된다.

```
이벤트 테이블 + userId별 라우팅 + 워커 멤버십 + 하트비트
+ lease + 파티션 소유권 + 리밸런싱 + 컨슈머 offset + 재시도
```

주장하는 것은 이것이다.

> **DB를 쓰면 이 기능들을 직접 만들어야 하는데, Kafka는 메시징 시스템 자체에서 제공한다.**

그리고 어려운 것은 만드는 일이 아니라 **장애 상황에서 정확성을 지키는 일**이다 (split-brain, fencing token).
→ [05. DB로 직접 만들면 어디까지 가야 하는가](docs/planning/05-why-not-diy.md)

**언제 Kafka가 필요 없는지 아는 것**도 이 프로젝트의 산출물이다.

## 요구사항

| # | 요구사항 | Kafka 메커니즘 |
|---|---|---|
| 1 | 같은 사용자의 거래는 **순서대로** | 파티션 키 |
| 2 | 워커를 늘려 **병렬 처리** | 컨슈머 그룹 |
| 3 | **워커가 죽어도** 자동 인수 | 리밸런싱 |
| 4 | 전체를 다시 읽어 **원장 재구축** | offset seek |
| 5 | **부정탐지 서비스가 나중에 합류** | 그룹별 독립 offset |
| 6 | **실패해도 원장이 틀어지지 않음** | retry 전략, DLT |

1번과 6번은 **정면으로 충돌한다.** 순서를 지키려면 멈춰야 하고, 멈추면 처리량이 죽는다.

## 다른 도구는 왜 안 되나

| | 1+2+3 | 4 (재생) | 5 (독립 소비자) |
|---|---|---|---|
| DB 테이블 큐 | △ 직접 만들면 가능 | ✅ | △ 커서 직접 관리 |
| RabbitMQ | ❌ | ❌ | ✅ |
| Redis Streams | ❌ 파티션 개념 없음 | ✅ | ✅ |
| SQS FIFO | ✅ | ❌ | ❌ |
| **Kafka** | ✅ | ✅ | ✅ |

**셋을 한 번에 제공하는 것은 Kafka뿐이다.**

## 구조

```
ledger-api (:8081)        balance-worker (:8082…) × N ★      fraud-service (:8083)
Producer + SSE 게이트웨이   순서·병렬·리밸런싱의 무대             나중에 합류
     │                            ↑                                 ↑
     └──→ Kafka: ledger-events (파티션 3, 키=userId) ────────────────┘
```

| 컨슈머 그룹 | 인스턴스 | 역할 |
|---|---|---|
| `gateway-group` | 1개 | 전체 파티션 구독 → SSE 중계 |
| `balance-group` | **N개 ★** | 잔액 계산 |
| `fraud-group` | 1개 | 나중에 합류, 전체 재생 |

## 기술 스택

Kotlin (JDK 17) · Spring Boot 3.x · Spring Kafka · Spring Data JPA + PostgreSQL · Gradle 멀티모듈
Vue 3 + Vite · Pinia · Chart.js
Apache Kafka (KRaft) · Kafka UI · Docker Compose

## 사전 준비

- Docker / Docker Compose v2 이상
- JDK 17 이상
- Node.js 20 이상

## 진행 상황

**1차 목표는 5단계까지.**

| 구간 | 단계 | 내용 | 티켓 |
|---|---|---|---|
| 준비 | - | 기획 · 설계 · 운영 체계 | KS-1, 10~13 ✅ |
| | 0단계 | Kafka 인프라 + CLI 실습 | KS-2, KS-3 |
| | 1단계 | 뼈대 + PostgreSQL | KS-4, KS-5 |
| | 2단계 | `ledger-api` 발행 + 실시간 피드 | KS-14, KS-15 |
| | 3단계 | `balance-worker` 1개 — 잔액 계산 | 미발급 |
| **1차** | **4단계 ★** | **순서 깨짐 목격 → 파티션 키 → 리밸런싱** | 미발급 |
| **1차** | **5단계 ★** | 원장 재구축 & 멱등성 | 미발급 |
| 2차 | 6단계 | `fraud-service` 합류 | 미발급 |
| 2차 | 7단계 | 실패 처리 — blocking retry, DLT | 미발급 |

**4단계가 목적지다.** 0~3단계는 4단계를 성립시키기 위한 준비다.
5단계 완료 시 `main` 머지 + `step-5` 태그로 1차 완결.
