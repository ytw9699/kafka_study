# 브랜치 / PR 전략

[← README](../../README.md) · [문서 목록](../README.md)

> **이 문서 한눈에** — `main` ← `dev` ← 작업 브랜치, 커밋 · PR 규칙


## 브랜치 구조

```
main   ──●────────────────────●──────────────────●──   릴리스 (단계 완료 시점)
          ╲                  ╱                  ╱
dev    ────●────●────●──────●────●────●────────●───    통합 브랜치 (기본 개발선)
            ╲  ╱      ╲    ╱      ╲  ╱
feature      ●╱        ●──╱        ●╱                  티켓 단위 작업
```

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `main` | 안정 상태. **각 학습 단계가 완료된 시점의 스냅샷** | 직접 커밋 금지. `dev`에서만 머지 |
| `dev` | 기본 개발선. 모든 티켓 작업이 여기로 모임 | 직접 커밋 금지. feature 브랜치 PR로만 |
| `feature/*` 등 | 티켓 하나당 하나 | `dev`에서 분기, `dev`로 PR |

> 개인 학습 프로젝트라 `release`/`hotfix`는 두지 않는다. Git Flow를 단순화한 형태.

## 작업 브랜치 이름

```
{타입}/KS-{번호}-{영문-케밥케이스-요약}
```

| 티켓 타입 | 브랜치 접두사 |
|---|---|
| `FEAT` | `feature/` |
| `FIX` | `fix/` |
| `CHORE` | `chore/` |
| `DOCS` | `docs/` |
| `REFACTOR` | `refactor/` |
| `EXPERIMENT` | `experiment/` |

예시:
```
feature/KS-1-infra-docker-compose
experiment/KS-5-offset-reset-replay
docs/KS-9-troubleshooting-advertised-listeners
```

## 커밋 메시지

```
{타입}: [KS-{번호}] {한 줄 요약}

{본문 — 왜 이렇게 했는지. 무엇을 했는지가 아니라}
```

타입은 소문자: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `experiment`

예시:
```
feat: [KS-14] ledger-api 거래 발행 및 SSE 게이트웨이 구현

파티션 키를 userId로 잡아 같은 사용자의 거래 순서를 보장한다.
응답에 partition/offset을 포함시킨 것은 학습 목적 — 화면에서
"내 거래가 어느 파티션에 들어갔는지" 바로 확인하기 위함.
```

## PR 규칙

### 제목
```
[KS-{번호}] {제목}
```

### 본문에 반드시 포함
1. **티켓 문서 링크** — `docs/issues/KS-N-....md`
2. **무엇을 왜 했는지** — 구현 내용이 아니라 판단 근거
3. **확인 방법** — 눈으로 검증하는 절차 (이 프로젝트는 "보이는 것"이 중요)
4. **배운 것** (있다면)

### 대상
- feature/* → **`dev`**
- `dev` → **`main`** (한 학습 단계가 끝났을 때)

### 머지 후
- 작업 브랜치 삭제
- 티켓 문서 상태를 `DONE`으로, **"배운 것" 섹션 작성**
- `docs/README.md` 티켓 보드 갱신

## `dev` → `main` 머지 시점

한 **학습 단계**(0~6단계)가 통째로 끝나서 동작이 확인됐을 때만.
특히 **4단계 완료 시점이 1차 완결**이다 (`step-4`).
즉 `main`의 커밋 히스토리를 보면 **학습 진도가 그대로 보이게** 된다.

머지 후 태그를 붙인다:
```bash
git tag -a step-0 -m "0단계: 로컬 Kafka 인프라 완료"
```

이렇게 하면 나중에 "2단계 시점 코드가 어땠지?"를 바로 꺼내볼 수 있다.
