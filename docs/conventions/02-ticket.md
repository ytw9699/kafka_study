# 티켓 체계

[← README](../../README.md) · [문서 목록](../README.md)

> **이 문서 한눈에** — 작업 하나 = 티켓 문서 하나(`KS-N`). 번호 · 양식 · 상태 흐름


Jira 대체. **작업 단위 하나 = `docs/issues/` 안의 파일 하나.**

## 티켓 번호

```
KS-{번호}
```

- `KS` = **K**afka **S**tudy (프로젝트 접두사)
- 번호는 **1부터 순차 증가**. 타입별로 나누지 않고 하나의 시퀀스를 쓴다 (Jira와 동일)
- **번호는 재사용하지 않는다.** 티켓을 취소해도 그 번호는 비워두고 다음 번호로 간다
- **번호를 미리 예약하지 않는다.** 티켓 문서를 실제로 만들 때 발급한다.
  앞으로 할 일의 목록은 [작업 로드맵](../planning/04-roadmap.md)에 두고, 착수 시점에 티켓으로 옮긴다

**다음 번호 확인 방법**: `docs/README.md`의 티켓 보드에서 마지막 번호 + 1. 또는

```bash
ls docs/issues | sort -t- -k2 -n | tail -1
```

## 파일명

```
KS-{번호}-{영문-케밥케이스-요약}.md
```

예시:
- `KS-2-infra-docker-compose.md`
- `KS-14-ledger-api-publish.md`
- `KS-3-kafka-cli-basics.md`

## 티켓 타입

문서 본문 상단 메타에 표기한다.

| 타입 | 용도 |
|---|---|
| `FEAT` | 새 기능 / 새 단계 구현 |
| `FIX` | 버그 수정 |
| `CHORE` | 설정, 빌드, 의존성, 잡무 |
| `DOCS` | 문서 작업 |
| `REFACTOR` | 동작 변경 없는 구조 개선 |
| `EXPERIMENT` | 학습용 실험 (Kafka 동작 확인 등) |

> 이 프로젝트에는 `EXPERIMENT`가 중요하다. "offset을 리셋하면 어떻게 되나" 같은 **학습 자체가 목적인 작업**을 기능 구현과 구분하기 위함.

## 상태

| 상태 | 의미 |
|---|---|
| `TODO` | 아직 시작 안 함 |
| `IN PROGRESS` | 작업 중 |
| `IN REVIEW` | PR 올라감 |
| `DONE` | 머지 완료 |
| `CANCELED` | 취소 (번호는 비워둠) |

## 티켓 문서 양식

```markdown
# KS-{번호}: {제목}

| | |
|---|---|
| **타입** | FEAT |
| **상태** | TODO |
| **단계** | 0단계 — 인프라 |
| **브랜치** | `feature/KS-2-infra-docker-compose` |
| **PR** | - |

## 배경

왜 이 작업이 필요한가. 앞선 어떤 문서/티켓에서 파생됐는가.

## 목표

이 티켓이 끝나면 무엇이 가능해지는가. 한두 문장.

## 작업 내용

- [ ] 할 일 1
- [ ] 할 일 2

## 상세 설계

이 작업 한정의 설계. 설정값, 스키마, 코드 구조 등.
프로젝트 전체에 영향 가는 결정이면 `planning/` 문서에 쓰고 여기서는 링크만.

## 완료 조건 (DoD)

- [ ] 눈으로 확인 가능한 검증 방법 1
- [ ] 검증 방법 2

## 배운 것

작업 후 채운다. **이 프로젝트는 학습이 목적이므로 이 섹션이 가장 중요하다.**
개념적으로 새로 안 것, 예상과 달랐던 것, 다음에 주의할 것.

## 참고

- 관련 문서 / 티켓 / 외부 링크
```

## 티켓과 브랜치·PR·커밋의 연결

| | 형식 | 예시 |
|---|---|---|
| 브랜치 | `{타입소문자}/KS-{번호}-{요약}` | `feature/KS-2-infra-docker-compose` |
| 커밋 | `{타입}: [KS-{번호}] {내용}` | `feat: [KS-2] Kafka KRaft + Kafka UI 컴포즈 구성` |
| PR 제목 | `[KS-{번호}] {제목}` | `[KS-2] 로컬 Kafka 인프라 구성` |

PR 본문에는 티켓 문서 링크를 반드시 넣는다.

자세한 내용은 [03-branch-strategy.md](03-branch-strategy.md) 참조.

## 티켓 진행 흐름

```
1. docs/issues/ 에 티켓 문서 작성 (상태: TODO)
2. docs/README.md 티켓 보드에 한 줄 추가
3. dev 에서 브랜치 생성 (상태: IN PROGRESS)
4. 작업 + 커밋
5. dev 로 PR (상태: IN REVIEW) — 티켓 문서에 PR 링크 기입
6. 머지 (상태: DONE) — 티켓의 "배운 것" 섹션 작성
```

> **"배운 것"을 안 쓰면 티켓을 닫지 않는다.** 이 프로젝트의 산출물은 코드가 아니라 이해다.
