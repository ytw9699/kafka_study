## 배경

Kafka를 학습하려는데, 대부분의 자료가 "메시지를 발행하고 구독한다"에서 끝난다. 그건 RabbitMQ도 SQS도 Redis Pub/Sub도 한다. **왜 굳이 Kafka인가**에 대한 답이 남지 않는다.

먼저 무엇을 왜 만들지 확정하고, 그 다음 코드를 쓴다.

또한 이 프로젝트는 Jira를 쓰지 않으므로, 이슈 관리와 기록을 `docs/`로 대체하는 체계를 함께 정한다.

## 목표

1. Kafka가 **대체 불가능한 지점**을 조준한 시나리오를 확정한다.
2. 그 시나리오를 검증하는 0~7단계 학습 로드맵을 세운다.
3. 기술 스택을 근거와 함께 확정한다.
4. Jira 없이 굴러가는 문서/티켓/브랜치 체계를 만든다.

## 상세 설계

### 확정된 시나리오

> 주문이 발생하면 실시간으로 화면에 뜬다.
> 그리고 **나중에 추가된 통계 서비스가 과거 주문까지 전부 읽어서** 매출 집계를 스스로 만들어낸다.

뒤쪽 문장이 핵심이다. 큐로는 구조적으로 불가능하다 — 소비된 메시지가 존재하지 않기 때문.

### 핵심 설계 판단

**두 컨슈머를 서로 다른 컨슈머 그룹으로 둔다.**

| 서비스 | 컨슈머 그룹 | `auto-offset-reset` | 의미 |
|---|---|---|---|
| `feed-service` | `feed-group` | `latest` | 기동 이후 주문만 (실시간 피드) |
| `stats-service` | `stats-group` | `earliest` | 기동 시점에 쌓여 있던 과거 주문 전부를 재생 |

### 의도적으로 미룬 것

**3단계에서는 `processed_event` 테이블을 만들지 않는다.**
4단계에서 offset을 리셋했을 때 **집계가 2배가 되는 문제를 먼저 겪어봐야** 멱등성의 필요성이 몸에 남는다. 처음부터 방어 코드를 넣으면 학습 기회를 잃는다.

## 배운 것

### Kafka의 대체 불가능한 지점은 "replay"가 아니라 그 상위 개념이다

처음엔 "replay가 1순위 차별점"이라고 정리했지만, 엄밀히 따지면 실무에서 replay 자체가 도입 동기인 경우는 드물다. retention이 보통 7일이라 "6개월치 재생"은 데이터레이크의 몫이다.

더 정확한 표현:

> **이벤트가 소비 후 사라지는 메시지가 아니라, 여러 소비자가 각자의 위치(offset)를 들고 읽는 "공유된 지속 로그"다.**

replay는 이 성질의 **결과 중 하나**일 뿐이다. 같은 성질에서 신규 컨슈머의 상태 구축, 버그 수정 후 재처리, 스트림 처리 상태 복구, CDC가 전부 파생된다.

### 도구 선택은 "무엇을 안 골랐는가"가 더 중요하다

- **SSE 연결이 끊기는 문제**는 Kafka가 푸는 문제가 아니다. 서버-브라우저 레이어와 서버-서버 레이어는 다르다. 서버 2대 규모면 Redis Pub/Sub가 더 적합하다.
- **단순 MSA 이벤트 통신**은 RabbitMQ나 SNS+SQS로도 충분하다. Kafka가 유일한 정답인 케이스가 아니다.
- **Kubernetes**를 0단계에 넣으면 학습의 주인공이 Kafka에서 쿠버로 바뀐다. offset 리셋·리밸런싱 실험에 필요한 빠른 재기동 사이클도 깨진다.

### 학습 설계에서 저장소 선택이 학습량을 바꾼다

`ConcurrentHashMap`으로 집계하면 키가 알아서 덮어써져서 **replay 중복 집계 문제가 보이지 않고 지나간다.** JPA + H2로 두어야 문제가 실제로 터지고, 멱등성을 직접 해결하게 된다.

또한 H2를 **파일 모드가 아닌 인메모리 모드**로 두어야 "재기동 → DB 비워짐 → Kafka 재생으로 재구축"이라는 이벤트 소싱의 기본 발상을 매번 체험한다.
