## 배경

[KS-37](KS-37-doc-sync-after-failure-handling.md)을 쓰는 사이 7단계가 `main` 에 머지되고 `step-7` 태그가 붙었다.
그래서 KS-37 이 적은 "7단계는 `dev` 에만 있어 태그가 없다"가 머지 직후 틀린 말이 됐다.

또 KS-37 의 README 정리는 `dev` 에만 들어가, GitHub 첫 화면(`main`)의 README 는 수정 전 상태였다.


> **정정 ([KS-43](KS-43-default-branch-fact.md))** — 이 티켓은 "GitHub 첫 화면은 `main`"이라는 전제로 판단했지만, 이 저장소의 **기본 브랜치는 `dev`** 다.
> 방문자가 처음 보는 README 는 처음부터 `dev` 의 것이었다. `main` 반영 자체는 해가 없지만, 이유는 "첫 화면"이 아니라 "`main` 을 직접 보는 사람을 위해서"가 맞다.

## 작업 내용

- [x] README 진행 상황 표 · 태그 안내, 문서 인덱스, 진행 기록 단계표 — "태그 전" → `step-7`
- [x] `dev` → `main` 머지 — **예외.** 규칙상 문서 보강은 `dev` 에만 머지하지만,
  처음 보는 사람이 보는 화면이 `main` 의 README 라서 이번에는 반영한다. `step-7` 태그는 7단계 코드 시점을 가리키므로 옮기지 않는다

## 배운 것

- **상태를 적는 문장은 머지 순서에 따라 바로 틀린다.** "태그 전"처럼 시점에 묶인 표현은, 같은 시각에 다른 작업이 진행 중이면 쓰는 순간 낡을 수 있다. 상태는 가능하면 태그 · 티켓처럼 확인 가능한 사실로 적는다.
- **"문서 보강은 `dev` 에만" 규칙에는 빈틈이 있다.** 저장소 첫 화면은 `main` 이므로, README 처럼 첫인상을 결정하는 문서는 `main` 반영 여부를 따로 판단해야 한다.
