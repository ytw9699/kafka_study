## 배경

[KS-39](KS-39-readme-screenshots.md)에서 스크린샷을 찍다가, replay 직후 잔액표 아래에
**"화면을 켜기 전에 발행된 거래가 있어 기대 잔액이 부족하게 계산됩니다"** 경고가 뜨는 것을 봤다.
화면을 먼저 켜고 거래를 발생시켰으므로 **틀린 경고**였다.

원인을 찾다가 같은 뿌리의 문제를 하나 더 찾았다.

| 문제 | 원인 |
|---|---|
| replay 뒤 틀린 경고 | 경고 기준이 "워커가 처리한 건수 > 화면이 받은 거래 수"였다. replay 는 **같은 거래를 한 번 더 처리**하므로 워커 건수만 두 배가 된다 |
| 거래가 300건을 넘으면 기대 잔액이 틀어짐 | 화면은 피드에 **최근 300건만** 남기는데, 기대 잔액도 **그 300건으로** 계산했다 |
| 피드 [지우기] 를 누르면 기대 잔액이 사라짐 | 지우기가 계산에 쓰는 목록까지 비웠다. 비교할 행이 없으니 **"일치 ✓" 처럼 보였다** |

## 작업 내용

- [x] `stores/ledger.ts` — 기대 잔액 계산용 기록(`history`, 자르지 않음)과 피드 표시용 목록(`events`, 최근 300건)을 분리. [지우기] 는 피드만 비운다
- [x] 경고 기준을 **"파티션에서 화면이 처음 받은 거래의 offset 이 0 보다 큰가"** (`missedPartitions`)로 변경
- [x] 경고 문구 — 어느 파티션인지 표시, "워커 잔액을 재구축하라"는 조언 제거(재구축해도 화면이 놓친 거래는 다시 받지 못한다)

## 탈락시킨 대안

| 대안 | 탈락 이유 |
|---|---|
| 경고 기준을 "처리 건수 > 받은 거래 수 × 2" 처럼 느슨하게 | replay 를 두 번 하면 또 틀린다. 근본 원인(건수로는 재처리와 놓침을 구분할 수 없다)이 그대로다 |
| 피드 최대 개수를 늘림 | 문제를 뒤로 미룰 뿐이다 |
| 화면이 켜질 때 과거 거래를 다시 받아 오기 | ledger-api 가 DB 없이 Kafka 를 처음부터 읽어 보내야 한다. 학습 범위 밖 |

**왜 offset 인가** — offset 은 Kafka 가 파티션 안에서 매기는 번호라, 화면이 처음 받은 거래가 0번이 아니면 그 앞을 놓친 것이 확실하다.
replay · rebuild 는 기록을 **다시 읽을 뿐 새로 만들지 않으므로** 이 번호가 바뀌지 않는다.

## 검증

데이터를 초기화하고 워커 1개로, 같은 시험을 **고치기 전 · 후 코드로** 각각 돌렸다.

| 경우 | 고치기 전 | 고친 후 |
|---|---|---|
| 화면을 먼저 켜고 거래 55건 | 일치 ✓ | 일치 ✓ |
| → replay | (KS-39 에서 확인) 틀린 경고 | 2배라 불일치(정상), **경고 없음** |
| 거래 385건 (피드 300건 초과) | **불일치 5명 😱** — 워커는 맞는데 화면 계산이 틀림 | **일치 ✓**, 피드는 300줄 |
| 피드 [지우기] | "일치 ✓" — 기대 잔액이 비어 비교할 행이 없음 | **일치 ✓** — 실제 값 비교 |
| 거래가 쌓인 뒤 화면을 켬 | 경고 | **경고** ("p1, p2" 표시) — 원래 목적 유지 |

프론트 빌드(`vue-tsc` 타입 검사 포함) 통과.

## 배운 것

- **건수로는 "다시 처리한 것"과 "놓친 것"을 구분할 수 없다.** at-least-once 에서는 같은 거래를 여러 번 처리할 수 있으니, 처리 건수는 거래 수의 근거가 되지 못한다.
  무엇을 놓쳤는지는 **Kafka 가 매긴 위치(offset)** 로 판단해야 한다. 컨슈머가 offset 으로 "어디까지 읽었나"를 기억하는 것과 같은 원리다.
- **표시용 데이터와 계산용 데이터를 같은 목록에 두면, 표시를 줄이는 순간 계산이 틀린다.**
- **"일치"도 틀릴 수 있다.** 비교할 대상이 없을 때 "불일치 0건"은 "일치"가 아니다.
