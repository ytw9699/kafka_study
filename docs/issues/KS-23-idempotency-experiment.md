## 배경

Kafka 의 기본 전달 보장은 **at-least-once** 다. 같은 이벤트를 두 번 받을 수 있다.

지금까지 컨슈머에 **아무 방어도 넣지 않았다.** [KS-16](KS-16-balance-worker.md)에서
"멱등 처리는 5단계에서" 라고 미뤄둔 이유가 이것이다 —
**문제를 먼저 겪어야 필요성이 몸에 남는다.**

## 목표

재생 시 포인트가 두 배가 되는 것을 목격하고, 멱등 처리로 해결한다.

## 선행 조건

- [KS-22](KS-22-replay-api.md) 완료
- **워커 1개** (재생의 본질을 보는 것이 목적. 분산 조율은 범위 밖)
- 파티션 키는 `USER_ID`

## 상세 설계

### 멱등 키가 `eventId` 인 이유

`userId` 로는 안 된다 — 한 사용자에게 여러 이벤트가 발생한다.
금액 같은 내용 기반 키도 안 된다 — 같은 금액을 두 번 적립할 수 있다.

**이벤트마다 고유한 `eventId` 만이 안전하다.**

### 세 가지 방식의 차이

| | offset | 잔액 테이블 | 결과 |
|---|---|---|---|
| `replay` (멱등 없음) | 0으로 | 유지 | **두 배** 😱 |
| `rebuild` | 0으로 | **비움** | 정확히 복원 |
| `replay` (멱등 있음) | 0으로 | 유지 | **불변** ✅ |

**언제 무엇을 쓰는가**

- **집계 로직이 바뀌었다** → `rebuild`. 과거 계산이 통째로 무효이므로 비우고 다시
- **상시 운영 중 중복 방지** → 멱등 처리. 리밸런싱·재기동에서 중복이 생겨도 안전

멱등 처리가 있으면 `replay` 도 안전해지지만, **`rebuild` 를 대체하지는 않는다.**
로직이 바뀌면 이전 결과 자체가 틀렸으므로 비워야 한다.

### CLI `--reset-offsets` 는 왜 안 쓰는가

**활성 컨슈머가 있으면 거부된다.** 워커를 내려야 하는데,
그러면 재생 시작 시점에 워커가 방금 뜬 상태라 **화면에서 "두 배로 뛰는 순간"을 볼 수 없다.**

이것을 직접 확인해 "왜 API 로 만들었는가"의 근거로 삼는다.

### 멱등 처리가 완벽하지 않다는 점

`processed_event` 기록과 잔액 갱신이 **같은 트랜잭션**이어야 한다.
분리되면 그 사이에 죽었을 때 다시 중복이 생긴다.

또한 이것은 **컨슈머 쪽 멱등성**이다. 프로듀서가 같은 거래를 두 번 발행하면
`eventId` 가 달라 막지 못한다. 그 경우는 비즈니스 키(주문번호 등)가 필요하다.

**"멱등성"이 한 가지가 아니라는 점을 정리한다.**
