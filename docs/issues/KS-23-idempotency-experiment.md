## 배경

Kafka 의 기본 전달 보장은 **at-least-once** 다. 같은 이벤트를 두 번 받을 수 있다.

지금까지 컨슈머에 **아무 방어도 넣지 않았다.** [KS-16](KS-16-balance-worker.md)에서
"멱등 처리는 5단계에서" 라고 미뤄둔 이유가 이것이다 —
**문제를 먼저 겪어야 필요성이 몸에 남는다.**

## 목표

재생 시 포인트가 두 배가 되는 것을 목격하고, 멱등 처리로 해결한다.

## 선행 조건

- [KS-22](KS-22-replay-api.md) 완료
- **워커 1개** (재생의 본질을 보는 것이 목적. 분산 조율은 범위 밖)
- 파티션 키는 `USER_ID`

## 작업 내용

- [x] 거래를 발행해 잔액을 만든다 (기준값 기록)
- [x] `POST /api/balance/replay` → **잔액이 두 배가 되는 것 확인** 😱
- [x] 재생 과정을 화면에서 관찰 (`app.replay.delay-ms`)
- [x] `POST /api/balance/rebuild` → **정확히 복원되는 것 확인** ✅

- [x] `processed_event` 테이블 추가 (**`event_id` PK**)
- [x] 멱등 처리 구현 — 이미 처리한 `eventId` 는 skip
- [x] `replay` 재실행 → **잔액 불변** 확인 ✅

- [x] 세 방식의 차이 정리

## 상세 설계

### 멱등 키가 `eventId` 인 이유

`userId` 로는 안 된다 — 한 사용자에게 여러 이벤트가 발생한다.
금액 같은 내용 기반 키도 안 된다 — 같은 금액을 두 번 적립할 수 있다.

**이벤트마다 고유한 `eventId` 만이 안전하다.**

### 세 가지 방식의 차이

| | offset | 잔액 테이블 | 결과 |
|---|---|---|---|
| `replay` (멱등 없음) | 0으로 | 유지 | **두 배** 😱 |
| `rebuild` | 0으로 | **비움** | 정확히 복원 |
| `replay` (멱등 있음) | 0으로 | 유지 | **불변** ✅ |

**언제 무엇을 쓰는가**

- **집계 로직이 바뀌었다** → `rebuild`. 과거 계산이 통째로 무효이므로 비우고 다시
- **상시 운영 중 중복 방지** → 멱등 처리. 리밸런싱·재기동에서 중복이 생겨도 안전

멱등 처리가 있으면 `replay` 도 안전해지지만, **`rebuild` 를 대체하지는 않는다.**
로직이 바뀌면 이전 결과 자체가 틀렸으므로 비워야 한다.

### CLI `--reset-offsets` 는 왜 안 쓰는가

**활성 컨슈머가 있으면 거부된다.** 워커를 내려야 하는데,
그러면 재생 시작 시점에 워커가 방금 뜬 상태라 **화면에서 "두 배로 뛰는 순간"을 볼 수 없다.**

이것을 직접 확인해 "왜 API 로 만들었는가"의 근거로 삼는다.

### 멱등 처리가 완벽하지 않다는 점

`processed_event` 기록과 잔액 갱신이 **같은 트랜잭션**이어야 한다.
분리되면 그 사이에 죽었을 때 다시 중복이 생긴다.

또한 이것은 **컨슈머 쪽 멱등성**이다. 프로듀서가 같은 거래를 두 번 발행하면
`eventId` 가 달라 막지 못한다. 그 경우는 비즈니스 키(주문번호 등)가 필요하다.

**"멱등성"이 한 가지가 아니라는 점을 정리한다.**

## 배운 것

### 두 배가 되는 것은 버그가 아니라 정상 동작이다

Kafka 의 전달 보장은 **at-least-once** 다. 같은 이벤트를 두 번 주는 것은 **약속된 동작**이며,
중복을 걸러내는 것은 **컨슈머의 책임**이다.

방어를 안 넣었으니 두 번 적용된 것뿐이다. "Kafka 가 중복을 보냈다"가 아니라
**"내가 멱등하게 만들지 않았다"** 가 정확한 서술이다.

### `clearAll()` 이 처리 기록도 비워야 한다

처음에 잔액만 비웠다면 `rebuild` 가 **전부 skip** 되어 잔액이 비어 있는 채로 끝났을 것이다.

**멱등 기록은 잔액과 생명주기를 같이해야 한다.** 하나만 지우면 상태가 어긋난다.
이것이 `rebuild` 와 `replay` 의 차이를 더 분명하게 만든다 —
`rebuild` 는 "처음 보는 것처럼" 다시 시작하는 것이다.

### 거절된 이벤트도 기록해야 한다

거절 역시 **처리한 결과**다. 기록하지 않으면 재생 시 다시 거절 판정이 돌아
`rejectedEvents` 카운트가 계속 늘어난다.

"성공한 것만 기록한다"고 생각하기 쉬운데, **멱등성은 결과가 아니라 처리 여부의 문제**다.

### 멱등 키가 `eventId` 여야 하는 이유를 테스트로 고정했다

```
✅ 금액이 같아도 eventId 가 다르면 별개로 처리된다
```

같은 사용자가 같은 금액을 두 번 적립하는 것은 **정상 거래**다.
내용 기반 키(userId + amount)로는 이것을 중복과 구분할 수 없다.

### 멱등성은 한 가지가 아니다

| 지점 | 무엇을 막는가 | 키 |
|---|---|---|
| **컨슈머 멱등성** (이번에 만든 것) | 재생·리밸런싱·재기동에서의 중복 처리 | `eventId` |
| **프로듀서 멱등성** | 같은 거래를 두 번 발행하는 것 | 비즈니스 키 (주문번호 등) |

`ledger-api` 가 같은 거래를 두 번 발행하면 `eventId` 가 달라 **막지 못한다.**
"멱등성을 구현했다"고 말할 때 **어느 지점인지 밝혀야 한다.**

### 세 방식은 대체 관계가 아니다

| | offset | 잔액 | 처리 기록 | 언제 쓰는가 |
|---|---|---|---|---|
| `replay` (멱등 없음) | 0으로 | 유지 | - | **쓰면 안 된다** |
| `replay` (멱등 있음) | 0으로 | 유지 | 유지 | 안전하지만 **아무 일도 안 일어난다** |
| `rebuild` | 0으로 | 비움 | 비움 | **집계 로직이 바뀌었을 때** |

멱등 처리가 있어도 `rebuild` 가 필요하다.
**로직이 바뀌면 이전 계산 자체가 틀렸으므로** 비우고 다시 쌓아야 한다.

멱등성은 "중복을 막는 것"이지 "재계산하는 것"이 아니다.

### 트랜잭션 경계가 중요하다

멱등 검사와 잔액 갱신, 처리 기록이 **같은 `@Transactional` 안**에 있어야 한다.

분리되면 잔액은 갱신됐는데 기록이 안 된 상태에서 죽을 수 있고,
재시작 시 다시 중복이 생긴다. **멱등 처리를 넣었다고 안전한 것이 아니라,
경계를 맞춰야 안전하다.**
