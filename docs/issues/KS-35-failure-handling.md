## 배경

지금 워커는 **처리에 실패하면 어떻게 할지 정해 두지 않았다.**
[TS-2](../troubleshooting/TS-2-poison-pill.md)에서 형식이 깨진 메시지 하나 때문에 워커가 무한 재시도로 멈추는 것을 겪었지만,
그때는 토픽을 비워서 넘어갔을 뿐 **해결하지 않았다.**

실무에서 Kafka 를 쓰면 반드시 정해야 하는 것이 이것이다.

- 잠깐 실패한 것(DB 일시 장애, 외부 API 타임아웃)은 **몇 번, 얼마 간격으로 다시 시도**하는가
- 다시 해도 안 되는 것(잘못된 데이터)은 **어디로 빼 두고** 다음으로 넘어가는가 — DLT(Dead Letter Topic)
- 그 사이 **순서는 지켜지는가**

그리고 이 프로젝트에서는 이 셋이 **정면으로 충돌한다** ([01. 기획서 5번](../planning/01-planning.md)).

```
사용자 A:  ① 5,000 적립   ② 3,000 사용 (실패)   ③ 2,000 사용

②를 DLT로 빼고 ③을 먼저 처리 → ②를 건너뛴 잔액이 된다 → 영구히 틀린다
```

## 목표

1. 실패를 처리하지 않으면 **워커가 멈춘다**는 것을 다시 겪는다 → 실제로는 멈추지 않고 **조용히 건너뛰었다** (결과 1)
2. Spring Kafka 가 권장하는 **non-blocking retry 가 포인트 계산을 깨뜨리는 것**을 화면에서 본다 (실험 E)
3. **blocking retry** 로 바꿔 순서를 지키고, 그 대가로 **같은 파티션의 다른 사용자까지 멈추는 것**을 본다 (실험 F)
4. 다시 해도 안 되는 실패만 **빠르게 DLT 로 격리**해 파티션을 다시 흐르게 한다
5. **깨진 메시지(poison pill)** 가 워커를 멈추지 않게 격리한다

## 결정한 것

| 질문 | 결정 | 탈락시킨 대안 |
|---|---|---|
| 실패를 일으키는 방법 | **거래의 사유 칸**에 `[실험] 일시 실패 N초` · `[실험] 영구 실패` | 워커별 설정 API — 워커가 여러 개면 모두에게 따로 걸어야 한다 |
| 일시 실패 표현 | **발생 후 N초 동안** 실패 | "N번 실패" — 시도 횟수를 워커끼리 공유해야 한다 |
| 일시 · 영구 구분 | 예외 종류 (`TransientFailureException` / `PermanentFailureException`) | 메시지 내용 판단 |
| 영구 실패 뒤 같은 사용자 거래 | **사용자 보류** — 뒤 거래도 DLT 로 순서대로 | 그냥 처리(잔액 틀어짐), 파티션 전체 정지(무관한 사용자까지 멈춤) |
| 모드 비교 방법 | `APP_ERROR_MODE` = `DEFAULT` · `NON_BLOCKING` · `BLOCKING` | 코드 브랜치를 바꿔 가며 비교 |
| DLT 재처리 | **이번 범위 밖** — DLT 에 순서대로 보관만 한다 | — |

## 실행 결과

모든 실험은 같은 Kafka · 같은 코드에서 **모드만 바꿔** 실행했다. (아래 "결과 1~4"는 이 티켓 안의 순서이고, 프로젝트의 학습 단계와는 무관하다.)

### 결과 1 — 아무 설정 없음 (`DEFAULT`, Spring Kafka 기본값)

`user-9`: ① 5,000 적립 ② 3,000 사용 (**영구 실패**) ③ 1,000 사용 — 정답은 잔액 **1,000**

```
② 를 즉시 10번 다시 시도 (PermanentFailureException 10회)
→ 에러 로그만 남기고 다음 거래로 넘어감
적용 p2#2 user-9 사용 5,000 → 4,000

워커 잔액 4,000   기대 잔액 1,000   차이 +3,000   😱
```

**예상과 달랐다.** 로드맵에는 "무한 재시도로 멈춘다"고 적었지만, Spring Kafka 기본 에러 처리기는
**10번 다시 하고 조용히 건너뛴다.** 실패한 거래는 어디에도 남지 않는다. 멈추는 것보다 더 나쁘다 — 아무도 모르게 틀린다.

(TS-2 에서 무한히 멈췄던 것은 **역직렬화** 실패였다. 리스너에 도달하기 전에 실패해 에러 처리기가 손을 못 썼다. 결과 4 참조.)

### 결과 2 — 재시도 토픽 (`NON_BLOCKING`) — 실험 E

`user-8`: ① 5,000 적립 ② 3,000 사용 (**5초 일시 실패**) ③ 4,000 사용 — 정답은 잔액 **2,000**, 거절 1

```
적용 p0#0 user-8 적립        0 → 5,000
적용 p0#2 user-8 사용 4,000  5,000 → 1,000      ← ③ 이 먼저
거절 p0#0 user-8 사용 3,000  잔액 1,000 < 3,000   ← ② 는 재시도 토픽에서 나중에

워커 잔액 1,000 (거절 1)   기대 잔액 2,000   😱
```

**권장 패턴이 순서를 뒤집어 잔액을 깨뜨렸다.**

곁가지 발견 — 재시도 간격이 같아도 기본값은 **시도마다 토픽을 하나씩**(`retry-0` ~ `retry-8`) 만든다.
`SameIntervalTopicReuseStrategy.SINGLE_TOPIC` 으로 `ledger-events-retry` 하나로 합쳤다.

### 결과 3 — 그 자리에서 재시도 + DLT + 보류 (`BLOCKING`)

워커 3개. 해시 결과 `user-1 · 2 · 6 · 7` 은 파티션 2, `user-8` 은 파티션 0.

**3-1. 실험 E 재실행** (`user-7`, 8,000 사용 5초 일시 실패 → 4,000 사용)

```
일시 실패 중 (5초) × 3   ← 그 자리에서 기다림
적용 p2#7 user-7 사용 8,000  10,000 → 2,000
거절 p2#8 user-7 사용 4,000  잔액 2,000          ← 순서대로

잔액 2,000 · 거절 1   ✅ 정답
```

**3-2. 실험 F — 순서를 지키는 대가** (`user-1` 거래를 **20초** 실패시키고 바로 다른 사용자 거래)

| 사용자 | 파티션 | 처리까지 |
|---|---|---|
| `user-8` | 0 (다른 파티션) | **1초** |
| `user-2` | 2 (user-1 과 같은 파티션) | **22초** |

`user-2` 는 아무 문제가 없는데 앞 사람의 재시도(10회)가 끝날 때까지 **같이 기다렸다.**

**3-3. 영구 실패 → DLT + 보류** (`user-6`: 3,000 **영구 실패** → 1,000 → 500, 바로 뒤 `user-2`)

```
user-2 처리: 1초                 ← 같은 파티션인데 기다리지 않음 (영구 실패는 재시도 없이 바로 DLT)
user-6 잔액: 10,000              ← 보류. 세 거래 모두 반영 안 됨
보류: user-6 (PermanentFailureException ...)

ledger-events.DLT 파티션 2:
  user-6 3,000  [실험] 영구 실패    원인: PermanentFailureException
  user-6 1,000  보류 뒤 거래 1     원인: UserQuarantinedException
  user-6   500  보류 뒤 거래 2     원인: UserQuarantinedException
```

DLT 에 **원래 순서 그대로**, 원인 헤더(`kafka_dlt-exception-*`)와 함께 쌓였다. 화면에는 `user-6` 옆에 **"보류"** 가 뜬다.

### 결과 4 — 깨진 메시지 격리 (`ErrorHandlingDeserializer`)

TS-2 와 같은 원시 텍스트를 `user-2` 키로 토픽에 직접 넣고, 바로 뒤 `user-2` 정상 거래.

```
정상 거래 처리: 1초 (8,000 → 7,500)       ← 워커가 멈추지 않음
ledger-events.DLT:  user-2  이건 JSON이 아닌 깨진 메시지   ← 원본 그대로 보관
보류: user-6 만                           ← 누구 거래인지 모르는 메시지라 user-2 를 보류하지 않음
```

### 단위 테스트

```
✅ 표시가 없으면 실패하지 않는다
✅ 영구 실패 표시가 있으면 언제나 실패한다
✅ 일시 실패는 정해진 시간 동안만 실패한다
```

## 포인트 계산 vs 메시지 발송 — 같은 실패, 다른 정답

| | 포인트 계산 (이 프로젝트) | 메시지 대량 발송 |
|---|---|---|
| 순서가 결과를 바꾸나 | **바꾼다** — 사용이 적립보다 먼저면 거절 | 대체로 안 바꾼다 — 각 발송이 독립 |
| 일시 실패 | **blocking** — 그 자리에서 기다린다 | **non-blocking** — 재시도 토픽으로 미루고 다음 발송 |
| 영구 실패 | DLT + **그 사용자 보류** | DLT 로 빼고 끝 |
| 대가 | 같은 파티션의 다른 사용자가 기다린다 (실험 F) | 같은 수신자에게 순서가 바뀌어 도착할 수 있다 |

## 남은 한계

| 항목 | 내용 |
|---|---|
| DLT 재처리 | DLT 에 쌓인 거래를 원인 해결 후 다시 처리하고 보류를 푸는 기능은 없다 |
| 보류 판단의 원자성 | 보류 기록(DB)과 DLT 발행(Kafka)이 한 트랜잭션이 아니다. 그 사이에 죽으면 다시 받아 처리하므로 결과적으로 맞지만, 순간적으로 어긋날 수 있다 |
| 재시도 토픽 모드의 재생 | `NON_BLOCKING` 에서는 재시도 컨슈머도 같은 리스너를 써서 되감기 콜백이 섞인다. 이 모드에서는 rebuild · replay 를 막았다 |
| 실험 F 의 대가 줄이기 | 일시 실패 재시도 시간을 짧게 잡거나 파티션을 늘리면 줄어든다. 측정은 KS-29 와 함께 |

## 배운 것

- **기본값은 "멈춘다"가 아니라 "조용히 버린다"였다.** Spring Kafka 기본 에러 처리기는 10번 다시 하고 로그만 남기고 넘어간다.
  멈추는 시스템은 누군가 알아채지만, 조용히 버리는 시스템은 **틀린 잔액을 정상처럼** 보여 준다. 실패 처리를 "정하지 않는 것"도 하나의 선택이고, 가장 나쁜 선택일 수 있다.
- **같은 패턴이 일에 따라 정답과 오답이 된다.** 재시도 토픽은 처리량을 지키는 좋은 패턴이지만, 순서가 결과를 바꾸는 일에서는 잔액을 깨뜨린다.
  고르는 기준은 "권장 여부"가 아니라 **"이 메시지에 순서가 의미 있는가"** 다.
- **순서를 지키는 대가는 이웃이 치른다.** 한 사용자의 일시 실패 20초가 같은 파티션의 다른 사용자를 22초 기다리게 했다.
  그래서 **다시 해도 안 되는 실패는 빨리 빼내야** 하고, 빼낼 때는 **그 사용자만** 멈춰야 한다 (보류).
- **"실패를 빼낸다"와 "순서를 지킨다"는 사용자 단위 보류로 함께 얻을 수 있다.** 파티션 전체를 멈추지도, 건너뛰지도 않는 중간 지점이다.
- **깨진 메시지는 리스너 앞에서 실패한다.** `ErrorHandlingDeserializer` 로 실패를 리스너 단계로 넘겨야 에러 처리기가 DLT 로 뺄 수 있다. TS-2 의 무한 멈춤이 이것이었다.
