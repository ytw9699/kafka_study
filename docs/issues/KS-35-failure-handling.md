## 배경

지금 워커는 **처리에 실패하면 어떻게 할지 정해 두지 않았다.**
[TS-2](../troubleshooting/TS-2-poison-pill.md)에서 형식이 깨진 메시지 하나 때문에 워커가 무한 재시도로 멈추는 것을 겪었지만,
그때는 토픽을 비워서 넘어갔을 뿐 **해결하지 않았다.**

실무에서 Kafka 를 쓰면 반드시 정해야 하는 것이 이것이다.

- 잠깐 실패한 것(DB 일시 장애, 외부 API 타임아웃)은 **몇 번, 얼마 간격으로 다시 시도**하는가
- 다시 해도 안 되는 것(잘못된 데이터)은 **어디로 빼 두고** 다음으로 넘어가는가 — DLT(Dead Letter Topic)
- 그 사이 **순서는 지켜지는가**

그리고 이 프로젝트에서는 이 셋이 **정면으로 충돌한다** ([01. 기획서 5절](../planning/01-planning.md)).

```
사용자 A:  ① 5,000 적립   ② 3,000 사용 (실패)   ③ 2,000 사용

②를 DLT로 빼고 ③을 먼저 처리 → ②를 건너뛴 잔액이 된다 → 영구히 틀린다
```

## 목표

1. 실패를 처리하지 않으면 **워커가 멈춘다**는 것을 다시 겪는다
2. Spring Kafka 가 권장하는 **non-blocking retry 가 포인트 계산을 깨뜨리는 것**을 화면에서 본다 (실험 E)
3. **blocking retry** 로 바꿔 순서를 지키고, 그 대가로 **같은 파티션의 다른 사용자까지 멈추는 것**을 본다 (실험 F)
4. 다시 해도 안 되는 실패만 **빠르게 DLT 로 격리**해 파티션을 다시 흐르게 한다
5. **깨진 메시지(poison pill)** 가 워커를 멈추지 않게 격리한다

| # | 작업 | 확인 방법 |
|---|---|---|
| 7-1 | 특정 조건에서 예외를 던지는 코드 삽입 | 워커가 무한 재시도로 멈춤 |
| 7-2 | ★ non-blocking retry(retry topic) 구성 | 실패한 거래가 나중에 처리됨 |

| 7-6 | 영구 실패 판별 → DLT 로 격리 | 파티션이 다시 흐름 |
| 7-7 | Kafka UI 에서 DLT 내용과 원인 헤더 확인 | 실패 메시지 확인 |
| 7-8 | 일시적 실패(재시도) vs 영구 실패(DLT) 기준 정리 | 문서화 |
| **추가** | `ErrorHandlingDeserializer` 로 **깨진 메시지 격리** | TS-2 의 원시 JSON 을 넣어도 워커가 멈추지 않고 DLT 로 감 |
| **추가** | **포인트 계산 vs 메시지 발송** 비교 정리 | 순서가 중요한 일은 blocking, 각 건이 독립적인 일(발송)은 non-blocking + DLT 가 맞다는 것을 문서로 |

## 사전 결정할 것

- [ ] 실패를 일으키는 방법 — 특정 `userId` · 금액에서 예외, 또는 실험용 API 로 켜고 끄기
- [ ] 영구 실패 vs 일시 실패 구분 기준 — 예외 종류로 나눌지
- [ ] 영구 실패한 거래 **뒤의 같은 사용자 거래**를 어떻게 할지 — 같이 보류할지 (DLT 로 빼면 순서가 깨진다)
- [ ] DLT 에 쌓인 거래를 **다시 처리하는 방법** (재처리 API 또는 수동)
- [ ] 화면에 DLT 현황을 보여줄지

## 완료 조건 (DoD)

- [ ] 실험 E — non-blocking retry 로 잔액이 틀어지는 것을 화면에서 확인했다
- [ ] blocking retry 로 바꿔 잔액이 맞는 것을 확인했다
- [ ] 실험 F — 한 사용자의 실패가 같은 파티션의 다른 사용자를 멈추는 것을 확인했다
- [ ] 영구 실패가 DLT 로 빠지고 파티션이 다시 흐르는 것을 확인했다
- [ ] 깨진 메시지를 넣어도 워커가 멈추지 않는다
- [ ] 일시 실패 · 영구 실패 기준과 "포인트 계산 vs 발송" 비교를 문서로 남겼다
