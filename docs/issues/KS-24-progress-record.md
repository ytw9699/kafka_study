## 정정한 불일치

### Chart.js 를 결국 쓰지 않았다

기술 스택에 적혀 있었지만 **코드에서 한 번도 쓰지 않았다.**

도메인이 주문/매출 → 포인트 원장으로 바뀌면서([KS-13](KS-13-pivot-ledger.md))
시계열 차트가 필요 없어졌다. 지금 화면은 **표와 색상 뱃지**로 되어 있고,
**"두 숫자가 같은가 다른가"를 보는 데는 그쪽이 정확하다.**

`package.json` 의 의존성은 6~7단계에서 쓸 여지가 있어 남겨뒀다.

### 원자적 upsert 를 쓰지 않았다

로드맵 3-2 에 `ON CONFLICT` 라고 적혀 있었으나 **JPA `findById` + `save`** 를 썼다.

파티션 키 덕분에 **경합 자체가 없기 때문**이다. 근거를 로드맵에 명시했다.
→ [KS-16](KS-16-balance-worker.md)

### 5단계는 워커 1개로 진행했다

`rebuild` 는 **호출한 워커의 파티션만** 되감는다. 분산 재생 조율은 범위 밖이므로
워커 1개로 실험했다. 로드맵에 제약으로 명시했다.

## 배운 것

### 티켓의 "배운 것"만으로는 부족하다

각 티켓에 배운 것을 성실히 남겼지만, **전체 그림은 23개를 다 읽어야 보인다.**

특히 **여러 티켓에 걸쳐 드러난 것**들이 어디에도 정리되어 있지 않았다.

- 시나리오가 세 번 무너진 이유 (KS-12 → KS-13)
- 설계가 틀렸다가 고쳐진 지점 (KS-11 → KS-18)
- 파티션 키가 순서와 동시성을 함께 준다는 것 (KS-16 → KS-20)

**티켓은 "그때 무엇을 했나"를 기록하고, 종합 문서는 "무엇을 알게 됐나"를 기록한다.**
둘은 다른 문서다.

### 문서와 구현은 자연스럽게 어긋난다

Chart.js 는 도메인이 바뀔 때 같이 지웠어야 했고,
`ON CONFLICT` 는 구현하며 필요 없다는 것을 알았을 때 로드맵을 고쳤어야 했다.

**"결정을 바꿨으면 문서도 바꾼다"** 가 규칙이지만 실제로는 놓친다.
그래서 **주기적으로 대조하는 시점**이 필요하다. 단계 완료 시점이 그 자리다.

### 정정 자체가 기록할 가치가 있다

"Chart.js 를 안 썼다"를 그냥 지우는 대신 **왜 안 쓰게 됐는지**를 남겼다.
"표가 차트보다 나은 경우"라는 판단이 거기 들어 있기 때문이다.

**탈락한 선택에도 근거가 있고, 그것이 다음 판단에 쓰인다.**
