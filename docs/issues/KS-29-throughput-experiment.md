## 배경

지금까지 확인한 것은 Kafka의 **정확성** 쪽이다 — 순서([KS-20](KS-20-order-broken-experiment.md)), 장애 인수([KS-21](KS-21-rebalance-experiment.md)), 재생 · 멱등([KS-23](KS-23-idempotency-experiment.md)), 실패 처리([KS-35](KS-35-failure-handling.md)).

하지만 Kafka를 쓰는 가장 흔한 이유는 **처리량**이다. 대용량 스트리밍, 데이터 파이프라인, 로그 집계가 모두
"많이, 빠르게 받아 내고, 소비자를 늘려 수평 확장한다"에 기대고 있다.

이 프로젝트는 그것을 **숫자로 재 본 적이 없다.** 실험 규모도 수십 ~ 수백 건이었다.
[KS-19](KS-19-worker-scale-out.md)에서 "워커 4개면 하나가 논다"는 배정만 봤지, 그래서 **얼마나 빨라지는지**는 보지 않았다.

> [01. 기획서 3번](../planning/01-planning.md)대로, 노트북 한 대로 "Kafka가 필요한 규모"를 증명할 수는 없다.
> 이 실험의 목표는 증명이 아니라 **처리량을 결정하는 변수들이 실제로 어떻게 작동하는지 체감하는 것**이다.

## 목표

1. 워커 수를 늘리면 처리 속도가 **어디까지** 빨라지는가 — 파티션 수가 상한임을 시간으로 확인
2. 소비가 발행보다 느릴 때 **lag** 이 쌓이고 빠지는 모습을 관찰
3. 프로듀서 배치 설정이 **발행 처리량**을 얼마나 바꾸는가
4. 처리가 느리면 **멀쩡한 워커가 그룹에서 쫓겨나는** 것을 확인한다 (`max.poll.interval.ms`)
   — 7단계의 `BLOCKING` 재시도(2초 × 최대 30번, 약 1분)도 "느린 처리"다. 재시도 시간이 `max.poll.interval.ms`(기본 5분)를 넘으면 같은 일이 생긴다

## 실험 설계 (초안)

### 실험 1 — 워커 수와 처리 시간

| 조건 | 측정 |
|---|---|
| 파티션 3, 워커 1 · 2 · 3 · 4 | 같은 N건(예: 5만 건)을 다 처리하는 데 걸린 시간 |

예상: 1 → 3 까지는 빨라지고, 4 는 3 과 같다 (한 워커는 논다).
**예상과 다르면 그 이유가 학습 포인트다** — 예: 병목이 Kafka가 아니라 DB 쓰기일 수 있다.

### 실험 2 — lag 관찰

- 워커 1개로 대량 발행 → lag 이 쌓이는 것을 Kafka UI · `kafka-consumer-groups.sh --describe` 로 관찰
- 워커를 추가 → lag 이 빠지는 속도 변화 관찰
- **큐가 폭주를 흡수한다**([07 문서 2번](../planning/07-message-queue.md))는 말을 눈으로 확인

### 실험 3 — 프로듀서 배치

| 설정 | 측정 |
|---|---|
| `linger.ms` 0 / 5 / 50, `batch.size` 기본 / 확대 | 초당 발행 건수 |
| `acks` all / 1 | 처리량과 내구성의 교환 |

`.get()` 으로 매 건 기다리는 현재 발행 방식([LedgerEventPublisher](../../backend/ledger-api/src/main/kotlin/com/ytw/kafkastudy/ledgerapi/publish/LedgerEventPublisher.kt))이
처리량을 얼마나 깎는지도 비교한다 — 동기 대기 vs 비동기 콜백.

### 실험 4 — 느린 처리가 일으키는 리밸런싱

컨슈머는 한 번에 여러 건(`max.poll.records`, 기본 500)을 가져와 처리한 뒤 다음을 가져온다.
그 사이 간격이 `max.poll.interval.ms`(기본 5분)를 넘으면 Kafka 는 **"이 워커는 멈췄다"** 고 보고 그룹에서 내보낸다.

```
워커: 500건 가져옴 → 건당 1초 걸림 → 500초(8분 이상)
Kafka: 5분 동안 다음 요청이 없음 → 워커를 그룹에서 제외 → 리밸런싱
워커: 처리를 마치고 커밋하려 함 → 이미 파티션을 잃어서 커밋 실패
→ 다른 워커가 같은 거래를 처음부터 다시 처리 → 중복
```

하트비트(실험 B 의 `session.timeout.ms`)는 계속 가고 있어서 **살아 있는데도 쫓겨난다.**
대량 처리에서 가장 흔한 장애 중 하나다.

| 조건 | 확인할 것 |
|---|---|
| 처리마다 인위적으로 지연, `max.poll.interval.ms` 를 짧게 | 멀쩡한 워커가 쫓겨나고 리밸런싱이 반복되는지, 중복 처리가 생기는지 |
| `max.poll.records` 를 줄이거나 처리를 빠르게 | 리밸런싱이 멈추는지 |
| 멱등 처리 ON | 중복으로 받아도 잔액이 맞는지 |
