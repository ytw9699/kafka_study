## 배경

[기획서 6절](../planning/01-planning.md)의 도구 비교표에 이렇게 적었다.

> ~~"셋을 동시에 만족하는 것은 Kafka뿐이다."~~

**틀렸다. AWS Kinesis 를 빠뜨렸다.**

Kinesis 도 **샤드(= 파티션) 기반 로그**다.

| 요구사항 | Kinesis |
|---|---|
| 1+2+3 순서·병렬·인수 | ✅ 파티션 키로 샤드 배정, 컨슈머 자동 배분 |
| 4 재생 | ✅ 최대 365일 보존, 시퀀스/시각 기준 재생 |
| 5 독립 소비자 | ✅ Enhanced Fan-Out |

기존 표는 **"큐 계열이 탈락한다"** 를 보여준 것이지, Kafka 가 유일하다는 증명이 아니었다.

## 목표

비교표를 현업 기준으로 정확하게 고치고, "왜 Kafka인가"의 근거를 **기능이 아닌 것**으로 옮긴다.

## 정정 내용

### 결론을 바꿨다

```
"셋을 제공하는 것은 Kafka뿐"                              ← 과장
        ↓
"로그 기반 브로커 계열이며, 현업에서는 Kafka와 Kinesis"    ← 정직
```

### "왜 Kafka인가"의 근거가 바뀌었다

기능으로는 Kinesis 와 동등하므로, 근거는 **기능 밖**에 있어야 한다.

| 근거 | |
|---|---|
| **벤더 중립** | Kinesis 는 AWS 종속. Kafka 는 온프렘·모든 클라우드 |
| **생태계** | Connect · Streams · **Debezium(CDC)** · Schema Registry |
| **참고 자료** | 운영 사례·문서·커뮤니티가 가장 많다 |
| **자체 호스팅** | 이 프로젝트처럼 로컬에서 전부 돌려볼 수 있다 |

**AWS만 쓰는 조직이고 운영 인력이 없다면 Kinesis 가 합리적일 수 있다.**

### 표를 부풀리지 않았다

Pulsar · Event Hubs · NATS JetStream · Pub/Sub 도 대체로 만족하지만
**국내 현업에서 마주칠 확률이 낮아** 표에서 빼고 각주로만 남겼다.

**"정확하게"와 "실용적으로"는 다르다.** 전부 나열하면 정확하지만 판단에 도움이 안 된다.

## 배운 것

| # | 무엇 | 어디 |

| 3 | **"셋을 제공하는 것은 Kafka뿐"** | 이 티켓 |

**패턴이 같다.** "Kafka 가 특별하다"를 말하고 싶어서 **비교 대상을 좁게 잡았다.**
큐 계열만 놓고 비교하면 Kafka 가 유일해 보이지만, 같은 계열(로그 기반)을 넣으면 아니다.

> **비교표는 무엇을 넣었느냐보다 무엇을 뺐느냐가 결론을 정한다.**

### 기능이 같으면 근거는 기능 밖에 있다

Kinesis 와 기능이 동등하다는 것을 인정하고 나니, **왜 Kafka인가**의 답이 오히려 선명해졌다 —
생태계, 벤더 중립성, 참고 자료.

이것들은 **기술 비교표에 안 나오지만 실무 선택을 좌우하는 것**들이다.

### Kafka 의 파티션 단위 배분은 구조적 선택이지 본질이 아니다

[KS-19](KS-19-worker-scale-out.md)에서 **"컨슈머를 파티션 수보다 늘려도 소용없다"** 를 확인했다.
이것을 "메시징의 원리"처럼 이해하기 쉬운데, 아니다.

**Pulsar 의 `Key_Shared` 구독은 파티션이 아니라 키 단위로 배분**하므로 그 제약이 없다.

같은 문제(순서 보장 + 병렬 처리)를 푸는 **다른 설계**가 존재한다는 것을 알아야
"Kafka 를 배웠다"가 "메시징을 이해했다"로 넘어간다.
