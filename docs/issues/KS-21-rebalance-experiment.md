## 배경

[요구사항 3](../planning/01-planning.md) — **"워커가 죽어도 유실·중단 없이 남은 워커가 이어받는다."**

[05. DB로 직접 만들면](../planning/05-why-not-diy.md)에서 정리했듯,
이것을 직접 구현하려면 멤버십 관리 · 하트비트 · lease · fencing token 이 필요하다.
Kafka 는 이것을 **컨슈머 그룹 프로토콜로 제공한다.**

이 티켓은 그것이 실제로 동작하는 것을 눈으로 확인한다.

## 목표

워커를 죽이고 살리면서 **파티션이 재배정되는 것을 화면에서 보고**,
그 과정에서 **잔액이 정확하게 유지되는지** 확인한다.

## 선행 조건

- [KS-19](KS-19-worker-scale-out.md) 완료
- 파티션 키는 `USER_ID` (정상 모드)

## 작업 내용

- [ ] 워커 3개 기동 → 각자 파티션 1개씩 배정 확인
- [ ] 지속적으로 거래를 발생시키며(burst 반복) 워커 하나 종료
- [ ] ★ **화면에서 파티션이 재배정되는 것 확인**
- [ ] 재배정에 걸린 시간 측정 (`session.timeout.ms` 와 비교)
- [ ] 재배정 후 **잔액이 기대 잔액과 일치**하는지 확인 (유실·중복 없음)
- [ ] 워커를 다시 띄워 3개로 복귀
- [ ] 워커 4개 (파티션 3개) → **하나가 노는 것 확인**
- [ ] 워커 1개만 남기기 → 파티션 3개를 혼자 처리
- [ ] 결과를 "배운 것"에 기록

## 상세 설계

### 확인할 것

| # | 상황 | 기대 결과 |
|---|---|---|
| 1 | 워커 3개 | 파티션 1개씩 |
| 2 | 하나 종료 | 남은 둘이 3개를 나눔. **처리 계속됨** |
| 3 | 재배정 후 잔액 | 기대값과 일치 (유실·중복 없음) |
| 4 | 다시 3개 | 1개씩으로 복귀 |
| 5 | **4개** (파티션 3개) | **하나는 논다** |
| 6 | 1개만 | 혼자 3개 처리 |

5번은 [KS-3](KS-3-kafka-cli-basics.md) CLI 실습에서 이미 본 것이지만,
**애플리케이션 수준에서 다시 확인**한다. 파티션 수가 병렬도의 상한이라는 제약이 실무 설계에 직결되기 때문이다.

### 재배정에 시간이 걸린다

`kill` 로 죽이면 Kafka 는 즉시 알지 못한다.
**하트비트가 끊긴 것을 `session.timeout.ms`(기본 45초) 동안 기다린 뒤** 리밸런싱을 시작한다.

그동안 그 워커가 맡던 파티션은 **아무도 처리하지 않는다.**

> **감지 시간과 오탐(false positive)의 트레이드오프다.**
> 짧게 잡으면 GC 로 잠깐 멈춘 워커까지 죽었다고 판단해 불필요한 리밸런싱이 일어난다.
> [05. 문서](../planning/05-why-not-diy.md)의 split-brain 이 바로 이 지점에서 생긴다.

실험 중 답답하면 `session.timeout.ms` 를 짧게(예: 10초) 조정해볼 수 있다.
단, 그 대가도 함께 관찰한다.

### 정상 종료와 강제 종료는 다르다

| | `onPartitionsRevoked` | 리밸런싱 시작 |
|---|---|---|
| 정상 종료 (`SIGTERM`) | 호출됨 | 즉시 |
| 강제 종료 (`kill -9`) | **호출 안 됨** | `session.timeout` 후 |

둘 다 해보고 차이를 확인한다.
