## 배경

[요구사항 3](../planning/01-planning.md) — **"워커가 죽어도 유실·중단 없이 남은 워커가 이어받는다."**

[05. DB로 직접 만들면](../planning/05-why-not-diy.md)에서 정리했듯,
이것을 직접 구현하려면 멤버십 관리 · 하트비트 · lease · fencing token 이 필요하다.
Kafka 는 이것을 **컨슈머 그룹 프로토콜로 제공한다.**

이 티켓은 그것이 실제로 동작하는 것을 눈으로 확인한다.

## 목표

워커를 죽이고 살리면서 **파티션이 재배정되는 것을 화면에서 보고**,
그 과정에서 **잔액이 정확하게 유지되는지** 확인한다.

## 선행 조건

- [KS-19](KS-19-worker-scale-out.md) 완료
- 파티션 키는 `USER_ID` (정상 모드)

- [x] 재배정 후 **잔액이 기대 잔액과 일치**하는지 확인 (유실·중복 없음)
- [x] 워커를 다시 띄워 3개로 복귀
- [x] 워커 4개 (파티션 3개) → **하나가 노는 것 확인**
- [x] 워커 1개만 남기기 → 파티션 3개를 혼자 처리

## 상세 설계

### 확인할 것

| # | 상황 | 기대 결과 |
|---|---|---|
| 1 | 워커 3개 | 파티션 1개씩 |
| 2 | 하나 종료 | 남은 둘이 3개를 나눔. **처리 계속됨** |
| 3 | 재배정 후 잔액 | 기대값과 일치 (유실·중복 없음) |
| 4 | 다시 3개 | 1개씩으로 복귀 |
| 5 | **4개** (파티션 3개) | **하나는 논다** |
| 6 | 1개만 | 혼자 3개 처리 |

5번은 [KS-3](KS-3-kafka-cli-basics.md) CLI 실습에서 이미 본 것이지만,
**애플리케이션 수준에서 다시 확인**한다. 파티션 수가 병렬도의 상한이라는 제약이 실무 설계에 직결되기 때문이다.

### 재배정에 시간이 걸린다

`kill` 로 죽이면 Kafka 는 즉시 알지 못한다.
**하트비트가 끊긴 것을 `session.timeout.ms`(기본 45초) 동안 기다린 뒤** 리밸런싱을 시작한다.

그동안 그 워커가 맡던 파티션은 **아무도 처리하지 않는다.**

> **감지 시간과 오탐(false positive)의 트레이드오프다.**
> 짧게 잡으면 GC 로 잠깐 멈춘 워커까지 죽었다고 판단해 불필요한 리밸런싱이 일어난다.
> [05. 문서](../planning/05-why-not-diy.md)의 split-brain 이 바로 이 지점에서 생긴다.

실험 중 답답하면 `session.timeout.ms` 를 짧게(예: 10초) 조정해볼 수 있다.
단, 그 대가도 함께 관찰한다.

### 정상 종료와 강제 종료는 다르다

| | `onPartitionsRevoked` | 리밸런싱 시작 |
|---|---|---|
| 정상 종료 (`SIGTERM`) | 호출됨 | 즉시 |
| 강제 종료 (`kill -9`) | **호출 안 됨** | `session.timeout` 후 |

둘 다 해보고 차이를 확인한다.

## 실행 결과

### 정상 종료 vs 강제 종료 — 재배정 시간이 6배 차이났다

| | `onPartitionsRevoked` | 재배정까지 |
|---|---|---|
| **정상 종료** (`kill` = SIGTERM) | **호출됨** | **8초** |
| **강제 종료** (`kill -9`) | **0회** | **47초** |

```
정상 종료:
  파티션 반납 worker=w-8093 partitions=[2]     ← 스스로 알렸다
  → 재배정 완료: 8초
  w-8082: [0, 1] gen=3
  w-8092: [2]    gen=4

강제 종료:
  onPartitionsRevoked 호출 횟수: 0             ← 알릴 기회가 없었다
  → 재배정 완료: 47초
```

### 유실도 중복도 없다

```
발행 총 135 건
처리 적용 128 + 거절 7 = 135 건               ← 정확히 일치
balance-group  p1 lag=0  p2 lag=0
```

리밸런싱이 **두 번** 일어나는 동안 계속 거래를 발행했는데도 숫자가 맞는다.

### 워커 4개 (파티션 3개)

```
w-8082: [0]
w-8092: [2]
w-8093: [1]
w-8094: []      ← 놀고 있음
```

### 워커 1개만

```
w-8082: [0, 1, 2] gen=8      ← 혼자 3개 처리
```

## 배운 것

### 정상 종료와 강제 종료의 차이가 6배였다 (8초 vs 47초)

이유는 **누가 먼저 알리느냐**다.

- **정상 종료**: 컨슈머가 스스로 `LeaveGroup` 을 보낸다 → 코디네이터가 **즉시** 리밸런싱
- **강제 종료**: 아무 말 없이 사라진다 → **하트비트가 끊긴 것을 기다려야** 안다 (`session.timeout.ms` 기본 45초)

47초는 기본값 45초와 거의 일치한다. **추측이 아니라 설정값이 그대로 관찰됐다.**

> 실무 함의: **배포 시 파드를 `SIGKILL` 로 죽이면 최대 45초간 그 파티션이 방치된다.**
> graceful shutdown 을 보장해야 하는 구체적 이유다.

### "감지 시간"과 "오탐"은 같은 다이얼의 양끝이다

`session.timeout.ms` 를 줄이면 재배정이 빨라진다. 그런데 **GC 로 잠깐 멈춘 워커까지 죽었다고 판단**하게 된다.

그러면 살아 있는 워커의 파티션이 다른 워커에게 넘어가고, 원래 워커가 깨어나 쓰기를 시도한다
— **[05. 문서](../planning/05-why-not-diy.md)의 split-brain 이다.**

Kafka 는 이것을 **generation id 로 막는다.** 이번 실험에서 세대가 계속 올라가는 것을 봤다
(`gen 2 → 3 → 4 → … → 8`). 옛 세대의 offset 커밋은 브로커가 거부한다.

> 직접 만들었다면 이 fencing 부터 설계해야 했다.
> **"리밸런싱을 만든다"는 것은 사실상 "fencing token 을 만든다"는 뜻이다.**

### 리밸런싱 중에도 정확성이 깨지지 않는다

리밸런싱이 두 번 일어나고 워커가 3→2→3→4→1 로 바뀌는 동안 계속 거래를 발행했는데
**발행 135건 = 처리 135건**, lag 0 이었다.

유실도 중복도 없다. 이유는 offset 커밋이 **파티션 소유권과 함께** 움직이기 때문이다.
소유권을 넘기기 전에 커밋하고, 새 소유자는 커밋된 지점부터 읽는다.

> [KS-18](KS-18-worker-restart-offset.md)에서 확인한 "재기동은 이어읽기"와 같은 성질이
> **워커가 바뀌는 상황에서도** 성립한다는 것을 확인했다.

### 파티션 수는 병렬도의 상한이자 하한이다

- **4개 워커** → 하나가 논다 (상한)
- **1개 워커** → 혼자 3개를 처리한다 (하한 없음)

워커가 줄어도 **일이 사라지지 않고 남은 워커에게 몰린다.**
장애 시 처리량이 떨어질 뿐 멈추지는 않는다 — 이것이 요구사항 3의 실체다.

### 이번 실험이 요구사항 3을 증명했다

> **"워커가 죽어도 유실·중단 없이 남은 워커가 이어받는다."**

[05. 문서](../planning/05-why-not-diy.md)에서 이것을 직접 만들려면
멤버십 · 하트비트 · lease · fencing token 이 필요하다고 정리했다.

**Kafka 에서는 워커를 하나 더 띄우는 것으로 끝났다.** 코드는 `ConsumerRebalanceListener`
하나뿐이고, 그것도 **화면에 보여주기 위한 것**이지 동작에 필요한 것이 아니다.

이것이 "직접 만들 것이냐, 제공받을 것이냐"의 실물이다.
