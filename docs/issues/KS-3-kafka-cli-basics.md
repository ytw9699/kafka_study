## 배경

Spring 위에서 시작하면 `@KafkaListener`가 알아서 해주는 것들 때문에 토픽·파티션·offset의 실체가 안 잡힌다.
**Kafka가 큐와 다르다는 것을 CLI 수준에서 먼저 확인**하고 넘어간다.

선행: [KS-2](KS-2-infra-docker-compose.md) (Kafka 컨테이너 기동)

## 목표

CLI만으로 Kafka의 세 가지 성질을 눈으로 확인한다. 코드는 쓰지 않는다.

## 작업 내용

- [x] `ledger-events` 토픽 생성 (파티션 3, 복제 1)
- [x] 콘솔 producer로 **키를 지정해** 메시지 발행
- [x] 같은 키로 여러 건 발행 → 파티션 고정 확인
- [x] **서로 다른** 컨슈머 그룹 2개로 동시 구독 → 둘 다 받음
- [x] **같은** 컨슈머 그룹으로 인스턴스 2개 → 파티션을 나눠 가짐
- [x] `--from-beginning`으로 재소비
- [x] `kafka-consumer-groups --describe`로 그룹별 offset 확인
- [x] `docker compose down` → `up` 후 메시지 유지 확인

## 상세 설계

### 확인할 세 가지

| # | 확인 | 의미 |
|---|---|---|
| 1 | 같은 키 → **항상 같은 파티션** | 순서 보장의 기반 |
| 2 | **다른** 그룹 2개 → 같은 메시지를 **각각** 수신 | 브로드캐스트 (SSE 게이트웨이가 쓸 방식) |
| 3 | **같은** 그룹 인스턴스 2개 → 파티션을 **나눠 가짐** | 작업 분배 (잔액 워커가 쓸 방식) |
| 4 | `--from-beginning` → **이미 소비한 메시지를 다시** 읽음 | 재생 |

**2번과 3번의 차이가 핵심이다.** 같은 토픽인데 그룹 구성에 따라 동작이 완전히 다르다.
이 프로젝트는 두 가지를 모두 쓴다 — `gateway-group`(브로드캐스트)과 `balance-group`(분배).

### 볼륨 검증

`docker compose down` 후 재기동해도 토픽과 메시지가 유지되어야 한다.
**이것이 깨지면 3단계(뒤늦게 합류한 컨슈머가 과거를 읽는다)가 성립하지 않는다.**

## 실행 방법

실습을 재현 가능하게 [`docker/cli-lab.sh`](../../docker/cli-lab.sh)로 남겼다.

```bash

```


## 배운 것

### 같은 토픽인데 그룹 구성에 따라 동작이 정반대다

| | 결과 | 이 프로젝트에서 |
|---|---|---|
| **다른 그룹** 2개 | 둘 다 전부 받음 (브로드캐스트) | `gateway-group` — SSE 중계 |
| **같은 그룹** 인스턴스 2개 | 파티션을 나눠 가짐 (분배) | `balance-group` — 잔액 워커 |

**이것이 이 단계의 핵심이다.** 설정 한 줄(`--group`) 차이인데 의미가 완전히 다르다.

그리고 이 차이가 곧 [설계](../planning/02-architecture.md)의 근거다 —
SSE를 여러 인스턴스인 `balance-worker`에 붙이면 브라우저가 한 인스턴스의 파티션 이벤트만 받게 되므로,
단일 인스턴스인 `ledger-api`가 **별도 그룹**으로 전체를 구독해 중계한다.

### 키 해시 분포는 균등하지 않다

`user-1`, `user-2`, `user-3`이 **전부 파티션 2**로 갔다. 처음엔 키 파싱이 실패한 줄 알았는데,
키를 12개로 늘려보니 정상 분산됐다 (`0: user-8,12` / `1: user-4,5,11` / `2: 나머지 7개`).

**우연이 아니라 구조적 특성이다.** 파티션 3개에 키를 murmur2 해시로 나누면 균등할 수 없다.
실험 3에서도 인스턴스별 수신량이 2/7/3으로 크게 갈렸다.

→ 특정 파티션에 트래픽이 몰리는 **hot partition** 문제가 실재하고,
   7단계의 "한 사용자 실패가 같은 파티션의 다른 사용자를 막는다"와 직결된다.

### 파티션 수가 병렬 처리의 상한이다

컨슈머 4개를 같은 그룹에 넣었더니 **하나는 파티션을 못 받고 놀았다.**

컨슈머를 늘려도 파티션보다 많아지면 소용이 없다.
4단계에서 `balance-worker`를 늘릴 때 그대로 적용되는 제약이며,
**파티션 수는 나중에 늘릴 수는 있어도 줄일 수 없으므로** 처음부터 여유 있게 잡아야 한다.

### 실험 순서가 결과를 바꾼다 — 컨슈머를 먼저 붙여야 한다

처음에 "발행 → 컨슈머 3개 기동" 순서로 했더니 인스턴스별 수신이 14/5/0으로 나왔다.
먼저 붙은 컨슈머가 이미 다 소비하고 offset을 커밋해버려, 뒤에 합류한 인스턴스는 읽을 게 없었던 것이다.

**"컨슈머를 먼저 붙이고 그 다음 발행"** 으로 바꾸니 정확히 파티션 1개씩 배정되고 합계가 발행량과 일치했다.

→ 이것 자체가 offset의 동작을 보여준다. 컨슈머 그룹의 진행 상태는 **공유**되며,
   늦게 합류해도 "남들이 이미 읽은 것"을 다시 주지 않는다.
   6단계에서 `fraud-service`가 **새 그룹**으로 합류해야 과거를 전부 읽는 이유가 여기 있다.

### `--from-beginning`은 그룹이 없을 때만 처음부터다

`--group` 없이 실행하면 임시 그룹이 만들어져 매번 처음부터 읽는다.
`--group`을 주면 **커밋된 offset이 있을 때 `--from-beginning`이 무시된다.**

→ 5단계에서 `auto-offset-reset: earliest`가 "최초 1회용"인 것과 같은 원리다.
   재생을 반복하려면 **명시적 seek**이 필요하다.
