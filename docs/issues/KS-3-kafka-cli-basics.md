## 배경

Spring 위에서 시작하면 `@KafkaListener`가 알아서 해주는 것들 때문에 토픽·파티션·offset의 실체가 안 잡힌다.
**Kafka가 큐와 다르다는 것을 CLI 수준에서 먼저 확인**하고 넘어간다.

선행: [KS-2](KS-2-infra-docker-compose.md) (Kafka 컨테이너 기동)

## 목표

CLI만으로 Kafka의 세 가지 성질을 눈으로 확인한다. 코드는 쓰지 않는다.

## 작업 내용

- [ ] `order-events` 토픽 생성 (파티션 3, 복제 1)
- [ ] 콘솔 producer로 **키를 지정해** 메시지 발행
- [ ] 같은 키로 여러 건 발행 → 파티션 고정 확인
- [ ] 컨슈머 그룹 2개로 동시 구독
- [ ] `--from-beginning`으로 재소비
- [ ] `kafka-consumer-groups --describe`로 그룹별 offset 확인
- [ ] `docker compose down` → `up` 후 메시지 유지 확인
- [ ] 확인 결과를 이 문서 "배운 것"에 기록

## 상세 설계

### 확인할 세 가지

| # | 확인 | 큐(RabbitMQ/SQS)라면 |
|---|---|---|
| 1 | 같은 키 → **항상 같은 파티션** | 키 개념 자체가 다름 |
| 2 | 서로 다른 컨슈머 그룹이 같은 메시지를 **각각** 수신 | 하나만 받고 사라짐 |
| 3 | `--from-beginning`으로 **이미 소비한 메시지를 다시** 읽음 | 불가능 |

3번이 Kafka의 정체성이다.

### 볼륨 검증

`docker compose down` 후 재기동해도 토픽과 메시지가 유지되어야 한다.
**이것이 깨지면 3단계(뒤늦게 합류한 컨슈머가 과거를 읽는다)가 성립하지 않는다.**

## 완료 조건 (DoD)
