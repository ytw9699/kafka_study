# KS-18: 워커 재기동 — offset 이어읽기 확인

| | |
|---|---|
| **타입** | EXPERIMENT |
| **상태** | IN REVIEW |
| **단계** | 3단계 |
| **브랜치** | `experiment/KS-18-worker-restart-offset` |
| **PR** | [#22](https://github.com/ytw9699/kafka_study/pull/22) |

## 배경

`auto-offset-reset: earliest` 를 설정해두면 **재기동할 때마다 처음부터 읽을 것 같지만 아니다.**

이 설정은 **커밋된 offset 이 없을 때만** 동작한다. 한 번 소비하면 offset 이
`__consumer_offsets` 에 커밋되고, 재기동하면 **거기서 이어서 읽는다.**

이것이 실무 정상 동작이며, **5단계에서 명시적 재생 API 를 따로 만드는 이유**다.

## 목표

"재기동 = 이어읽기"를 직접 확인하고, `earliest` 가 최초 1회용임을 이해한다.

## 작업 내용

- [x] 거래를 여러 건 발행해 잔액을 만든다
- [x] Kafka UI 에서 `balance-group` 의 CURRENT-OFFSET 기록
- [x] 워커를 종료했다가 다시 기동
- [x] 잔액이 **그대로 유지**되는지 확인 (중복 적용 없음)
- [x] offset 이 **이어지는지** 확인
- [x] 워커가 꺼진 동안 발행한 거래가 **재기동 후 처리**되는지 확인
- [x] 컨슈머 그룹을 바꿔 기동 → 이번엔 처음부터 읽는지 확인
- [x] 결과를 "배운 것"에 기록

## 상세 설계

### 확인할 세 가지

| # | 상황 | 기대 결과 |
|---|---|---|
| 1 | 워커 재기동 | 잔액 유지, 중복 적용 없음 |
| 2 | 꺼진 동안 발행된 거래 | 재기동 후 처리됨 (유실 없음) |
| 3 | **새 컨슈머 그룹**으로 기동 | 처음부터 전부 읽음 |

3번이 6단계(`fraud-service` 나중에 합류)의 원리와 같다.

### 왜 이것을 별도 티켓으로 두는가

코드 변경이 거의 없고 **관찰이 목적**이므로 `EXPERIMENT` 타입이다.

이 동작을 정확히 이해하지 못하면 5단계에서 **"재생이 왜 자동으로 안 되지"** 로 혼란이 생긴다.
설계서에도 "상태 재구축은 자동이 아니라 명시적"이라고 적어두었는데, 그 근거를 여기서 확인한다.

## 완료 조건 (DoD)

- [x] 재기동 후 잔액이 유지되고 중복 적용이 없다
- [x] 꺼진 동안의 거래가 유실 없이 처리된다
- [x] 새 그룹으로 기동하면 처음부터 읽는 것을 확인했다
- [x] `earliest` 가 최초 1회용임을 문서로 정리했다

## 실행 결과

### 실험 1·2 — 재기동은 이어읽기다

**재기동 전**

```
적용 36
  user-1: 22,090   user-2: 11,380   user-3: 4,620   user-4: 9,660

balance-group  p1 cur=9  end=9
               p2 cur=27 end=27
```

**워커를 끄고 6건 발행** → `lag=6` 으로 밀림

```
balance-group  p2 cur=27 end=33 lag=6
```

**재기동 후**

```
적용 42                                  ← 36 + 밀린 6건. 정확히 6만 늘었다
  user-1: 30,090   (22,090 +10,000 −2,000)
  user-2: 19,380   (11,380 +10,000 −2,000)
  user-3: 12,620   ( 4,620 +10,000 −2,000)
  user-4:  9,660   ← 그동안 거래가 없었으므로 그대로

balance-group  p1 cur=9  end=9  lag=0
               p2 cur=33 end=33 lag=0

offset 0 재처리 건수: 0                   ← 처음부터 읽지 않았다
```

**`auto-offset-reset: earliest` 인데도 처음부터 읽지 않았고, 중복 적용도 없었다.**

### 실험 3 — 새 그룹은 처음부터 읽는다

```
기존 balance-group     --from-beginning 을 줬는데도 수신:  0 건
새 그룹 balance-group-v2                          수신: 42 건
토픽 전체                                                 42 건
```

## 배운 것

### `auto-offset-reset` 은 "커밋된 offset 이 없을 때"의 기본값일 뿐이다

이름이 오해를 부른다. **"재기동하면 리셋한다"가 아니다.**

| 상황 | 동작 |
|---|---|
| 그룹이 그 파티션을 **처음** 만남 | `auto-offset-reset` 적용 (`earliest` → offset 0) |
| **커밋된 offset 이 있음** | 그 지점에서 이어 읽음. 설정은 **무시된다** |

`--from-beginning` 도 똑같다. 기존 그룹으로 주면 **0건**이 나온다.
그 옵션은 사실상 `auto.offset.reset=earliest` 를 켜는 것이고, 커밋이 있으면 발동하지 않는다.

> **offset 은 컨슈머가 아니라 브로커(`__consumer_offsets`)에 산다.**
> 프로세스를 죽였다 살려도 Kafka 는 기억하고 있다.

### 이것이 5단계에서 명시적 재생 API 를 만드는 이유다

"재기동하면 다시 읽겠지"라는 기대는 **틀렸다.**
전체 재생을 하려면 **명시적으로 seek** 해야 한다.

[설계서](../planning/02-architecture.md)에 "상태 재구축은 자동이 아니라 명시적"이라고 적어둔 근거를 여기서 확인했다.

> 설계 리뷰([KS-11](KS-11-design-finalize.md)) 때 이 성질을 놓쳐서
> "재기동하면 로그로부터 재구축된다"는 **동작하지 않는 설계**를 문서에 적었었다.
> 이번에 직접 확인하면서 그 수정이 옳았음이 입증됐다.

### 유실이 없다 — 워커가 꺼져 있어도 로그는 쌓인다

워커가 죽은 동안 발행된 6건이 `lag=6` 으로 남아 있다가 재기동 후 전부 처리됐다.

컨슈머 장애가 **데이터 유실로 이어지지 않는다.** 큐라면 컨슈머가 없을 때
메시지를 어디에 둘지가 문제가 되지만, Kafka 는 애초에 로그이므로 이 질문이 생기지 않는다.

### 그룹 이름을 바꾸는 것이 "새 소비자"를 만드는 방법이다

`balance-group-v2` 로 붙으니 42건을 전부 읽었다.
**6단계에서 `fraud-service` 가 과거를 전부 읽는 것과 같은 원리**다.

실무에서도 "집계 로직이 바뀌어 전체 재계산이 필요하다"면
그룹 이름을 바꿔 새로 붙이는 것이 가장 단순한 방법이다.
다만 `__consumer_offsets` 에 죽은 그룹이 쌓이므로 정리가 필요하다.

### 빈 파티션은 offset 이 `-` 로 남는다

```
p0 cur=- end=0 lag=-
```

`0` 이 아니라 `-` 다. **커밋한 적이 없다**는 뜻이다.
offset 은 소비할 때 비로소 생긴다.
