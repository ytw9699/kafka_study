## 배경

**이 프로젝트 전체의 하이라이트다.**

지금까지 "파티션 키가 순서를 보장한다"를 문서로 읽고 CLI 로 확인했다.
이제 **그것이 없을 때 무슨 일이 일어나는지**를 틀린 숫자로 본다.

## 목표

파티션 키를 흩뜨려 **워커가 계산한 잔액과 기대 잔액이 어긋나는 것**을 화면에서 목격한다.
그리고 키를 되돌리면 다시 일치하는 것을 확인한다.

## 선행 조건

- [KS-19](KS-19-worker-scale-out.md) 완료 (워커 여러 개 + 파티션 배정 화면)
- 워커 인스턴스 **3개** 기동
- 브라우저를 **먼저** 열어 SSE 연결 (기대 잔액은 SSE 로 받은 것만 계산한다)
- 잔액 테이블과 토픽을 비운 깨끗한 상태

## 상세 설계

### 왜 잔액이 틀어지는가 — 원인이 둘이다

**1. 순서 역전으로 거절 판정이 달라진다**

```
잔액 0
① 50,000 적립 (p0)   ② 8,000 사용 (p1)

워커A 가 ② 를 먼저 처리 → 잔액 0 → 부족, 거절
워커B 가 ① 을 처리     → 잔액 50,000

기대: 42,000    실제: 50,000
```

**2. lost update — 두 워커가 같은 행을 동시에 건드린다**

`USER_ID` 모드에서는 한 사용자를 한 워커만 다루므로 경합이 없었다
([KS-16](KS-16-balance-worker.md) 참조).

`RANDOM` 이면 두 워커가 **같은 `user_balance` 행**을 동시에 읽고 쓴다.
`findById` → 계산 → `save` 사이에 다른 워커가 끼어들면 한쪽 갱신이 사라진다.

> **파티션 키를 흩뜨리면 순서 보장뿐 아니라 동시성 안전도 함께 무너진다.**
> 둘이 같은 뿌리에서 나왔기 때문이다.

### burst 를 쓰는 이유

경쟁 상태는 **거래가 촘촘히 이어질 때** 잘 드러난다.
손으로 하나씩 넣으면 간격이 벌어져 워커가 순서대로 처리해버린다.

### 재현이 확률적이라는 점

순서 역전은 **타이밍에 의존**하므로 매번 같은 값이 나오지는 않는다.
한 번에 안 보이면 burst 를 반복하거나 건수를 늘린다.

**이것도 학습 포인트다** — 분산 시스템의 버그는 재현이 어렵고, 그래서 위험하다.

## 완료 조건 (DoD)

- [ ] `USER_ID` 대조군에서 차이가 0이다
- [ ] `RANDOM` 으로 바꾼 뒤 **차이가 0이 아닌 사용자가 나타난다**
- [ ] 피드에서 같은 `userId` 가 여러 파티션 색으로 흩어진 것이 보인다
- [ ] 키를 되돌리고 재구축하면 다시 일치한다
- [ ] 어긋난 원인(순서 역전 / lost update)을 설명할 수 있다
