## 배경

**이 프로젝트 전체의 하이라이트다.**

지금까지 "파티션 키가 순서를 보장한다"를 문서로 읽고 CLI 로 확인했다.
이제 **그것이 없을 때 무슨 일이 일어나는지**를 틀린 숫자로 본다.

## 목표

파티션 키를 흩뜨려 **워커가 계산한 잔액과 기대 잔액이 어긋나는 것**을 화면에서 목격한다.
그리고 키를 되돌리면 다시 일치하는 것을 확인한다.

## 선행 조건

- [KS-19](KS-19-worker-scale-out.md) 완료 (워커 여러 개 + 파티션 배정 화면)
- 워커 인스턴스 **3개** 기동
- 브라우저를 **먼저** 열어 SSE 연결 (기대 잔액은 SSE 로 받은 것만 계산한다)
- 잔액 테이블과 토픽을 비운 깨끗한 상태

## 작업 내용

- [x] 깨끗한 상태에서 시작 (토픽/잔액 초기화, 워커 3개, 브라우저 연결)
- [x] `USER_ID` 모드로 burst → **차이 0 확인** (대조군)
- [x] `POST /api/config/partition-key-mode` → `RANDOM`
- [x] burst 재투입
- [x] 같은 `userId` 가 여러 파티션에 흩어지는 것을 피드에서 확인
- [x] ★ **잔액과 기대 잔액이 어긋나는 것 확인**
- [x] 어긋난 정도와 방향 기록 (왜 그렇게 되는지 설명)
- [x] 키를 `USER_ID` 로 되돌리고 재구축 → **일치 복구**
- [x] 결과를 "배운 것"에 기록

## 상세 설계

### 왜 잔액이 틀어지는가 — 원인이 둘이다

**1. 순서 역전으로 거절 판정이 달라진다**

```
잔액 0
① 50,000 적립 (p0)   ② 8,000 사용 (p1)

워커A 가 ② 를 먼저 처리 → 잔액 0 → 부족, 거절
워커B 가 ① 을 처리     → 잔액 50,000

기대: 42,000    실제: 50,000
```

**2. lost update — 두 워커가 같은 행을 동시에 건드린다**

`USER_ID` 모드에서는 한 사용자를 한 워커만 다루므로 경합이 없었다
([KS-16](KS-16-balance-worker.md) 참조).

`RANDOM` 이면 두 워커가 **같은 `user_balance` 행**을 동시에 읽고 쓴다.
`findById` → 계산 → `save` 사이에 다른 워커가 끼어들면 한쪽 갱신이 사라진다.

> **파티션 키를 흩뜨리면 순서 보장뿐 아니라 동시성 안전도 함께 무너진다.**
> 둘이 같은 뿌리에서 나왔기 때문이다.

### burst 를 쓰는 이유

경쟁 상태는 **거래가 촘촘히 이어질 때** 잘 드러난다.
손으로 하나씩 넣으면 간격이 벌어져 워커가 순서대로 처리해버린다.

### 재현이 확률적이라는 점

순서 역전은 **타이밍에 의존**하므로 매번 같은 값이 나오지는 않는다.
한 번에 안 보이면 burst 를 반복하거나 건수를 늘린다.

**이것도 학습 포인트다** — 분산 시스템의 버그는 재현이 어렵고, 그래서 위험하다.

## 완료 조건 (DoD)

- [x] `USER_ID` 대조군에서 차이가 0이다
- [x] `RANDOM` 으로 바꾼 뒤 **차이가 0이 아닌 사용자가 나타난다**
- [x] 피드에서 같은 `userId` 가 여러 파티션 색으로 흩어진 것이 보인다
- [x] 키를 되돌리고 재구축하면 다시 일치한다
- [x] 어긋난 원인(순서 역전 / lost update)을 설명할 수 있다

## 실행 결과

조건: 워커 **3개**, 각각 파티션 1개씩. 5명 × 13건 = 65건 발행.

### 대조군 — `USER_ID`

```
byPartition: { "1": 26, "2": 39 }        ← 두 파티션에만 (해시 편중)

사용자    워커 잔액   기대 잔액   차이   거절(워커/기대)
user-1       710       710       0        2 / 2
user-2     2,590     2,590       0        1 / 1
user-3     1,900     1,900       0        4 / 4
user-4     8,880     8,880       0        0 / 0
user-5     4,140     4,140       0        3 / 3

적용 55  거절 10                              일치 ✓
```

**워커가 3개인데도 완벽히 일치한다.** 거절 건수까지 정확히 같다.

### 실험군 — `RANDOM` 😱

```
byPartition: { "0": 22, "1": 24, "2": 19 }   ← 세 파티션에 고르게 흩어졌다

사용자    워커 잔액   기대 잔액      차이     거절(워커/기대)
user-1    39,540     6,920     +32,620       9 / 4
user-2     1,550       560        +990       3 / 4
user-3    40,140       380     +39,760      10 / 6
user-4    35,750    15,660     +20,090       2 / 0
user-5       700     3,360      -2,660      11 / 5

적용 82  거절 35                        불일치 5명 😱
```

**5명 전부 틀렸다.** 피드에서 같은 `user-5` 의 거래가 p0·p1·p2 세 색으로 흩어진 것이 보였다.

### 복구 — `USER_ID` 로 되돌리고 재구축

```
사용자    워커 잔액   기대 잔액   차이   거절
user-1       340       340       0      2 / 2
user-2     6,190     6,190       0      0 / 0
user-3        20        20       0      2 / 2
user-4       360       360       0      1 / 1
user-5     1,090     1,090       0      2 / 2

적용 58  거절 7                          일치 ✓
```

**설정 한 줄로 깨지고, 한 줄로 복구된다.**

## 배운 것

### 파티션 키 하나가 전부였다

코드는 한 줄도 바뀌지 않았다. 워커 수도 같다. **바뀐 것은 발행 시 쓰는 키뿐이다.**

```kotlin
USER_ID -> userId
RANDOM  -> UUID.randomUUID().toString()
```

그런데 결과는 **전부 일치**에서 **전부 불일치**로 바뀌었다.
"파티션 키를 잘 잡아야 한다"가 왜 그렇게 강조되는지를 **틀린 숫자로** 배웠다.

### 틀어지는 방향이 대부분 `+` 인 것에 이유가 있다

`user-5` 만 `−2,660` 이고 나머지 넷은 모두 워커 잔액이 **더 크다.**

**사용(`SPEND`)이 적립보다 먼저 처리되면 잔액 부족으로 거절되기 때문**이다.
거절된 사용은 잔액을 깎지 않으므로 결과가 **커진다.**

거절 건수를 비교하면 명확하다.

| | 워커 | 기대 | |
|---|---|---|---|
| user-1 | 9 | 4 | 5건이 **잘못 거절**됨 |
| user-3 | 10 | 6 | 4건 |
| user-4 | 2 | 0 | 2건 |

**순서가 깨지면 거절 판정이 달라지고, 그것이 잔액 차이로 나타난다.**
이 도메인을 고른 이유가 정확히 이것이다 — 순서가 결과를 **결정적으로** 바꾼다.

> `user-5` 가 `−` 인 것은 lost update 쪽이 더 크게 작용했기 때문으로 보인다.
> 원인이 둘이므로 방향이 한쪽으로만 나오지는 않는다.

### 원인이 하나가 아니다

**1. 순서 역전** — 위에서 본 거절 판정 오류

**2. lost update** — 두 워커가 같은 `user_balance` 행을 동시에 읽고 쓴다

`USER_ID` 모드에서는 한 사용자를 한 워커만 다루므로 경합이 없었다
([KS-16](KS-16-balance-worker.md)에서 확인). `RANDOM` 이면 그 전제가 무너진다.

> **파티션 키를 흩뜨리면 순서 보장과 동시성 안전이 함께 무너진다.**
> 둘이 같은 뿌리에서 나왔기 때문이다. 이것이 이번 실험의 가장 중요한 발견이다.

### 대조군이 없었다면 아무것도 증명하지 못했다

`RANDOM` 결과만 보면 "워커가 3개라서 그런가?" 하고 헷갈렸을 것이다.

**같은 워커 3개로 `USER_ID` 에서는 완벽히 일치했다.**
변수가 파티션 키 하나로 고정되었기 때문에 인과를 말할 수 있다.

[KS-17](KS-17-balance-panel.md)에서 기대 잔액을 `occurredAt` 기준으로 계산하고
거절 규칙까지 맞춘 것이 여기서 값을 했다. 그렇게 하지 않았다면
**기대 잔액도 함께 틀려져** 비교 자체가 불가능했다.

### 발견한 UI 문제 — 모드 표시가 stale 해졌다

API 로 모드를 바꿨더니 화면은 여전히 `USER_ID` 를 표시했다 (기동 시 1회만 조회).

**"지금 정상 모드인가 실험 모드인가"를 오판하면 실험 해석 자체가 어긋난다.**
2초 폴링으로 고쳤다.

관찰 도구가 틀리면 실험이 무의미해진다 — 사소해 보이지만 이 프로젝트에서는 중요한 결함이었다.
