## 배경

이후 모든 단계의 재료가 되는 **이벤트를 만들어내는** 서비스. 데이터가 있어야 나머지가 성립한다.

## 목표

`POST /api/orders`로 주문을 저장하고 Kafka에 발행한다.
**같은 `userId`의 주문이 항상 같은 파티션에 들어가는 것**을 Kafka UI에서 확인한다.

## 작업 내용

- [ ] `Order` 엔티티 + Repository (`orderdb`) — `status` 컬럼 포함
- [ ] `POST /api/orders` — 저장 후 `ORDER_CREATED` 발행 (키 = `userId`)
- [ ] `POST /api/orders/{orderId}/cancel` — 상태 변경 후 `ORDER_CANCELED` 발행 (키 = `userId`)
- [ ] 이미 취소된 주문은 `409 Conflict` — 이벤트 중복 발행 방지
- [ ] 응답에 `partition` / `offset` 포함
- [ ] `GET /api/orders` — 원본 주문 목록 (현재 상태)
- [ ] `POST /api/orders/seed` — 여러 날짜에 걸친 시드 생성
- [ ] 같은 `userId`로 반복 주문해 파티션 고정 확인
- [ ] 생성·취소가 같은 파티션에 들어가는지 확인

## 상세 설계

### 파티션 키를 `userId`로 잡는 이유 — 취소 때문에 구체화된다

Kafka는 **파티션 내부에서만** 순서를 보장한다. 토픽 전체 순서는 보장하지 않는다.

같은 주문의 `CREATED`와 `CANCELED`가 **다른 파티션**에 들어가면, 컨슈머가 **취소를 생성보다 먼저 볼 수 있다.**
그러면 "존재하지 않는 주문의 취소"를 처리하게 되어 집계가 깨진다.

두 이벤트 모두 키를 `userId`로 두면 같은 파티션에 순서대로 들어가므로 이 문제가 발생하지 않는다.
**파티션 키 설계가 추상적 원칙이 아니라 구체적 필요임이 여기서 드러난다.**

### `orders` 테이블에 `canceled_at`을 두지 않는다

`status` 컬럼만 둔다 (`ACTIVE` / `CANCELED`). **의도적이다.**

이 테이블은 "DB는 지금을 알고, 이벤트 로그는 과거를 안다"를 보여주는 **대조군**이다.
3단계에서 stats의 일자별 매출과 이 테이블을 비교하면, DB만으로는 "언제 취소됐는지"를 알 수 없어
과거 시점 매출을 재현할 수 없다는 것이 숫자로 드러난다.

`canceled_at` 컬럼을 추가하고 싶어지는 충동이 바로 "이력을 DB에 넣기 시작하는" 지점이며, 그 끝이 Kafka다.

### 시드 API가 필요한 이유

일자별 매출 차트를 보려면 **여러 날짜에 걸친** 데이터가 필요하다.
하루에 손으로 만들면 전부 오늘 날짜라 차트가 막대 하나로 끝난다.

```json
POST /api/orders/seed
{ "days": 7, "count": 40, "cancelRatio": 0.2 }
```

3단계의 재료(30건 이상)를 만드는 용도이기도 하다. 프로덕션에는 없을 API다.

### 응답에 partition/offset을 넣는 이유

실무에서는 불필요하다. **학습 목적**이다 — 화면에서 "내 주문이 어느 파티션 몇 번 offset에 들어갔는지"를 바로 보기 위함이며, 2단계 피드의 뱃지로 이어진다.

`KafkaTemplate.send()`는 비동기(`CompletableFuture`)이므로 이 값을 응답에 담으려면 결과를 기다려야 한다.
학습용으로는 문제없지만, **응답 지연이 생긴다는 것은 인지한다.**

### 범위 밖

DB 저장과 Kafka 발행 사이의 원자성(트랜잭셔널 아웃박스)은 다루지 않는다.
저장은 됐는데 발행이 실패하는 경우가 있을 수 있다는 한계만 인지한다.
