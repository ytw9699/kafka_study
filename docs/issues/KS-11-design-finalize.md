## 배경

코드를 쓰기 전에 설계 전체를 비판적으로 재검토했다. **핵심 데모를 무너뜨리는 결함이 발견됐다.**
함께 저장소 선택을 재고하고, 범위를 확정하고, 작업을 실행 가능한 단위로 분해한다.

## 목표

설계를 최종 확정하고, 착수 가능한 티켓으로 분해한다.

## 발견한 문제와 해결

### 🔴 3단계 하이라이트가 두 번째 기동부터 깨진다

기존 문서에 "stats-service를 재기동하면 집계가 사라지고 Kafka 재생으로 다시 채워진다"고 적었으나 **사실이 아니었다.**

`auto-offset-reset: earliest`는 **해당 컨슈머 그룹의 커밋된 offset이 없을 때만** 동작한다.
한 번 소비하면 offset이 `__consumer_offsets`에 커밋되고, 재기동 시 거기서 이어서 읽는다.

| | Kafka offset | H2(인메모리) 집계 |
|---|---|---|
| 최초 기동 | 0부터 40건 | 40건 집계 ✅ |
| 재기동 | **40부터 이어서** | **0에서 시작** ❌ |

→ 집계가 영구히 틀린 상태가 되고, 3단계 데모를 두 번 볼 수 없다.

**해결**: 저장소를 영속(PostgreSQL)으로 바꾸고, 재생을 **명시적 API**로 분리했다. (아래 참조)

### 🔴 인메모리 + 자동 재생은 잘못된 감각을 남긴다

한때 "H2 인메모리 + 기동 시마다 `seekToBeginning`"을 검토했다. 그러나 **실무 컨슈머는 기동할 때마다 처음부터 읽지 않는다.** 커밋된 offset부터 이어서 읽는다. 데이터가 수백만 건이면 매 기동마다 전체 재생은 애초에 불가능하다.

인메모리로 가면 "Kafka 컨슈머는 켤 때마다 전부 다시 읽는 것"이라는 잘못된 인상이 남는다.

**해결**: 정상 동작과 재생을 분리한다.

| 상황 | 읽기 시작점 | 집계 테이블 |
|---|---|---|
| 최초 기동 (3단계) | offset 0 (`auto-offset-reset`) | 비어 있음 |
| 재기동 (평상시) | 커밋된 offset에서 이어서 | 유지 |
| `POST /api/stats/rebuild` | offset 0 (명시적 seek) | **비움** |
| `POST /api/stats/replay` | offset 0 (명시적 seek) | **유지** → 중복 😱 |

### 🔴 4단계 원래 설계는 애초에 동작하지 않았다

"CLI로 offset을 리셋해 중복 집계를 재현한다"였으나, `kafka-consumer-groups --reset-offsets`는 **활성 컨슈머가 있으면 거부된다.** 서비스를 내려야 하는데, 인메모리였다면 집계도 함께 날아가 중복이 발생하지 않는다.

**해결**: `POST /api/stats/replay`로 **서비스를 살려둔 채** 재생한다. 집계가 2배로 뛰는 순간을 화면에서 실시간으로 볼 수 있어 오히려 낫다.
CLI `--reset-offsets`는 4단계에서 **그 제약 자체를 확인하는 용도**로 별도로 다룬다.

### 🟠 H2 → PostgreSQL

H2 파일 모드도 이 규모에서는 굴러가지만, **4단계 upsert 문법이 다르다.**

| | 문법 |
|---|---|
| PostgreSQL | `INSERT ... ON CONFLICT ... DO UPDATE` |
| H2 | `MERGE INTO ... KEY(...)` |

가장 값진 학습 구간에서 H2 전용 문법을 익히면 실무 전이가 안 된다.
추가로 embedded 파일 모드는 한 JVM만 열 수 있어(file lock) 인스턴스 확장 실험이 막힌다.

**디버깅 표면을 줄이기 위해 Postgres는 0단계가 아니라 1단계에서 추가한다.**

### 🟠 5단계에서 화면이 깨진다 — 그리고 그것이 학습 포인트다

`feed-service` 인스턴스를 3개 띄우면 파티션이 나뉜다. 그런데 브라우저는 **하나의 인스턴스에만** SSE로 연결되므로, 주문 10건을 넣어도 화면에는 3건 정도만 보인다.

버그가 아니라 **레이어의 차이**다.

| | 구조 | 레이어 |
|---|---|---|
| Kafka 컨슈머 그룹 | 일을 **나눠 갖는다** | 서버 ↔ 서버 |
| SSE 브로드캐스트 | 모두에게 **뿌린다** | 서버 ↔ 브라우저 |

**해결**: 고치지 않고 **학습 포인트로 명시**했다. 여기서 Redis Pub/Sub이 왜 필요한지가 드러난다.

### 🟡 feed-service의 stateless 모순

"상태를 저장하지 않는다"고 해놓고 `GET /api/feed/recent`(메모리 버퍼)가 있었다.
게다가 5단계에서 인스턴스마다 버퍼가 달라 혼란을 키운다.

**해결**: 해당 API를 삭제했다. SSE 연결 이전 이벤트는 볼 수 없는 것이 정상이며, 과거를 읽는 것은 `stats-service`의 역할이다.

### 🟡 재생이 너무 빨라 안 보인다

수십 건 재생은 수백 밀리초에 끝나 차트가 채워지는 과정이 보이지 않는다.

**해결**: `app.replay.delay-ms` 설정 추가 (기본 0, 데모 시 50).

### 🟡 기타

- 6단계 DLT 대상을 `stats-service`로 명시
- `KafkaTemplate.send()`가 비동기라 응답에 partition/offset을 담으면 지연이 생긴다는 점 명시
- `replay` 구현 시 `KafkaConsumer`는 thread-safe하지 않으므로 `ConsumerSeekCallback`을 보관해 다음 poll에 적용한다는 구현 노트 추가
- **왜 서비스를 3개로 쪼개는가**의 근거 명문화 — 3단계(나중에 켜기)와 5단계(feed만 여러 개)가 프로세스 분리를 요구한다

## 범위 확정

- **Kubernetes 제외** — Kafka 학습이 쿠버 학습에 묻힌다. 7단계를 삭제했다
- **1차 목표는 0~4단계** — 여기까지가 "왜 Kafka인가"에 답하는 구간. 완료 시 `main` 머지 + `step-4` 태그
- 5~6단계는 2차 (실무 운영 지식)
- 5단계의 Redis Pub/Sub은 **구현하지 않는다.** 왜 필요한지 이해까지가 범위

## 배운 것

### 설계 문서는 "동작을 검증"해주지 않는다

`auto-offset-reset: earliest`와 "재기동하면 재생된다"는 문장은 **따로 보면 둘 다 맞다.**
하지만 함께 놓으면 틀린다. 문서가 그럴듯하게 읽힌다는 것과 실제로 동작한다는 것은 다르다.

특히 **Kafka는 상태가 브로커 쪽(`__consumer_offsets`)에 있어서**, 애플리케이션 코드만 보면 놓치기 쉽다. "이 설정이 언제 발동하는가"를 정확히 따져야 한다.

### 학습용 트릭과 실무 패턴을 구분해야 한다

인메모리 + 자동 재생은 그림이 선명해서 좋아 보였다. 하지만 실무에서 하지 않는 일이고, **잘못된 감각을 남긴다.**

"학습에 유리한 구성"이 "배워야 할 것을 왜곡하는 구성"이 될 수 있다.
정상 동작을 정상대로 두고, 학습 장치는 **명시적으로 분리**하는 편이 낫다.

### 버그처럼 보이는 것이 가장 좋은 학습 재료일 수 있다

5단계에서 화면이 깨지는 것은 처음엔 설계 결함으로 보였다. 그러나 이것이야말로
"Kafka가 푸는 문제와 풀지 않는 문제"의 경계를 몸으로 알게 하는 지점이다.

**고치지 않고 남겨두기로 한 것**이 이번 리뷰의 가장 좋은 결정이었다.
