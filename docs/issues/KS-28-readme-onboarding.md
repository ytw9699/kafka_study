## 검증 중 발견한 것

### 1. 처음 클론한 사람은 빌드부터 실패한다

`jvmToolchain(17)` 은 "JDK 17 을 쓴다"는 선언일 뿐이다. 로컬에 **같은 CPU 아키텍처의 JDK 17** 이 없으면 빌드가 실패한다.

```
Cannot find a Java installation on your machine matching this tasks requirements:
{languageVersion=17, ...} for MAC_OS on aarch64.
No locally installed toolchains match and toolchain download repositories have not been configured.
```

검증한 맥에는 JDK 17 이 x86_64 용 하나뿐이었다. README 의 "JDK 17 이상"만 보고 따라 하면 여기서 막힌다.

`settings.gradle.kts` 에 `foojay-resolver-convention` 플러그인을 추가해 **없으면 자동으로 내려받게** 했다.
첫 빌드에서 aarch64 용 JDK 17 이 내려받아지고 테스트까지 통과했다.

| 대안 | 탈락 이유 |
|---|---|
| README 에 "JDK 17 을 설치하라"고 적는다 | 아키텍처까지 맞아야 한다는 함정을 설명해야 하고, 처음 보는 사람에게 한 단계를 더 요구한다 |
| `jvmToolchain` 을 지우고 실행 JDK 를 쓴다 | 17 로 고정한 의도(재현성)가 사라진다 |

### 2. "키를 되돌리고 재구축하면 복구된다"는 틀렸다

RANDOM 실험 뒤 키를 `USER_ID` 로 되돌리고 워커 1개로 `rebuild` 했더니 **5명 중 2명이 계속 어긋났다.**

RANDOM 모드로 발행된 이벤트는 이미 여러 파티션에 흩어져 **로그에 그렇게 기록되었다.**
다시 읽어도 파티션 사이의 순서는 보장되지 않으므로 같은 문제가 재현된다.

[KS-20](KS-20-order-broken-experiment.md)의 복구 수치(65건)는 실험군과 별개로 새로 발행한 한 묶음이다.
초기화 후 다시 발행한 결과로 보는 것이 맞다. KS-20 에 정정을 남겼다.

### 3. `rebuild` 는 워커 1개일 때만 전체를 복원한다

`rebuild` 는 **요청을 받은 워커가 맡은 파티션만** 되감는다. 그런데 잔액은 **전체를 비운다.**
워커가 여러 개일 때 부르면 다른 워커 몫의 잔액은 비워진 채 다시 채워지지 않는다.
이미 [06 진행 기록](../planning/06-progress.md)에 한계로 적혀 있었지만, 실험 안내에서는 빠져 있었다. README 실험 C 에 명시했다.

### 4. `cli-lab.sh` 를 앱 토픽에 돌리면 워커가 멈춘다

CLI 실습 스크립트는 같은 `ledger-events` 토픽에 원시 JSON 을 넣는다. 앱이 읽으면 역직렬화에 실패해 무한 재시도에 빠진다([TS-2](../troubleshooting/TS-2-poison-pill.md)).
README 에는 토픽 생성 명령만 따로 안내하고, 스크립트는 앱 토픽에 실행하지 말라고 적었다.

## 배운 것

- **문서를 쓴 사람은 문서를 검증할 수 없다.** 이미 아는 사람은 빠진 단계를 머릿속으로 채운다.
  토픽 생성, JDK 아키텍처, 워커 수 조건 — 전부 "당연해서" 적지 않았던 것들이다. 깨끗한 환경에서 따라 해 보고서야 드러났다.
- **"복구된다"는 말에는 대상이 있어야 한다.** 키를 되돌리면 *앞으로의* 거래는 맞지만, *이미 기록된* 원장은 그대로다.
  로그가 원본이라는 말은 **잘못 기록된 것도 원본으로 남는다**는 뜻이다. 실무라면 잘못 발행된 구간을 식별해 보정 이벤트를 발행해야 한다.
- **선언과 보장은 다르다.** `jvmToolchain(17)` 은 17 을 쓰겠다는 선언이지 17 을 구해 오겠다는 보장이 아니다.
  주석에 "toolchain 이 17 을 찾아 쓴다"고 적어 두고 그것이 "없으면 실패한다"는 뜻이라는 것을 놓쳤다.
