## 배경

[KS-1](KS-1-project-setup-docs.md)에서 작성한 설계서에 구조도가 ASCII 아트 하나뿐이었고, 그마저도 **백엔드-Kafka 구간만** 그려져 있었다.

빠진 것:
- **프론트엔드 내부 구조** — 컴포넌트, 스토어, SSE 연결 관리가 문서에 없음
- **인프라 계층** — 컨테이너 구성, 네트워크, 리스너 분리가 없음
- **시간 축 흐름** — "3단계에서 뒤늦게 합류한 컨슈머가 과거를 읽는다"는 이 프로젝트의 핵심인데, 정적 구조도로는 표현이 안 됨

## 목표

프론트엔드부터 인프라까지 **전 계층**을 문서 하나로 파악할 수 있게 한다.

## 상세 설계

### 왜 Mermaid인가

ASCII 아트는 수정할 때마다 정렬이 깨지고, **시퀀스(시간 축)를 표현할 수 없다.**
Mermaid는 GitHub 마크다운에서 그대로 렌더되므로 별도 이미지 파일 관리가 필요 없고, 다이어그램이 코드처럼 diff로 리뷰된다.

### 문서에 새로 명시한 판단들

기존에 대화로만 있고 문서에 없던 것들을 명문화했다.

**Spring 서비스는 컨테이너에 넣지 않는다**
3~5단계에서 서비스를 껐다 켜고 인스턴스를 늘리는 실험을 반복한다. 매번 이미지를 빌드하면 학습 리듬이 끊긴다.

**Kafka 로그는 볼륨에 보존, H2는 인메모리**
이 비대칭이 의도적이다. `docker compose down` 후에도 토픽이 남아야 3단계가 성립한다. 반대로 H2는 비워져야 "로그로부터 상태를 재구축한다"가 매번 체험된다.

**`OrderFeed`에 partition/offset 뱃지를 단다**
실무에선 불필요하지만, 파티션 개념을 화면에서 직접 체감하게 하는 장치. 같은 `userId`로 반복 주문하면 partition 번호가 고정되는 것이 보인다.

**SSE의 한계를 문서에 명시**
`EventSource`는 자동 재연결되지만 **재연결 중 놓친 이벤트는 복구되지 않는다.** 이것이 "Kafka는 SSE 연결 끊김을 해결하는 도구가 아니다"의 실물이다. Kafka의 offset은 컨슈머 서비스가 어디까지 읽었는지를 기억할 뿐, 브라우저가 어디까지 받았는지는 모른다.

## 배운 것

### 정적 구조도만으로는 이 프로젝트의 핵심이 안 보인다

"두 컨슈머가 같은 토픽을 구독한다"는 박스와 화살표로 그려진다. 하지만 이 프로젝트의 진짜 주장은
**"stats-service가 나중에 켜져도 과거를 전부 읽는다"** 이고, 이건 **시간 축이 없으면 표현이 불가능하다.**

구조도는 "무엇이 무엇과 연결되는가"를, 시퀀스 다이어그램은 "언제 무슨 일이 벌어지는가"를 답한다. Kafka처럼 **시간(로그의 순서와 위치)이 본질인 기술**은 후자가 없으면 설명이 안 된다.

### 문서를 그리다 보면 미정 사항이 드러난다

프론트 구조를 그리려 하니 CORS를 어떻게 처리할지, SSE 연결을 어디서 해제할지가 정해져 있지 않다는 게 드러났다. 코드를 쓰기 전에 그림을 그리는 것의 실익.
