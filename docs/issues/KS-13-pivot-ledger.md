## 배경

[KS-12](KS-12-scenario-cancellation.md)에서 주문 취소 이벤트를 넣어 "왜 Kafka인가"를 강화했다고 판단했으나, **그것도 무너졌다.**

> "취소/일자별 매출도 결국 `order_events` append-only 테이블 하나면 되는 것 아닌가?"

맞다. 이 SQL 한 줄이면 끝난다.

```sql
SELECT DATE(occurred_at),
       SUM(CASE WHEN event_type='CREATED' THEN amount ELSE -amount END)
FROM order_events GROUP BY 1;
```

즉 KS-12의 시나리오가 증명한 것은 **"이력을 저장해야 한다"** 였지 **"Kafka여야 한다"** 가 아니었다.
"이력 테이블을 만드는 순간 그게 Kafka다"라고 썼는데, 정확히는 **이벤트 소싱**이지 Kafka가 아니다.

### 더 근본적인 문제 — 방향이 거꾸로였다

**도구를 먼저 정해놓고 거기에 맞는 요구사항을 역설계하고 있었다.**
실무는 반대다 — 요구사항이 먼저 있고 도구를 고른다.
그래서 시나리오를 아무리 다듬어도 계속 무너졌다.

## 목표

1. Kafka의 메커니즘을 **제대로 써야만 하는** 도메인으로 전환한다
2. "왜 Kafka인가"의 주장 강도를 **과장 없는 수준**으로 조정한다
3. 토이 프로젝트가 증명할 수 있는 것과 없는 것을 명시한다

## 새 도메인 — 포인트 지갑 원장(Ledger)

### 왜 이 도메인인가

**순서가 결과를 크게 바꾸는 도메인**이어야 순서 보장이 진짜 요구사항이 된다.

```
잔액 1,000원
① 5,000원 적립   ② 3,000원 사용

①→② :  1,000 → 6,000 → 3,000   ✅
②→① :  1,000 → [잔액부족, 거절] → 6,000   ❌ 결과가 다르다
```

**순서가 뒤바뀌면 잔액이 틀리고, 그것이 화면에 숫자로 보인다.**
매출 집계처럼 "틀려도 티가 안 나는" 도메인과 확실히 다르다.

### 요구사항 6개

| # | 요구사항 | Kafka 메커니즘 |
|---|---|---|
| 1 | 같은 사용자의 거래는 **순서대로** | 파티션 키 |
| 2 | 워커를 늘려 **병렬 처리** | 컨슈머 그룹 |
| 3 | **워커가 죽어도** 자동 인수 | 리밸런싱 |
| 4 | 전체를 다시 읽어 **원장 재구축** | offset seek |
| 5 | **이상거래 탐지 서비스가 나중에 합류** | 그룹별 독립 offset |
| 6 | **실패해도 원장이 틀어지지 않음** | retry 전략, DLT |

**1번과 6번이 서로 부딪친다.** 순서를 지키려면 실패 지점에서 멈춰야 하고, 멈추면 처리량이 죽는다.
이 트레이드오프가 Kafka 실무의 진짜 어려움이며, 기존 도메인으로는 나올 수 없던 학습이다.

### 다른 도구와의 비교

| | 1+2+3 | 4 (재생) | 5 (독립 소비자) |
|---|---|---|---|
| DB 테이블 큐 | △ 직접 만들면 가능 | ✅ | △ 커서 직접 관리 |
| RabbitMQ | ❌ | ❌ | ✅ |
| Redis Streams | ❌ 파티션 개념 없음 | ✅ | ✅ |
| SQS FIFO | ✅ MessageGroupId | ❌ | ❌ |
| **Kafka** | ✅ | ✅ | ✅ |

**셋을 한 번에 제공하는 것은 Kafka뿐이다.** SQS FIFO는 반쪽(1~3), Redis Streams도 반쪽(4~5)이다.

## 주장 강도 조정

### 이전 (과장)

> ~~"Kafka가 아니면 구조적으로 불가능하다"~~

### 이후 (과장 없이)

> **"DB를 쓰면 이 기능들을 직접 만들어야 하는데, Kafka는 메시징 시스템 자체에서 제공한다."**

아래를 전부 만들면 DB로도 된다.

```
이벤트 테이블 + userId별 라우팅 + 워커 멤버십 + 하트비트
+ lease + 파티션 소유권 + 리밸런싱 + 컨슈머 offset + 재시도
```

**어려운 것은 만드는 일이 아니라 장애 상황에서 정확성을 지키는 일이다.**
대표적으로 split-brain — GC로 멈춘 워커의 lease가 만료되고 다른 워커가 인수했는데,
원래 워커가 깨어나 쓰기를 하면 이중 적용된다. 막으려면 **fencing token**이 필요하고,
Kafka는 이것을 컨슈머 그룹의 **generation id**로 해결한다.

**우연히 그 모양인 게 아니라, 이 문제를 풀면 그 구조가 될 수밖에 없다.**

→ `docs/planning/05-why-not-diy.md` 신설. 대응표와 함께 정리.

### 실무 판단 기준

| | |
|---|---|
| ❌ | "DB로는 안 되니까 Kafka" |
| ✅ | "검증된 구현이 있는데 분산 조정을 직접 만들 이유가 없으니까 Kafka" |
| ✅ | "규모가 작고 정확성 요구가 낮으면 DB 큐로도 충분하다" |

## 솔직한 한계 명시

Kafka의 필요성은 **규모**(초당 수만 건)와 **조직**(여러 팀의 독립 배포)에서 나오는데,
**둘 다 혼자 노트북에서 재현할 수 없다.**

| | |
|---|---|
| ❌ 증명 불가 | "Kafka가 필요하다" |
| ✅ 실제로 하는 것 | Kafka의 동작 방식을 직접 익힘 |
| ✅ 부수 효과 | **Kafka가 왜 그런 모양인지 이해**, 언제 필요 없는지 판단 |

**단 하나, "순서가 안 지켜지면 잔액이 틀린다"는 소규모에서도 즉시 아프다.**
워커를 둘로 늘리는 순간 깨진다. 이것을 4단계에서 직접 본다.

## 학습 방식 선택

두 가지를 놓고 (b)를 택했다.

| | 방식 | 판단 |
|---|---|---|
| (a) | DB 큐를 직접 만들어보다 막히는 고통을 겪은 뒤 Kafka로 전환 | "왜"가 확실히 남지만 시간 비용이 큼 |
| **(b)** | **Kafka부터 빠르게 익히고, DIY 비용은 문서로 정리** | **채택** |

**다만 (a)의 핵심 가치는 저비용으로 챙긴다.**
`app.partition-key-mode`를 `RANDOM`으로 바꾸면 **잔액이 틀어지는 것**을 볼 수 있다.
설정 한 줄이라 비용이 거의 없는데 "순서가 안 지켜지면 이렇게 된다"를 숫자로 직접 확인한다.

## 새 구조

```
ledger-api (:8081)          balance-worker (:8082…) × N ★     fraud-service (:8083)
Producer + SSE 게이트웨이     순서·병렬·리밸런싱을 실험하는 곳            나중에 합류
     │                              ↑                                ↑
     └──→ Kafka: ledger-events (파티션 3, 키=userId) ──────────────────┘
```

| 컨슈머 그룹 | 인스턴스 | 역할 |
|---|---|---|
| `gateway-group` | 1개 | 전체 파티션 구독 → SSE 중계 |
| `balance-group` | **N개 ★** | 잔액 계산 |
| `fraud-group` | 1개 | 나중에 합류, 전체 재생 |

### SSE 게이트웨이를 ledger-api에 둔 이유

`balance-worker`가 여러 인스턴스이므로 거기에 SSE를 붙이면 브라우저가 하나에만 연결되어 **일부만 보인다.**
단일 인스턴스인 `ledger-api`가 **별도 그룹**으로 전체를 구독해 중계하면 해결된다.

> 이전 기획에서 이 문제를 "5단계 학습 포인트"라며 남겨뒀었다.
> 새 도메인에서는 **설계로 해결**한다. 작업 분배와 브로드캐스트는 다른 레이어이므로 분리하는 것이 맞다.
> 대신 그 개념 자체는 0단계 CLI 실습(같은 그룹 vs 다른 그룹)에서 다룬다.

### `ledger-api`는 DB를 갖지 않는다

**Kafka가 원장의 원본(source of truth)이다.** 요청을 DB에 저장하면
"로그가 원본이고 나머지는 파생 상태"라는 전제가 흐려진다.

## 단계 재편

| 단계 | 내용 |
|---|---|
| 0 | Kafka 인프라 + CLI (같은 그룹 vs 다른 그룹 확인 추가) |
| 1 | 뼈대 + PostgreSQL |
| 2 | `ledger-api` 발행 + 실시간 피드 |
| 3 | `balance-worker` 1개 — 잔액 계산 + **기대 잔액 병행 표시** |
| **4 ★** | **워커 여러 개 — 순서 깨짐 확인 → 파티션 키로 해결 → 리밸런싱** |
| **5 ★** | 원장 재구축 & 멱등성 |
| 6 | `fraud-service` 합류 |
| 7 | 실패 처리 — blocking retry, 파티션 블로킹, DLT |

**1차 목표는 5단계까지.** 4단계가 목적지다.

## 배운 것

### 도구를 정해놓고 요구사항을 역설계하면 계속 무너진다

세 번의 시나리오(단순 매출 → 취소/일자별 매출 → 원장)를 거쳤다.
앞의 둘이 무너진 이유는 같다 — **"Kafka가 필요해 보이는" 요구사항을 만들려 했기 때문**이다.

세 번째가 버틴 이유는 도메인 자체가 **순서에 의존**하기 때문이다.
억지로 붙인 요구사항이 아니라 일 자체의 성질이라 무너지지 않는다.

**시나리오를 고르는 기준은 "Kafka를 쓸 수 있는가"가 아니라 "이 일의 핵심이 무엇인가"다.**

### 솔직하게 인정할수록 주장이 강해진다

"불가능"을 포기하고 "직접 만들 것이냐 제공받을 것이냐"로 바꾸니 오히려 반박이 어려워졌다.
그리고 **"언제 Kafka가 필요 없는지"** 를 함께 말할 수 있게 되면서 실무 판단으로서의 가치가 생겼다.

### 토이 프로젝트의 한계를 인정하는 것이 출발점이다

Kafka의 필요성은 규모와 조직에서 나오고, 그건 혼자 만들 수 없다.
이걸 인정하지 않으면 계속 억지 시나리오를 만들게 된다.

대신 **"필요성"이 아니라 "메커니즘"과 "왜 그런 모양인지"** 를 목표로 두면 토이 프로젝트로도 충분히 도달할 수 있다.
