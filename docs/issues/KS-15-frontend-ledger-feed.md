## 배경

프론트는 **Kafka의 흐름을 눈으로 보는 창**이다. 화면은 최소로 유지하고,
프론트 작업이 Kafka 학습을 압도하지 않게 한다.

## 목표

거래를 발생시키고, 그것이 어느 파티션으로 갔는지 화면에서 확인한다.

## 상세 설계

### userId 프리셋이 중요한 이유

**같은 userId로 연속 거래를 빠르게 만드는 것**이 이 프로젝트의 핵심 조작이다.
매번 입력하게 하면 4단계 실험이 번거로워진다. `user-1` ~ `user-5` 버튼을 둔다.

### partition 뱃지

파티션 번호마다 색을 다르게 준다.
같은 userId로 거래하면 **같은 색만 계속 쌓이는 것**이 한눈에 보인다.
4단계에서 `RANDOM` 모드로 바꾸면 **색이 섞이기 시작한다.**

### SSE 생명주기

`onMounted` 연결, `onUnmounted` `close()`. **해제를 빠뜨리면 연결이 누적된다.**

`EventSource`는 끊기면 브라우저가 자동 재연결하지만 **재연결 중 놓친 이벤트는 복구되지 않는다.**
Kafka의 offset은 **컨슈머 서비스가** 어디까지 읽었는지를 기억할 뿐, 브라우저가 어디까지 받았는지는 모른다.

### CORS

Vite dev 프록시로 처리한다. 백엔드에 CORS 설정을 흩뿌리지 않는다.

| 프론트 경로 | 대상 |
|---|---|
| `/api/tx`, `/api/stream`, `/api/config` | `localhost:8081` |
| `/api/balance`, `/api/workers` | `localhost:8082` |
| `/api/fraud` | `localhost:8083` |

## 검증 결과

### `USER_ID` 모드 — 같은 사용자는 같은 색

`user-1` 로 5건 적립:

```
p2  #63  user-1  +5,000
p2  #62  user-1  +5,000
p2  #61  user-1  +5,000
p2  #60  user-1  +5,000
p2  #59  user-1  +5,000
```

**전부 보라색 p2 로 고정.**

### `RANDOM` 모드 — 색이 섞인다

같은 `user-1` 로 5건 더:

```
p0  #15  user-1  +5,000     ← 주황
p2  #64  user-1  +5,000     ← 보라
p0  #14  user-1  +5,000
p0  #13  user-1  +5,000
p1  #41  user-1  +5,000     ← 파랑
```

패널이 빨간 경고로 바뀌고 `key` 가 UUID(`814966f7-563f-...`)로 표시된다.

**4단계 실험 A 의 조건이 화면에서 눈으로 확인된다.**

## 배운 것

### 색상 뱃지가 설명 열 줄보다 낫다

"같은 키는 같은 파티션으로 간다"를 글로 읽는 것과,
**같은 색만 계속 쌓이다가 갑자기 섞이기 시작하는 것을 보는 것**은 다르다.

파티션 번호를 숫자로만 표시했다면 스크롤하며 비교해야 하는데,
색을 입히니 **한눈에 패턴이 보인다.** 4단계에서 이 화면이 그대로 진단 도구가 된다.

### SSE 프록시는 버퍼링을 꺼야 한다

Vite dev 프록시가 응답을 버퍼링하면 이벤트가 뭉쳐서 늦게 도착한다.

```ts
proxyRes.headers['cache-control'] = 'no-cache'
proxyRes.headers['x-accel-buffering'] = 'no'
```

이번 환경에서는 설정 없이도 동작했지만, nginx 등을 앞에 두면 반드시 필요하다.
`x-accel-buffering: no` 는 nginx 에게 이 응답을 버퍼링하지 말라고 알리는 관례적 헤더다.

### 검증할 때 화면 갱신을 기다려야 한다

처음 스크린샷을 찍었을 때 피드가 비어 있어 SSE 가 안 되는 줄 알았다.
프록시와 직접 연결을 `curl` 로 각각 확인해보니 **둘 다 정상**이었고,
단지 **스크린샷이 이벤트 도착보다 빨랐던 것**이었다.

비동기 시스템을 검증할 때는 "안 보인다"와 "아직 안 왔다"를 구분해야 한다.
이 프로젝트 전체가 비동기이므로 앞으로도 반복될 함정이다.

### `busy` 가드가 빠른 연속 클릭을 삼킨다

발행 시 `send().get()` 으로 ack 을 기다리므로 한 건에 수십 ms 가 걸린다.
그 사이 클릭은 `busy` 가드에 막혀 무시된다.

4단계에서 **촘촘한 연속 거래**가 필요하므로 손 클릭에 의존하면 안 되고,
`POST /api/tx/burst` 를 써야 한다. 버튼을 미리 만들어둔 이유다.

### 기대 잔액을 지금 만들어두는 것이 맞다

`stores/ledger.ts` 의 `expectedBalances` 는 아직 화면에 쓰이지 않는다.
3단계에서 워커가 계산한 실제 잔액과 나란히 놓기 위한 준비물이다.

**4단계에서 둘이 어긋나는 순간이 이 프로젝트의 결정적 장면**이므로,
비교 대상을 프론트가 독립적으로 갖고 있어야 한다.
워커의 값만 보면 "틀렸다"는 것을 알 방법이 없다.
