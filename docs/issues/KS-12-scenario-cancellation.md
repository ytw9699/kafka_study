## 배경

기존 시나리오에 대해 정당한 반문이 나왔다.

> "통계 서비스가 과거 주문을 읽어 집계를 구축한다 — 이걸 Kafka만 할 수 있나?
> 그냥 DB에 넣어두고 통계 페이지에서 조회하면 되는 것 아닌가?"

**맞는 지적이었다.** 기존 시나리오는 `ORDER_CREATED` 하나뿐이었고, 집계는 단순 매출 합계였다.
그렇다면 이 한 줄이면 끝난다.

```sql
SELECT product_name, SUM(total_price) FROM orders GROUP BY product_name;
```

버그를 고치면 다시 조회하면 된다. **Kafka가 필요 없다.**

즉 이 프로젝트는 "왜 Kafka인가"를 주장하면서, 정작 **그 주장을 스스로 반증하는 시나리오**를 쓰고 있었다.

## 목표

DB 조회로는 **구조적으로 불가능한** 요구사항을 시나리오에 넣어, "왜 Kafka인가"에 코드로 답할 수 있게 한다.

## 해결 — 주문 취소와 일자별 매출

### 이벤트를 두 종류로

| 이벤트 | 시점 |
|---|---|
| `ORDER_CREATED` | 주문 생성 |
| `ORDER_CANCELED` | 주문 취소 (며칠 뒤일 수 있다) |

### 통계 정의를 바꾼다

> **일자별 매출 = 그날 생성된 주문 금액 합 − 그날 취소된 주문 금액 합**
>
> 3월 5일에 생성되고 4월 2일에 취소된 주문은 **3월 5일 매출에 그대로 남고 4월 2일에 차감된다.**

### 왜 이것이 DB로 불가능한가

`orders` 테이블은 **현재 상태**만 담는다.

| order_id | total_price | status | created_at |
|---|---|---|---|
| ORD-1 | 178,000 | `CANCELED` | 2026-03-05 |

```sql
SELECT DATE(created_at), SUM(total_price)
FROM orders WHERE status = 'ACTIVE' GROUP BY 1;
```

→ **3월 5일 매출에서 178,000원이 사라진다.** 4월에 취소했는데 3월 매출이 소급해서 줄었다. **틀렸다.**

주문이 취소되면 `status`가 `CANCELED`로 **덮어써지고 언제 취소됐는지가 사라진다.**
**DB는 지금을 알지만 과거를 모른다.**

### "`canceled_at` 컬럼을 추가하면?"

된다. 그런데 그 다음에 취소 철회, 재취소, 수량 변경 추적 요구가 오면 컬럼으로는 감당이 안 되고,
결국 **주문 변경 이력 테이블**을 만들게 된다.

**그리고 그 순간, 만든 것이 바로 Kafka다.**
순서대로 쌓이고, 덮어쓰지 않고, 여러 소비자가 각자의 위치에서 읽는 변경 로그.

## 부수 효과 — 설계가 여러 곳에서 단단해졌다

취소 이벤트 하나를 넣었을 뿐인데 기존에 추상적이던 것들이 구체화됐다.

### 1. 파티션 키 설계에 진짜 이유가 생겼다

기존에는 "같은 사용자의 순서 보장"이라는 다소 막연한 근거였다. 이제는 명확하다.

같은 주문의 `CREATED`와 `CANCELED`가 **다른 파티션**에 들어가면 컨슈머가 **취소를 생성보다 먼저 볼 수 있고**, 그러면 집계가 깨진다.
두 이벤트 모두 키를 `userId`로 두어야 하는 **구체적 필요**가 생겼다.

### 2. 멱등 키가 `orderId`에서 `eventId`로 바뀌었다

같은 `orderId`로 이벤트가 **두 개** 발생한다.
`orderId`를 멱등 키로 쓰면 **취소 이벤트가 "이미 처리한 주문"으로 판정되어 버려진다.**

4단계의 `processed_event` 테이블 PK를 `event_id`로 정정했다.
이것 자체가 좋은 함정이므로, 로드맵에 "직접 `order_id`로 만들어보고 취소가 반영되지 않는 것을 확인한 뒤 고치라"고 적었다.

### 3. `eventType` 필드가 쓸모를 갖게 됐다

값이 하나뿐이라 YAGNI였는데, 이제 실제로 분기에 쓰인다.

### 4. `GET /api/orders`에 목적이 생겼다

기존에는 "기준선" 정도였다. 이제는 **논증의 대조군**이다.
DB 화면과 통계 화면의 숫자가 다른 것이 이 프로젝트의 결론이 된다.

## 상세 설계

### 시드 API가 필요한 이유

일자별 매출 차트를 보려면 **여러 날짜에 걸친** 데이터가 필요하다.
하루에 손으로 만들면 전부 오늘 날짜라 차트가 막대 하나로 끝난다.

```json
POST /api/orders/seed
{ "days": 7, "count": 40, "cancelRatio": 0.2 }
```

### 이벤트는 자기 완결적이어야 한다

취소 이벤트에도 `productName`, `totalPrice`를 **중복해서 담는다.**
컨슈머가 "그 주문이 얼마짜리였는지"를 알려고 원본 DB를 조회해야 한다면 **서비스 경계가 무너진다.**

### `orders` 테이블에 `canceled_at`을 두지 않는다

의도적이다. 이 테이블은 **대조군**이다.
`canceled_at`을 추가하는 순간 논증이 흐려진다.

## 배운 것

### 프로젝트의 주장은 시나리오가 증명해야 한다

문서에 "Kafka는 로그이므로 재생할 수 있다"고 아무리 써도, **시나리오가 DB로도 되는 것이면 아무것도 증명하지 못한다.**

기존 시나리오는 Kafka를 쓸 **수는** 있는 시나리오였지, Kafka를 써야만 **하는** 시나리오가 아니었다.
이 차이를 스스로 알아채기 어려웠다 — 문서가 그럴듯하게 읽혔기 때문이다.

### 정직한 경계를 긋는 것이 주장을 강하게 만든다

"단일 서비스 + 현재 상태만 필요 + 소규모라면 DB 조회로 충분하다. Kafka는 오버스펙"이라고 먼저 인정하고 나니,
**그렇지 않은 조건**이 무엇인지가 오히려 선명해졌다.

모든 상황에 Kafka가 낫다고 주장하는 것보다, **언제 필요 없는지를 아는 것**이 실무 판단력이다.

### 요구사항 하나가 설계 전반을 정합적으로 만든다

취소 이벤트 하나를 넣었더니 파티션 키, 멱등 키, `eventType`, `GET /api/orders`가 전부 제자리를 찾았다.
**설계가 어색하게 느껴진다면 요구사항이 부족한 것일 수 있다.**
