# 05. DB로 직접 만들면 어디까지 가야 하는가

[← README](../../README.md) · [문서 목록](../README.md)

> **이 문서 한눈에**
> - Kafka 없이 **DB 테이블로 같은 기능을 만들면** 무엇을 직접 짜야 하는가
> - 진짜 어려운 것은 만드는 게 아니라 **장애 상황의 정확성** — split-brain 과 fencing token
> - DB로 충분한 경우와 Kafka가 필요한 경우의 판단 기준


이 프로젝트는 **"Kafka가 아니면 불가능하다"고 주장하지 않는다.**
DB로도 만들 수 있다. 다만 **무엇을 만들어야 하는지**를 정확히 알고 선택하자는 것이다.

> 구현하지 않는다. **설계 수준으로만** 정리한다.
> 실제로 만들어보는 것이 학습에는 더 좋지만, 시간 비용이 커서 [기획서 10번](01-planning.md)에서 범위 밖으로 두었다.

---

## 1. 요구사항을 DB로 만들려면

[기획서 5번](01-planning.md)의 요구사항 1~3을 DB 테이블 큐로 만든다고 하자.

> 같은 사용자의 거래는 순서대로, 여러 사용자는 동시에, 워커가 죽으면 자동 인수.

### 시도 1 — `SKIP LOCKED`

```sql
SELECT * FROM ledger_events
WHERE processed = false
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

워커들이 잠기지 않은 행을 하나씩 집어간다. 병렬은 된다.

**문제**: 워커A가 user-42의 ①을 집고, 워커B가 동시에 user-42의 ②를 집는다.
→ **같은 사용자의 거래가 동시에 처리된다. 순서가 깨진다.**

### 시도 2 — 워커 1개

순서는 지켜진다. **병렬이 없다.** 요구사항 2번 탈락.

### 시도 3 — 사용자별로 워커 고정

```sql
WHERE hash(user_id) % :워커수 = :내번호
```

같은 사용자는 항상 같은 워커에게 간다. 순서 ✅, 병렬 ✅.

**문제들**:
- 워커 수(`:워커수`)를 누가 관리하는가? 워커가 3개인지 5개인지 각 워커가 어떻게 아는가
- 워커가 죽으면 그 워커의 몫은 누가 처리하는가
- 죽은 것을 **어떻게 아는가** (하트비트)
- 워커를 추가하면 배정이 바뀌는데, 그 순간 **처리 중이던 것들**은 어떻게 되는가

→ **멤버십 관리 + 하트비트 + 재분배**를 만들어야 한다.

### 시도 4 — lease 방식

각 워커가 사용자(또는 샤드)에 대해 **기한이 있는 소유권**을 획득한다.

```sql
UPDATE shard_lease
SET owner = :워커, expires_at = now() + interval '10 seconds'
WHERE shard_id = :샤드 AND (owner IS NULL OR expires_at < now());
```

워커가 죽으면 lease가 만료되고 다른 워커가 가져간다. 그럴듯하다.

**그런데 여기서 진짜 함정이 나온다.**

## 2. 진짜 어려운 것 — split-brain

```
워커A: shard-3 lease 획득 (10초)
       거래 처리 시작
       ↓ GC로 8초 멈춤 (또는 네트워크 지연, 디스크 I/O 대기)
       lease 만료 (워커A는 모른다)
워커B: shard-3 lease 인수 → 거래 처리 → 잔액 갱신
워커A: 깨어남. 자기 lease가 아직 유효한 줄 알고 → 잔액 갱신   ← 이중 적용
```

**두 워커가 동시에 같은 샤드의 소유자라고 믿는 상태.** 원장에서는 곧 돈이 틀리는 것이다.

### 이걸 막으려면 — fencing token

lease를 줄 때마다 **단조 증가하는 번호**를 함께 발급한다.

```
워커A: lease 획득 → token = 33
       (멈춤)
워커B: lease 인수 → token = 34, 잔액 갱신 (token 34 기록)
워커A: 깨어나 잔액 갱신 시도 (token 33)
저장소: "이미 34를 봤다. 33은 거부"   ← 차단 ✅
```

**중요**: 검사를 **저장소 쪽에서** 해야 한다. 워커가 스스로 "내 lease 유효한가?"를 확인하는 것으로는 못 막는다. 확인한 직후에 멈출 수 있기 때문이다.

즉 잔액 테이블에 `last_token` 컬럼을 두고 모든 쓰기에 조건을 걸어야 한다.

### Kafka는 이걸 어떻게 하는가

컨슈머 그룹의 **generation id**가 정확히 fencing token이다.
리밸런싱이 일어날 때마다 세대 번호가 올라가고, **옛 세대의 offset 커밋은 브로커가 거부한다.**

> Kafka가 우연히 그렇게 생긴 것이 아니다.
> **이 문제를 정확히 풀면 그 구조가 될 수밖에 없다.**

---

## 3. 남은 문제들

fencing까지 해결해도 끝이 아니다.

### offset 커밋과 상태 갱신의 원자성

```
1. 잔액 테이블 갱신
2. "여기까지 처리했음" 기록
```

둘 사이에서 워커가 죽으면? 1만 되고 2가 안 되면 **재처리 시 중복 적용**된다.
→ 같은 트랜잭션에 넣거나, **멱등하게** 만들어야 한다.

> Kafka에서도 동일한 문제다. 그래서 5단계에서 멱등성을 다룬다.
> DB로 만들든 Kafka를 쓰든 **이 문제만은 사라지지 않는다** — at-least-once 의 성질이기 때문이다.

### 재분배 중 진행 중인 작업

소유권이 넘어가는 순간, 이전 소유자가 처리 중이던 것은 어떻게 되는가.
→ 경계를 명확히 정의하고, 넘기기 전에 정리(drain)하는 절차가 필요하다.

> Kafka는 `ConsumerRebalanceListener.onPartitionsRevoked`로 이 지점을 제공한다.

### 폴링 지연과 부하

`WHERE processed = false`를 계속 조회해야 한다.
→ 짧게 폴링하면 DB 부하, 길게 폴링하면 지연.

> Kafka는 long-poll로 이 트레이드오프를 없앤다.

### 여러 소비자가 각자 다른 속도로 읽기

잔액 워커와 이상거래 탐지 서비스가 같은 이벤트를 각자 소비해야 한다.
→ `processed` 플래그로는 안 된다. **소비자마다 커서 테이블**이 필요하다.

> Kafka는 컨슈머 그룹별 offset으로 기본 제공한다.

### 테이블 비대와 정리

처리 완료된 행을 지우면 재생을 못 하고, 안 지우면 테이블이 커져 인덱스가 무거워진다.

> Kafka는 retention 정책과 순차 로그 구조로 이 문제를 다르게 푼다.

## 4. 대응표

| DB로 직접 만들어야 하는 것 | Kafka가 제공하는 것 |
|---|---|
| 이벤트 테이블 (append-only) | 토픽 로그 |
| `userId`별 라우팅 / 샤딩 | 파티션 + 파티션 키 |
| 워커 멤버십 관리 | 컨슈머 그룹 |
| 하트비트 / 장애 감지 | `session.timeout.ms`, `heartbeat.interval.ms` |
| lease / 소유권 | 파티션 할당 |
| **fencing token** | **컨슈머 그룹 generation id** |
| 재분배 로직 | 리밸런싱 프로토콜 |
| 소비자별 커서 테이블 | 컨슈머 그룹별 offset |
| 재분배 시 정리 훅 | `ConsumerRebalanceListener` |
| 특정 지점부터 재처리 | `seek` / `--reset-offsets` |
| 폴링 루프와 부하 조절 | long-poll, `max.poll.records` |
| 재시도 / 실패 격리 | 에러 핸들러, retry topic, DLT |
| 보존 기간과 정리 | retention 정책, log compaction |

**왼쪽을 전부 만들면 오른쪽이 된다.** 이것이 이 문서의 결론이다.

> **Kafka 도 주지 않아서 직접 만든 것** — 7단계([KS-35](../issues/KS-35-failure-handling.md))의 **사용자 단위 보류**.
> Kafka 의 블로킹 단위는 파티션이라, 한 사용자의 영구 실패를 DLT 로 빼면서 **그 사용자의 뒤 거래만** 멈추려면
> 보류 테이블(`quarantined_user`)을 직접 두어야 했다. Kafka 가 모든 것을 대신해 주지는 않는다.

## 5. 그래서 언제 직접 만드는가

솔직히 말하면 **직접 만드는 게 맞는 경우도 있다.**

| 상황 | 판단 |
|---|---|
| 워커 1개로 충분한 처리량 | **DB 큐. Kafka는 오버스펙** |
| 순서가 중요하지 않음 | **DB 큐 + `SKIP LOCKED`로 충분** |
| 소비자가 하나뿐이고 재처리 요구가 없음 | **DB 큐로 충분** |
| 인프라 운영 인력이 없음 | Kafka 운영 비용을 고려해야 한다 |
| 위 세 조건 중 하나라도 깨짐 | **Kafka(또는 관리형 로그 브로커)를 검토** |

**"Kafka를 안 쓰는 판단"을 할 수 있는 것도 이 문서의 목적이다.**
