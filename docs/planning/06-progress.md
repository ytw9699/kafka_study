## 2. 요구사항을 코드로 확인한 결과

[기획서 5절](01-planning.md)의 요구사항 6개 중 **1~4를 확인**했다.

### 1. 같은 사용자의 거래는 순서대로 → [KS-20](../issues/KS-20-order-broken-experiment.md)

워커 3개 고정, **코드 변경 없이 파티션 키만** 바꿨다.

```
USER_ID              RANDOM
차이 0 (5명 전부)     불일치 5명
                     user-1  +32,620
                     user-3  +39,760
                     user-4  +20,090
```

**틀어지는 방향이 대부분 `+`인 데 이유가 있다.** 사용이 적립보다 먼저 처리되면
잔액 부족으로 거절되고, 거절된 사용은 잔액을 깎지 않으므로 결과가 커진다.

거절 건수가 그것을 증명한다 — `user-1` 은 9번 거절됐는데 기대값은 4번, **5건이 잘못 거절**됐다.

### 2. 워커를 늘려 병렬 처리 → [KS-19](../issues/KS-19-worker-scale-out.md)

```
워커 3개  →  p1 / p2 / p0  (1개씩)
워커 4개  →  하나가 논다     (파티션 수가 상한)
워커 1개  →  혼자 3개 처리   (하한 없음)
```

### 3. 워커가 죽어도 자동 인수 → [KS-21](../issues/KS-21-rebalance-experiment.md)

```
정상 종료 (SIGTERM)   onPartitionsRevoked 호출됨    8초
강제 종료 (kill -9)   호출 0회                     47초
```

47초는 `session.timeout.ms` 기본값 45초와 거의 일치한다. **설정값이 그대로 관찰됐다.**

리밸런싱이 두 번 일어나고 워커가 3→2→3→4→1로 바뀌는 동안에도
**발행 135건 = 처리 135건**, lag 0. 유실도 중복도 없었다.

### 4. 전체를 다시 읽어 원장 재구축 → [KS-23](../issues/KS-23-idempotency-experiment.md)

```
멱등 OFF + replay   →  정확히 2.00배 (4명 전부)  😱
rebuild             →  정확히 복원              ✅
멱등 ON  + replay   →  잔액 불변, 28건 전부 skip  ✅
```

### 5·6 — 미확인 (2차)

부정탐지 서비스 합류(6단계), 실패 처리·DLT(7단계).
**실무 운영 지식이며 핵심 주장과는 별개다.**

## 3. 시나리오가 세 번 무너진 기록

이 프로젝트에서 가장 값진 부분일 수 있다. → [KS-13](../issues/KS-13-pivot-ledger.md)

| # | 시나리오 | 왜 무너졌나 |
|---|---|---|
| 1 | 주문 → 매출 집계 | `SELECT ... GROUP BY` 한 줄이면 됨 |
| 2 | 주문 취소 + 일자별 매출 | `order_events` append-only 테이블이면 됨. **"이력을 저장해야 한다"를 증명했지 "Kafka여야 한다"가 아니었다** |
| 3 | **포인트 지갑 원장** | 버텼다 — 도메인 자체가 **순서에 의존**하기 때문 |

**앞의 둘이 무너진 이유는 같다.** 도구를 정해놓고 "Kafka가 필요해 보이는" 요구사항을 역설계했다.
실무는 반대다 — 요구사항이 먼저 있고 도구를 고른다.

> **시나리오를 고르는 기준은 "Kafka를 쓸 수 있는가"가 아니라 "이 도메인의 본질이 무엇인가"다.**

### 주장 강도도 두 번 낮췄다

```
"Kafka가 아니면 구조적으로 불가능하다"           ← 과장
        ↓
"DB를 쓰면 직접 만들어야 하는데 Kafka는 제공한다"  ← 정직
```

DB로도 만들 수 있다. **어려운 것은 만드는 일이 아니라 장애 상황에서 정확성을 지키는 일**이다.
→ [05. DB로 직접 만들면](05-why-not-diy.md)

그리고 **"언제 Kafka가 필요 없는지"** 를 함께 말할 수 있게 되면서 실무 판단으로서의 가치가 생겼다.

## 4. 설계가 틀렸다가 고쳐진 지점

문서에 그럴듯하게 적혀 있었지만 **실제로는 동작하지 않던 것들**이다.

### `auto-offset-reset: earliest` 는 최초 1회용이다 → [KS-11](../issues/KS-11-design-finalize.md), [KS-18](../issues/KS-18-worker-restart-offset.md)

초기 설계에 **"재기동하면 로그로부터 재구축된다"** 고 적었다. **틀렸다.**

이 설정은 **커밋된 offset 이 없을 때만** 동작한다. 재기동하면 이어서 읽는다.
`--from-beginning` 도 마찬가지로 기존 그룹에는 발동하지 않는다.

> **offset 은 컨슈머가 아니라 브로커(`__consumer_offsets`)에 산다.**

설계 리뷰(KS-11)에서 이것을 잡아 **명시적 재생 API**로 방향을 바꿨고,
KS-18에서 실제로 확인해 그 수정이 옳았음이 입증됐다.

### 4단계 원래 설계는 애초에 동작하지 않았다

"CLI로 offset을 리셋해 중복을 재현한다"였는데, `--reset-offsets` 는
**활성 컨슈머가 있으면 거부된다.** 워커를 내려야 하고, 그러면 화면에서 순간을 볼 수 없다.

실제로 확인했다.

```
Error: Assignments can only be reset if the group 'balance-group' is inactive,
       but the current state is Stable.
```

### 저장소 선택이 두 번 바뀌었다

```
H2 인메모리 → H2 파일 → PostgreSQL
```

H2 embedded 파일 모드는 **한 JVM만 열 수 있다(file lock)**.
4단계에서 워커 3개를 띄우는 것이 핵심 실험인데 **아예 불가능**하다.

## 5. 구현하며 발견한 것

문서에 없었는데 코드를 쓰면서 알게 된 것들.

### 파티션 키는 순서 보장뿐 아니라 **동시성 안전**도 준다 → [KS-16](../issues/KS-16-balance-worker.md)

원자적 upsert(`ON CONFLICT`)를 쓰려다 **필요 없다는 것을 알았다.**

한 파티션은 한 워커만 처리하므로 같은 사용자의 거래는 언제나 한 워커가 다룬다 —
**경합 자체가 없다.**

| 얻는 것 | 근거 |
|---|---|
| 순서 보장 | 파티션 내부 순서 + 단일 컨슈머 |
| 동시성 안전 | 같은 키 = 같은 파티션 = 같은 워커 |

**둘이 같은 뿌리에서 나온다.** 그래서 4단계에서 키를 흩뜨리자 **둘 다** 무너졌다
(순서 역전 + lost update).

### 해시 편중은 실재한다 → [KS-3](../issues/KS-3-kafka-cli-basics.md), [KS-14](../issues/KS-14-ledger-api-publish.md)

`user-1`, `user-2`, `user-3` 이 **전부 같은 파티션**으로 갔다.
사용자가 적으면 murmur2 해시가 파티션을 고르게 채우지 못한다.

→ 파티션이 남아도 **특정 워커에만 부하가 몰릴 수 있다.**

### "죽었다"를 아는 방법은 "소식이 없다"뿐이다 → [KS-19](../issues/KS-19-worker-scale-out.md), [KS-21](../issues/KS-21-rebalance-experiment.md)

`kill -9` 는 `onPartitionsRevoked` 를 부르지 않는다. 하트비트가 끊긴 것을 기다려야 안다.

**감지 시간과 오탐은 같은 다이얼의 양끝이다.** 짧게 잡으면 GC로 멈춘 워커까지
죽었다고 판단해 **split-brain** 이 생기고, 길게 잡으면 파티션이 방치된다.

Kafka 는 이것을 **generation id**(fencing token)로 막는다. 실험에서 세대가
`gen 2 → 3 → … → 8` 로 올라가는 것을 봤다.

### 멱등성은 한 가지가 아니다 → [KS-23](../issues/KS-23-idempotency-experiment.md)

| 지점 | 무엇을 막는가 | 키 |
|---|---|---|
| **컨슈머 멱등성** (구현한 것) | 재생·리밸런싱·재기동의 중복 처리 | `eventId` |
| **프로듀서 멱등성** | 같은 거래를 두 번 발행 | 비즈니스 키 |

`ledger-api` 가 같은 거래를 두 번 발행하면 `eventId` 가 달라 **막지 못한다.**

그리고 **멱등 처리가 있어도 `rebuild` 는 필요하다.** 로직이 바뀌면 이전 계산 자체가 틀렸으므로
비우고 다시 쌓아야 한다. 멱등성은 "중복을 막는 것"이지 "재계산하는 것"이 아니다.

## 7. 검증 도구가 결과를 만든다

이 프로젝트에서 반복해서 확인된 것.

### 대조군이 없으면 아무것도 증명하지 못한다 → [KS-20](../issues/KS-20-order-broken-experiment.md)

`RANDOM` 결과만 보면 "워커가 3개라서 그런가?" 하고 헷갈렸을 것이다.
**같은 워커 3개로 `USER_ID` 에서 완벽히 일치했기에** 변수가 하나로 고정되고 인과를 말할 수 있다.

### 비교 기준은 비교 대상과 독립적이어야 한다 → [KS-17](../issues/KS-17-balance-panel.md)

기대 잔액을 SSE **도착 순서**로 계산했다면, 키를 흩뜨렸을 때 **기대 잔액도 함께 틀려져**
비교 자체가 불가능했을 것이다.

`occurredAt` 으로 정렬해 파티션 배치와 무관하게 만들었고,
거절 규칙까지 워커와 맞춰 **차이의 원인이 순서 하나로 좁혀지게** 했다.

### 관찰 도구가 틀리면 실험이 무의미하다

API 로 파티션 키 모드를 바꿨는데 화면은 계속 이전 값을 표시했다(기동 시 1회만 조회).
**"지금 어느 모드인가"를 오판하면 해석이 통째로 어긋난다.** 폴링으로 고쳤다.

### 비동기 시스템에서는 "안 보인다"와 "아직 안 왔다"를 구분해야 한다 → [KS-15](../issues/KS-15-frontend-ledger-feed.md)

첫 스크린샷에서 피드가 비어 있어 SSE 가 안 되는 줄 알았다.
프록시와 직접 연결을 각각 확인해보니 **둘 다 정상**이었고, 스크린샷이 이벤트보다 빨랐을 뿐이었다.

## 8. 남은 것

### 2차 목표 (6~7단계)

| 단계 | 내용 | 왜 남겼나 |
|---|---|---|
| 6 | `fraud-service` 나중에 합류 | 요구사항 5. 실무 운영 지식 |
| 7 | 실패 처리 — blocking retry, DLT | 요구사항 6. **1번(순서)과 정면 충돌하는 지점** |

**7단계가 특히 값질 것이다.** Spring Kafka 가 권장하는 표준 패턴(non-blocking retry)이
**이 도메인에서는 원장을 깨뜨린다.** 블로그 예제를 따라만 해서는 나오지 않는 학습이다.

[TS-2](../troubleshooting/TS-2-poison-pill.md)에서 poison pill 을 이미 겪어
**DLT 가 왜 필요한지는 몸에 남아 있다.** 7단계에서는 "왜"가 아니라 "어떻게"에 집중할 수 있다.

### 알면서 남겨둔 한계

| 항목 | 내용 |
|---|---|
| 분산 재생 조율 | `rebuild` 는 호출한 워커의 파티션만 되감는다. 5단계는 워커 1개로 진행 |
| 트랜잭셔널 아웃박스 | DB 저장과 Kafka 발행의 원자성. 범위 밖 |
| 프로듀서 멱등성 | 같은 거래의 중복 발행은 비즈니스 키가 필요 |
| 스키마 진화 | `common` 모듈 공유라 구조적으로 학습 불가 |
| `ErrorHandlingDeserializer` | poison pill 의 정석 해결. 7단계 |
