# 07. 메시지 큐 — 왜 저장하는가, 무엇을 감당하는가

이 프로젝트의 출발점과, 그 과정에서 정리한 메시지 큐의 개념을 한곳에 모은 문서.
[01. 기획서](01-planning.md)가 "왜 Kafka인가"를 다룬다면, 이 문서는 **"왜 큐인가, 그리고 큐가 무엇을 대가로 요구하는가"** 를 다룬다.

---

## 1. 출발점 — 흘려보내는 메시지

실무에서 Redis Pub/Sub으로 실시간 주문 알림을 만들었다.

```
주문 저장(DB) → Redis PUBLISH → 각 서버의 구독 리스너 → 그 서버에 연결된 SSE 화면으로 전달
```

서버가 두 대이고 앞에 로드밸런서가 있어서, 주문을 받은 서버와 화면이 연결된 서버가 다를 수 있었다.
Redis는 **두 서버를 이어주는 fan-out** 용도였다.

Redis Pub/Sub은 메시지를 **저장하지 않는다.** 발행 순간 구독 중인 대상에게만 전달하고 끝이다.

- 화면이 재연결하는 사이, 구독이 해제된 사이, 배포로 서버가 바뀌는 사이의 메시지는 사라진다
- Redis가 한 대이므로 Redis가 죽으면 실시간 전달 자체가 멈춘다

그래도 저장형 브로커를 쓰지 않은 데는 이유가 있었다.

| 질문 | 답 |
|---|---|
| 원본은 어디에 있나 | **DB.** 주문은 저장된 뒤 알림이 나간다 |
| 놓치면 무엇을 잃나 | 화면 갱신이 늦어질 뿐, **데이터는 잃지 않는다** |
| 어떻게 복구하나 | 화면이 주기적으로 주문 목록을 **다시 조회(폴링)** 하는 안전망 |

**메시지가 "갱신하라는 신호"일 뿐이면 저장 비용을 치를 이유가 없다.** 이 판단은 지금도 맞다고 본다.

남은 질문은 이것이었다.

> **놓쳐도 DB가 있으니 괜찮다는 전제가 없다면, 메시징은 무엇을 보장해야 하는가?**

그래서 **메시지 자체가 원본인 도메인**(포인트 원장)을 골라 이 프로젝트를 시작했다.

## 2. 큐를 쓰는 이유 — "처리량 조절"이 지키는 것

흔히 "비동기로 처리할 수 있다"고 답하지만, 그것은 결과이지 이유가 아니다.
큐의 본질은 **보내는 쪽의 속도와 처리하는 쪽의 속도를 분리하는 것**이다.

```
큐 없음:  요청 1만 건/초 ──────────────→ 처리 서버 ──→ DB · 외부 API
          (유입 속도 = 처리 속도를 강요)       ↑ 커넥션 고갈, 외부 API 한도 초과, 연쇄 장애

큐 있음:  요청 1만 건/초 ──→ [ 큐 ] ──→ 처리 서버 ──→ DB · 외부 API
                          쌓아둔다      감당 가능한 속도로만 꺼낸다
```

| 이점 | 무엇을 지키는가 |
|---|---|
| **부하 평탄화** | 순간 폭주를 큐가 흡수한다. **DB 커넥션 · 스레드 · 외부 API 호출 한도** 같은 하위 자원이 감당할 수 있는 속도로만 일한다 |
| **장애 격리** | 처리 서버가 죽어도 요청은 큐에 남는다. 보내는 쪽은 처리 서버의 장애를 모른 채 계속 받을 수 있다 |
| **재처리** | 실패한 메시지를 다시 꺼내거나 DLQ로 옮겨 나중에 처리한다 |
| **수평 확장** | 처리가 밀리면 소비자를 늘린다. 보내는 쪽은 바꿀 필요가 없다 |
| **결합 제거** | 보내는 쪽은 누가, 몇 개가 처리하는지 모른다. 소비자를 추가해도 발행자는 그대로다 |

그래서 "처리량을 조절할 수 있어서 가장 좋은 점이 무엇인가"의 답은 이것이다.

> **유입량이 아무리 튀어도 DB와 외부 시스템에 가는 부하는 일정하게 유지된다. 한 구간의 폭주가 시스템 전체 장애로 번지지 않는다.**

### 대가 — 큐가 공짜로 주지 않는 것

| 대가 | 내용 |
|---|---|
| 최종 일관성 | 요청한 순간 처리되지 않는다. "접수됨"과 "처리됨"을 구분해야 한다 |
| **중복** | 대부분 at-least-once다. 같은 메시지를 두 번 받는 것을 전제로 **멱등 처리**를 해야 한다 |
| 순서 | 소비자를 늘리면 순서가 깨질 수 있다. 순서가 필요한 단위를 **키로 묶어야** 한다 |
| 실패 처리 | 처리 못 한 메시지를 어디로 보낼지(재시도 · DLQ) 정해야 한다 |
| 관측 | 쌓이는 속도와 빠지는 속도의 차이(**lag**)를 지켜보지 않으면 밀리는 것을 모른다 |
| 운영 | 브로커라는 인프라가 하나 늘어난다. 브로커 자체도 장애점이 된다 |

## 3. Pub/Sub · 큐 · 로그 — 언제 지우느냐의 차이

| | Pub/Sub (Redis Pub/Sub) | 큐 (SQS, RabbitMQ) | 로그 (Kafka, Kinesis) |
|---|---|---|---|
| 저장 | 하지 않음 | 소비될 때까지 | **보존 기간 동안** |
| 지우는 시점 | 전달 즉시 | 소비자가 처리 완료(ack)하면 | 보존 기간 만료 시 (소비와 무관) |
| 구독자가 없으면 | **소멸** | 쌓인다 | 쌓인다 |
| 여러 소비자 | 전원에게 복사 | 한 메시지는 한 소비자만 | **그룹마다 각자 전체를 읽는다** |
| 다시 읽기 | 불가 | 불가 | **offset만 되돌리면 가능** |
| 순서 | 약함 | FIFO 큐 기준 | **파티션 안에서 보장** |
| 맞는 용도 | 원본이 따로 있는 실시간 알림 | 작업 분배, 버퍼링 | 원본 이벤트, 여러 시스템이 같은 사실을 각자 소비 |

결정적 차이는 **"어디까지 읽었는지"를 누가 기억하느냐**다.

- 큐는 메시지를 **지워서** 위치를 표현한다. 지웠으니 다시 읽을 수 없다.
- 로그는 메시지를 남겨두고 **컨슈머 그룹마다 offset만 따로 기록**한다.
  그래서 같은 로그를 잔액 계산 · 부정탐지 · 리포트가 **각자의 속도로**, 필요하면 **처음부터 다시** 읽을 수 있다.

### Redis Streams와 Redis 이중화

Redis를 이미 쓰고 있다면 Redis Streams가 먼저 떠오른다. 저장 · 재생 · 소비자 그룹이 다 된다.
하지만 **파티션 개념이 없어서** 그룹 안에서 아무 소비자나 다음 메시지를 집어간다.
"같은 사용자는 한 소비자가 순서대로"를 하려면 키별 라우팅을 직접 만들어야 한다.

Redis를 메시징 경로에 둔다면 단일 장애점도 따져야 한다.

| 선택 | 효과 | 남는 것 |
|---|---|---|
| Sentinel | 마스터 장애 시 자동 승격 | 승격 중 수 초의 공백, 그 사이 Pub/Sub 메시지는 사라진다 |
| Cluster | 샤딩 + 노드별 복제 | Pub/Sub은 클러스터 전체로 브로드캐스트되어 노드가 늘수록 비용이 커진다(sharded Pub/Sub으로 완화) |
| 폴백 경로 | 브로커가 죽으면 폴링으로 내려간다 | 실시간성은 잃지만 기능은 유지 |

Pub/Sub 경로는 이중화를 해도 **전환 순간의 메시지는 보존되지 않는다.** 그래서 원본이 따로 있는 신호에만 쓴다.

## 4. 전달 보장과 멱등성

| 보장 | 의미 | 어떻게 되나 |
|---|---|---|
| at-most-once | 많아야 한 번 — **유실 가능** | 처리 전에 위치를 커밋 (Redis Pub/Sub은 사실상 이것) |
| **at-least-once** | 최소 한 번 — **중복 가능** | 처리 후에 위치를 커밋 (이 프로젝트의 워커) |
| exactly-once | 정확히 한 번 | 트랜잭션 · 추가 비용. 결과를 외부 DB에 쓰면 결국 멱등이 필요 |

중복은 **처리와 커밋 사이에 죽을 때, 리밸런싱 때, 재생할 때** 생긴다.
[KS-23](../issues/KS-23-idempotency-experiment.md)에서 멱등 없이 재생해 **포인트가 정확히 2배**가 되는 것을 확인했다.

멱등을 만들 때 정한 원칙:

| 원칙 | 이유 |
|---|---|
| 멱등 키는 **메시지 고유 ID**(`eventId`) | 사용자 ID는 메시지가 여럿이고, 내용 기반 키는 같은 금액을 두 번 적립할 수 있다 |
| 확인과 처리를 **같은 트랜잭션**으로 | 둘이 분리되면 그 사이에 죽었을 때 다시 중복이 생긴다 |
| 실패 · 거절도 **처리한 결과로 기록** | 재처리 시 거절 횟수가 다시 늘면 안 된다 |
| 컨슈머 멱등과 **발행 중복**은 별개 | 같은 요청을 두 번 발행하면 ID가 달라 컨슈머가 못 막는다 → 요청 단위의 비즈니스 키가 필요 |
| 멱등 ≠ 재계산 | 멱등은 중복을 막을 뿐, 로직이 바뀌면 비우고 다시 쌓는 재구축이 필요 |

## 5. 재시도와 DLQ — 도메인이 정답을 바꾼다

| 실패 종류 | 예 | 처리 |
|---|---|---|
| 일시적 | 타임아웃, 외부 API 503, DB 락 대기 | **백오프를 두고 재시도** |
| 영구적 | 역직렬화 실패, 잘못된 데이터, 존재하지 않는 대상 | 재시도해도 소용없다 → **빠르게 DLQ로 격리** |

[TS-2](../troubleshooting/TS-2-poison-pill.md)에서 형식이 깨진 메시지 하나가 **파티션 전체를 무한 재시도로 멈추게** 하는 것을 겪었다.
영구 실패를 빨리 빼내지 않으면 무관한 메시지까지 막힌다.

재시도 방식은 두 가지이고, **도메인에 따라 정답이 반대가 된다.**

| 방식 | 동작 | 순서 | 처리량 |
|---|---|---|---|
| blocking retry | 같은 자리에서 재시도, 파티션 정지 | **지켜진다** | 그 파티션이 멈춘다 |
| non-blocking retry | 실패 메시지를 retry 토픽으로 보내고 다음으로 진행 | **깨진다** | 유지된다 |

| 도메인 | 순서가 결과를 바꾸나 | 맞는 방식 |
|---|---|---|
| 포인트 원장 | **바꾼다** — 사용이 적립보다 먼저면 거절된다 | blocking retry + 영구 실패 시 그 사용자의 후속 거래도 보류 |
| 알림 · 메시지 발송 | 대체로 안 바꾼다 — 각 발송이 독립적 | **non-blocking retry + DLQ** — 한 건 실패로 전체 발송을 멈추지 않는다 |

Spring Kafka가 권장하는 non-blocking retry는 일반적으로 맞는 선택이지만, **원장에서는 순서를 뒤집어 잔액을 깨뜨린다.**
"권장 패턴"이 아니라 **"이 메시지에 순서가 의미 있는가"** 가 선택 기준이다. (7단계에서 직접 확인할 예정)

## 6. 설계 메모 — 대량 발송 파이프라인에 적용한다면

> **구현하지 않은 사고 실험이다.** 이 프로젝트에서 확인한 메커니즘을 순서가 덜 중요하고 처리량이 중요한 도메인에 옮겨보면 무엇이 달라지는지 정리한다.

```
발송 요청(캠페인) → [발송 요청 토픽] → 대상 분할 워커 → [채널별 발송 토픽] → 발송 워커 → 외부 발송 API
                                                                    │
                                                                    └→ [발송 결과 토픽] → 리포트 집계 · 재시도 판단
```

| 질문 | 원장에서 배운 것 | 발송에 옮기면 |
|---|---|---|
| 키를 무엇으로 | 순서가 결과를 바꾸는 단위(`userId`) | 순서가 거의 무관 → 키를 **고르게 분산**. 단 같은 수신자에게 연속 발송 순서가 중요하면 수신자 키 |
| 파티션 수 | 파티션 수가 병렬 처리의 상한 ([KS-19](../issues/KS-19-worker-scale-out.md)) | 목표 처리량 ÷ 워커 1개 처리량으로 산정. 나중에 늘리면 키 배치가 바뀐다 |
| 해시 편중 | 사용자 몇 명이 한 파티션에 몰렸다 | 대형 캠페인 하나가 한 파티션을 독점하지 않게 키 설계 |
| 중복 | `eventId` 멱등 + 같은 트랜잭션 | **같은 수신자에게 같은 메시지 두 번 발송 금지** → 발송 ID로 Redis `SET NX` + TTL 선점, DB 유니크 제약으로 최종 방어 |
| 유량 제어 | (원장에는 없었다) | 외부 발송 API의 초당 한도에 맞춰 **토큰 버킷**. 한도에 걸리면 컨슈머를 `pause` 했다가 `resume` — 큐가 쌓아두므로 버리지 않는다 |
| 재시도 | 원장은 blocking | 발송은 **non-blocking + DLQ**. 일시 실패는 지연 재시도, 영구 실패(잘못된 번호)는 즉시 DLQ |
| 소비자 추가 | 그룹별 독립 offset | 리포트 · 통계 · 이상 탐지를 **발송 흐름에 영향 없이** 별도 그룹으로 |
| 장애 감지 | `kill -9` 시 47초 공백 ([KS-21](../issues/KS-21-rebalance-experiment.md)) | 세션 타임아웃만큼 그 파티션 발송이 멈춘다 → **consumer lag 알림**으로 감시 |
| 재처리 | offset seek로 재구축 | 특정 시점 이후 발송 결과를 **다시 집계**. 발송 자체의 재실행은 중복 발송 방어가 전제 |

같은 Kafka라도 **원장은 순서와 정확성을, 발송은 처리량과 중복 방지를** 최우선으로 둔다.
도구가 아니라 메시지의 성격이 설계를 결정한다.

## 7. 인접 개념 — 분산 트랜잭션

큐로 서비스를 나누면 한 요청이 여러 서비스의 DB를 건드린다. 하나의 DB 트랜잭션으로 묶을 수 없다.

| 방식 | 내용 | 한계 |
|---|---|---|
| 2PC | 코디네이터가 모든 참여자의 준비를 확인한 뒤 일괄 커밋 | 코디네이터가 장애점, 참여자가 모두 지원해야 함, 느림 |
| **SAGA — 오케스트레이션** | 중앙 조정자가 단계를 순서대로 호출하고, 실패하면 **보상 트랜잭션**을 역순으로 호출 | 조정자에 로직이 몰린다 |
| **SAGA — 코레오그래피** | 각 서비스가 이벤트를 발행하고 다음 서비스가 구독해 이어간다. 실패도 이벤트로 알린다 | 흐름이 여러 서비스에 흩어져 추적이 어렵다 |
| **트랜잭셔널 아웃박스** | DB 변경과 "발행할 이벤트"를 **같은 트랜잭션**으로 아웃박스 테이블에 저장하고, 별도 프로세스가 브로커로 발행 | 발행이 지연될 수 있고 중복 발행 가능 → 소비 측 멱등이 필요 |

보상 트랜잭션은 "되돌리기"가 아니라 **"반대 효과를 내는 새 거래"** 다.
원장으로 치면 잘못된 적립을 지우는 것이 아니라 **차감 이벤트를 새로 발행**하는 것이다. 로그는 지우지 않는다.

이 프로젝트의 `ledger-api`는 DB가 없어서 아웃박스 문제가 생기지 않는다.
요청 → Kafka 발행이 곧 기록이기 때문이다. 발행자가 DB를 갖는 순간 아웃박스가 필요해진다.

## 8. 정리

| 메시지의 성격 | 맞는 도구 | 근거 |
|---|---|---|
| 원본이 따로 있는 실시간 신호 | **Pub/Sub** + 재조회 안전망 | 실무에서 만든 구조 |
| 순서 무관한 작업 분배 · 버퍼링 | **큐** (SQS, RabbitMQ) 또는 DB 큐 | 소비자 하나, 재처리 요구 없음이면 충분 |
| 원본 이벤트, 순서 · 재생 · 여러 독립 소비자 | **로그** (Kafka, Kinesis) | 이 프로젝트 |
| 규모가 작고 소비자가 하나 | DB 테이블 큐 | Kafka는 오버스펙 — [05](05-why-not-diy.md) |

> **메시지가 "알림"이면 흘려보내도 된다. 메시지가 "사실"이면 저장해야 한다.**
> 그리고 저장하는 순간 **중복 · 순서 · 실패 · 관측**을 감당해야 한다.
