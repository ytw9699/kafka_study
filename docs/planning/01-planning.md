# 01. 기획서

## 1. 이 프로젝트가 증명하려는 것

Kafka를 배우는 자료는 많지만, 대부분 "메시지를 발행하고 구독한다"에서 끝난다. 그건 RabbitMQ도, SQS도, Redis Pub/Sub도 한다. 그래서 **왜 굳이 Kafka인가**에 대한 답이 남지 않는다.

Kafka가 다른 메시징 도구로 **대체 불가능한** 지점은 하나다.

> **이벤트가 소비 후 사라지는 메시지가 아니라, 여러 소비자가 각자의 위치(offset)를 들고 읽는 "공유된 지속 로그"다.**

이 성질에서 파생되는 능력들:

| 파생 능력 | 큐(RabbitMQ/SQS)로 가능? |
|---|---|
| 컨슈머가 죽었다 살아나도 그 지점부터 이어서 처리 | △ (ack 안 한 것만) |
| **신규 컨슈머가 과거 이벤트로 자기 상태를 구축** | ✗ |
| 버그 고친 뒤 **같은 데이터를 다시 처리** | ✗ |
| 스트림 처리(집계·조인)의 상태 복구 | ✗ |
| CDC로 DB 변경분을 여러 싱크에 동기화 | ✗ |

**이 프로젝트는 위 표의 2번, 3번을 눈으로 보는 것을 목표로 한다.**

---

## 2. 현업에서 Kafka를 쓰는 이유 (우선순위)

학습 방향을 잡기 위해, 실무에서 Kafka가 필요해지는 상황을 정리한다.

### Kafka가 아니면 안 되는 경우

1. **같은 이벤트를 여러 독립 소비자가 "각자 전체를 다시 읽어야" 할 때**
   신규 서비스가 추가돼서 과거 이벤트로 자기 DB/상태를 채워야 하는 상황. 큐는 소비된 메시지가 없으므로 애초에 불가능.

2. **초고처리량 스트리밍 (초당 수만~수십만 건)**
   파티션 병렬 처리 + 순차 디스크 I/O 구조. RabbitMQ는 처리량 한계가 뚜렷이 낮다.

3. **순서 보장 + 높은 처리량을 동시에 요구할 때**
   SQS FIFO도 순서는 보장하지만 처리량이 매우 낮다. Kafka는 파티션 키 단위 순서 보장과 높은 처리량을 함께 만족한다.

4. **여러 시스템이 같은 원본 데이터를 각자 다른 목적으로 오래 두고 써야 할 때**
   데이터레이크, 검색엔진, 실시간 대시보드, ML 피처스토어. CDC(Debezium) 파이프라인이 대표 사례.

### Kafka가 "유일한 정답"은 아닌 경우

5. **단순 MSA 이벤트 통신** — RabbitMQ, SNS+SQS로도 충분하다. Kafka를 쓰는 건 보통 "이미 인프라가 있어서" 또는 "확장성 대비" 때문.
6. **SSE/WebSocket 실시간 푸시의 서버 간 브로드캐스트** — 서버 몇 대 규모면 Redis Pub/Sub가 더 가볍고 적합하다.

> **그래서 이 프로젝트의 시나리오는 1번에 정확히 조준한다.**

## 3. 다른 메시징 도구와의 차이

| | Kafka | SNS | SQS / Service Bus Queue | RabbitMQ |
|---|---|---|---|---|
| 메시지 보관 | 일정 기간 디스크에 로그로 보존 | 즉시 전달 후 미보관 | 소비되면 삭제 | 소비되면 삭제 |
| Replay(재처리) | **O** (offset 되감기) | X | X (DLQ 외엔 불가) | X |
| Fan-out (여러 구독자가 각자 전체 소비) | O (컨슈머 그룹별 독립) | O | 제한적 | O (Exchange) |
| 순서 보장 | 파티션 내 보장 | X (FIFO 토픽 예외) | FIFO 큐만 | 큐 단위 |
| 처리량 | 매우 높음 | 중간 | 중간 | 중간 |
| 강점 | 이벤트 스트리밍, 로그 파이프라인 | 알림 브로드캐스트 | 작업 큐 | 정교한 라우팅 |

**핵심**: fan-out과 비동기 처리는 다들 한다. **replay는 Kafka만 한다.**

## 4. 시나리오

### 도메인
간단한 주문 시스템.

### 요구사항
1. 사용자가 주문을 생성하면 **실시간으로 화면의 주문 피드에 나타난다.**
2. 매출 통계 대시보드가 **주문별 매출을 집계해서 보여준다.**
3. 통계 서비스는 **주문 서비스보다 나중에 만들어졌다.** 따라서 기동 시점에 **이미 쌓여 있는 과거 주문 전부를 읽어서** 집계를 스스로 구축해야 한다.
4. 집계 로직에 버그가 발견되면, **같은 주문 데이터를 다시 처리해서** 집계를 재구축할 수 있어야 한다.

3번과 4번이 이 프로젝트의 존재 이유다.

### 왜 이 시나리오인가
- 3번: 큐 기반에서는 **구조적으로 불가능**. "과거 메시지"라는 게 존재하지 않기 때문.
- 4번: replay를 실제로 해보면 **같은 주문이 두 번 집계되는 문제**가 터진다. 이게 Kafka 실무의 핵심 주제인 **멱등성(idempotency)** 이고, 이걸 직접 겪고 해결하는 것이 가장 큰 학습 포인트.

## 5. 단계별 학습 로드맵

### 1차 목표는 4단계까지다

**0~4단계까지가 이 프로젝트의 핵심**이다. 여기까지만 해도 "왜 Kafka인가"에 완전히 답할 수 있다.
5~6단계는 실무에 필요한 지식이지만 핵심 주장과는 별개이므로, **4단계 완료 시점에 `main` 머지 + `step-4` 태그로 한 번 완결**시킨다.

| 구간 | 단계 | 성격 |
|---|---|---|
| **1차 (핵심)** | 0 ~ 4단계 | "Kafka가 아니면 안 되는 이유"를 눈으로 확인 |
| 2차 (확장) | 5 ~ 6단계 | 실무 운영 지식 (리밸런싱, 장애 처리) |

각 단계는 독립적으로 동작 확인이 가능한 커밋 단위로 진행한다.
세부 작업 분해는 [04. 작업 로드맵](04-roadmap.md) 참조.

### 0단계 — 인프라
Docker Compose로 Kafka(KRaft 모드) + Kafka UI 기동. CLI로 토픽을 만들고 콘솔 producer/consumer로 메시지를 주고받는다.

**이 단계에서 CLI로 먼저 확인할 것** (Spring이 감춰주기 전에):
- 같은 키로 보낸 메시지가 항상 같은 파티션에 들어간다
- 서로 다른 컨슈머 그룹이 같은 메시지를 **각각** 받는다
- `--from-beginning`으로 **이미 소비된 메시지를 다시 읽을 수 있다**

> **배우는 것**: 토픽, 파티션, offset의 실체. **Kafka가 큐와 다르다는 것을 CLI 수준에서 먼저 확인.**

### 1단계 — Producer
`order-service`: `POST /api/orders` → 주문을 Postgres에 저장하고 `KafkaTemplate`으로 `order-events`에 JSON 발행. Kafka UI에서 메시지가 파티션에 쌓이는 것을 확인.

> **배우는 것**: 파티션 키(userId), 직렬화, 발행 결과 확인(ack).

### 2단계 — 실시간 Consumer + 프론트
`feed-service`가 `@KafkaListener`로 구독 → SSE로 프론트에 push. Vue 화면에서 주문을 넣으면 피드에 즉시 뜬다.
피드의 각 행에 **partition / offset 뱃지**를 달아, 같은 `userId`로 반복 주문하면 파티션이 고정되는 것을 화면에서 본다.

> **배우는 것**: 컨슈머 그룹, `auto-offset-reset: latest`, offset commit.

### 3단계 — 하이라이트: 뒤늦게 합류하는 Consumer

**⚠️ 이 단계는 딱 한 번만 자연스럽게 일어난다.** 순서를 지켜야 한다.

1. 1~2단계를 돌리며 주문을 **충분히 쌓아둔다** (30건 이상 권장)
2. 그 다음 `stats-service`를 **처음으로** 기동한다
3. 새 컨슈머 그룹이므로 커밋된 offset이 없다 → `auto-offset-reset: earliest`가 발동 → **과거 주문 전부를 처음부터 읽어 매출 집계를 만들어낸다**
4. 프론트 차트가 0에서 시작해 과거 데이터로 쭉 채워지는 것을 눈으로 본다

> 실수로 stats-service를 먼저 켜버리면 이 순간이 사라진다. 그때는 `POST /api/stats/rebuild`로 재현할 수 있다 (집계를 비우고 처음부터 다시 읽기).

> **배우는 것**: 컨슈머 그룹별 독립 offset. **큐와 결정적으로 다른 지점.**

### 4단계 — Replay & 멱등성

`POST /api/stats/replay` — **집계를 비우지 않은 채로** 과거 이벤트를 다시 읽는다.
→ **집계가 정확히 2배가 되는 것을 화면에서 실시간으로 목격한다.** 😱
→ 해결책 두 가지를 비교한다.

| 해결책 | 방식 | 실무에서 |
|---|---|---|
| `processed_event` 테이블 | `orderId` 중복을 걸러 증분 처리 | 상시 운영 중 재처리 |
| 집계 초기화 후 재구축 | `rebuild` — 비우고 처음부터 | 집계 로직 자체가 바뀐 경우 |

추가로 CLI `kafka-consumer-groups --reset-offsets`도 다룬다. **컨슈머가 떠 있으면 거부된다**는 제약과, 그것이 실무에서 갖는 의미를 확인한다.

> **배우는 것**: at-least-once 전달 보장의 실체, 멱등 컨슈머 설계, 증분 처리와 전체 재구축의 트레이드오프.

---

### 5단계 — 파티션 & 리밸런싱 *(2차)*

`feed-service` 인스턴스를 2~3개 띄워 파티션이 나뉘는 것을 관찰. 하나를 죽이면 리밸런싱되는 것을 확인.

**그리고 화면이 깨지는 것을 목격한다.** 주문을 10건 넣어도 화면에는 3건 정도만 보인다.
브라우저는 세 인스턴스 중 **하나에만** SSE로 연결되어 있고, 그 인스턴스는 자기가 배정받은 파티션의 이벤트만 받기 때문이다.

이것은 버그가 아니라 **레이어의 차이**다.

| | 구조 | |
|---|---|---|
| Kafka 컨슈머 그룹 | 일을 **나눠 갖는다** | 서버 ↔ 서버 |
| SSE 브로드캐스트 | 모두에게 **뿌린다** | 서버 ↔ 브라우저 |

여기서 Redis Pub/Sub(또는 브로드캐스트용 별도 토픽)이 왜 필요한지가 몸으로 드러난다.
**"Kafka는 SSE 연결 문제를 해결하는 도구가 아니다"** 가 실물로 확인되는 지점.

> **배우는 것**: 파티션 분배 전략, 리밸런싱, 순서 보장의 범위(파티션 내부로 한정), **그리고 Kafka가 풀지 않는 문제**.

### 6단계 — 에러 처리 & DLT *(2차)*

`stats-service`에서 특정 주문에 예외를 던지게 하고 `DefaultErrorHandler` + retry topic + DLT(Dead Letter Topic)를 구성한다.

> **배우는 것**: 실무 필수인 실패 처리 패턴, 무한 재시도로 컨슈머 전체가 멈추는 상황 방지.

## 6. 범위에서 제외한 것

의도적으로 넣지 않은 것들과 그 이유.

| 제외 항목 | 이유 |
|---|---|
| Avro + Schema Registry | 기초 단계에선 JSON으로 충분. 스키마 진화는 별도 심화 주제 |
| Kafka Streams | 진입장벽이 높고, 이 프로젝트의 핵심(로그 재생)과 별개 |
| 인증/인가 (SASL/SSL) | 로컬 학습 환경에서는 불필요 |
| 실서비스급 프론트 | Kafka가 주인공. 프론트는 흐름을 눈으로 보는 창 역할로 최소화 |
| Exactly-once (트랜잭션) | 4단계에서 멱등성으로 다루는 것이 더 실용적 |
| **Kubernetes** | Kafka 학습이 쿠버 학습에 묻힌다. 별개 주제이므로 이 프로젝트에서 제외 |
| 트랜잭셔널 아웃박스 | DB 저장과 Kafka 발행의 원자성. 중요하지만 이 프로젝트의 핵심(로그 재생)과 별개 |

## 7. 왜 서비스를 3개로 쪼개는가

"컨슈머 그룹만 다르게 하면 되니 앱 하나에 `@KafkaListener` 두 개를 두면 안 되나?" — 안 된다.
**이 프로젝트의 핵심 실험이 프로세스 분리를 요구하기 때문이다.**

| 실험 | 요구사항 |
|---|---|
| 3단계 — stats를 **나중에 처음 켠다** | stats가 별도 프로세스여야 함. 한 앱이면 order/feed와 같이 떠버림 |
| 5단계 — feed **인스턴스만 여러 개** 띄운다 | feed가 별도 프로세스여야 함 |

즉 3개 분리는 MSA를 흉내내기 위한 장식이 아니라, **실험 조건 자체**다.
