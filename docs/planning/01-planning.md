# 01. 기획서

## 1. 한 문장

> **같은 사용자의 거래 순서는 지키면서 여러 사용자를 동시에 처리하고,
> 워커가 죽어도 자동으로 이어받으며, 과거 거래까지 다시 읽어야 해서 Kafka를 쓴다.**

이 프로젝트는 위 문장을 **코드로 확인하는 것**이 목적이다.

---

## 2. 이 프로젝트가 주장하는 것 (그리고 주장하지 않는 것)

### 주장하지 않는 것: "Kafka가 아니면 불가능하다"

이 문장은 과장이다. 아래를 전부 직접 만들면 DB로도 된다.

```
이벤트 테이블 + userId별 라우팅 + 워커 멤버십 + 하트비트
+ lease + 파티션 소유권 + 리밸런싱 + 컨슈머 offset + 재시도
```

실제로 Kafka 이전에는 다들 이렇게 만들었다. **가능하다.**

### 주장하는 것: "직접 만들 것이냐, 제공받을 것이냐"

> **DB를 쓰면 위 기능들을 직접 만들어야 하는데, Kafka는 메시징 시스템 자체에서 제공한다.**

그리고 직접 만들 때 어려운 것은 **컴포넌트를 만드는 일이 아니라 장애 상황에서 정확성을 지키는 일**이다.

대표적인 함정 — **split-brain**:

```
워커A: user-42 lease 획득 → 거래 처리 시작
       ↓ GC로 8초 멈춤 (또는 네트워크 지연)
       lease 만료
워커B: user-42 lease 인수 → 거래 처리 → 잔액 갱신
워커A: 깨어남. 자기 lease가 유효한 줄 알고 → 잔액 갱신   ← 이중 적용 💥
```

이걸 막으려면 **fencing token**이 필요하다. lease마다 단조 증가하는 번호를 붙이고, 저장소가 "더 낮은 번호의 쓰기는 거부"해야 한다.

Kafka는 이것을 컨슈머 그룹의 **generation id**로 해결한다.
우연히 그 모양인 게 아니라, **이 문제를 풀면 그 구조가 될 수밖에 없어서** 그렇다.

자세한 대응표는 [05. DB로 직접 만들면 어디까지 가야 하는가](05-why-not-diy.md) 참조.

### 그래서 실무 판단 기준

| | |
|---|---|
| ❌ | "DB로는 안 되니까 Kafka" |
| ✅ | **"검증된 구현이 있는데 분산 조정을 직접 만들 이유가 없으니까 Kafka"** |
| ✅ | "규모가 작고 정확성 요구가 낮으면 DB 큐로도 충분하다" |

**언제 Kafka가 필요 없는지 아는 것**도 이 프로젝트의 산출물이다.

---

## 3. 정직한 한계 — 토이 프로젝트로 증명할 수 없는 것

Kafka의 필요성은 두 곳에서 나온다.

- **규모** — 초당 수만 건, DB가 못 버티는 지점
- **조직** — 여러 팀이 독립 배포하고 서로의 DB를 볼 수 없는 상황

**둘 다 혼자 노트북에서 재현할 수 없다.** 흉내는 낼 수 있어도 그건 필요가 아니다.

그래서 이 프로젝트의 목표를 정확히 다시 쓰면:

| | |
|---|---|
| ❌ 증명할 수 없는 것 | "Kafka가 필요하다" |
| ✅ 실제로 하는 것 | **Kafka의 메커니즘을 체득한다** — 파티션·순서 보장, 컨슈머 그룹, 리밸런싱, offset, 재생, at-least-once, 멱등성 |
| ✅ 부수적으로 얻는 것 | **Kafka가 왜 그런 모양인지 이해한다.** 그리고 **언제 필요 없는지 판단하는 감각** |

단, **딱 하나는 소규모에서도 진짜로 아프다.**
**"순서가 안 지켜지면 잔액이 틀린다"** — 이건 워커를 둘로 늘리는 순간 즉시 깨진다.
4단계에서 이것을 직접 목격한다.

## 4. 도메인 — 포인트 지갑 원장(Ledger)

### 왜 이 도메인인가

**순서가 결과를 결정적으로 바꾸는 도메인**이어야 순서 보장이 진짜 요구사항이 된다.

```
잔액 1,000원
① 5,000원 적립   ② 3,000원 사용

①→② 순서:  1,000 → 6,000 → 3,000   ✅
②→① 순서:  1,000 → [잔액부족, 거절] → 6,000   ❌ 결과가 다르다
```

**순서가 뒤바뀌면 잔액이 틀리고, 그것이 화면에 숫자로 보인다.**
"매출 집계"처럼 틀려도 티가 안 나는 도메인과 결정적으로 다르다.

### 이벤트

`ledger-events` 토픽에 두 종류가 흐른다. **키는 `userId`.**

| 이벤트 | 의미 |
|---|---|
| `POINT_EARNED` | 포인트 적립 |
| `POINT_SPENT` | 포인트 사용 (잔액 부족이면 거절) |

**Kafka가 원장의 원본(source of truth)이다.** 잔액은 이 로그로부터 계산된 파생 상태일 뿐이다.

## 5. 요구사항

| # | 요구사항 | 사용하는 Kafka 메커니즘 |
|---|---|---|
| 1 | **같은 사용자의 거래는 반드시 순서대로** 처리된다 | 파티션 키, 파티션 내 순서 보장 |
| 2 | 워커를 늘려 **여러 사용자를 동시에** 처리한다 | 컨슈머 그룹, 파티션 분배 |
| 3 | **워커가 죽어도** 유실·중단 없이 남은 워커가 이어받는다 | 리밸런싱, offset 커밋 |
| 4 | 잔액 계산 버그 발견 시 **전체 거래를 다시 읽어 원장을 재구축**한다 | offset seek, 로그 보존 |
| 5 | **부정거래 탐지 서비스가 나중에 추가**된다. 과거 거래 전체를 읽어 자체 상태를 만들며, 잔액 워커와 **완전히 독립적으로** 동작한다 | 컨슈머 그룹별 독립 offset |
| 6 | **처리가 실패해도 원장이 틀어지지 않는다** | 재시도 전략, DLT, 파티션 블로킹 |

### 1번과 6번은 정면으로 충돌한다

순서를 지키려면 실패한 지점에서 **멈춰야** 하고, 멈추면 **처리량이 죽는다.**

일반적인 컨슈머라면 실패한 메시지를 DLT로 보내고 다음으로 넘어가면 된다. **원장에서는 그러면 안 된다.**

```
사용자 A: ① 5,000 적립   ② 3,000 사용   ③ 2,000 사용

②가 실패 → DLT로 보내고 ③ 처리
→ ②를 건너뛴 잔액이 된다 → 원장이 영구히 틀린다
```

이 트레이드오프를 다루는 것이 Kafka 실무의 진짜 어려움이며, 7단계에서 정면으로 겪는다.

## 6. 다른 도구와의 비교

**현업에서 실제로 마주칠 것들**만 놓고 정직하게 따진다.

| | 1+2+3<br/>순서+병렬+인수 | 4<br/>재생 | 5<br/>독립 소비자 |
|---|---|---|---|
| **DB 테이블 큐** | △ 직접 만들면 가능 | ✅ | △ 커서 직접 관리 |
| **RabbitMQ** | ❌ 키 기반 파티셔닝 + 리밸런싱 없음 | ❌ 소비 시 삭제 | ✅ |
| **Redis Streams** | ❌ **파티션 개념이 없다** — 그룹 내 소비자가 아무 메시지나 집어간다 | ✅ | ✅ |
| **SQS FIFO** | ✅ MessageGroupId로 가능 | ❌ 소비 시 삭제 | ❌ |
| **AWS Kinesis** | ✅ 샤드 + 파티션 키 | ✅ 최대 365일 보존 | ✅ Enhanced Fan-Out |
| **Kafka** | ✅ | ✅ | ✅ |

### 셋을 동시에 만족하는 것은 **Kafka와 Kinesis** 다

큐 계열(RabbitMQ · SQS · Redis Streams)은 각각 반쪽이다.
SQS FIFO는 1~3을 하지만 4·5에서 탈락하고, Redis Streams는 4·5를 하지만 1~3에서 탈락한다.

**하지만 "Kafka뿐"은 아니다.** Kinesis도 샤드(=파티션) 기반 로그이므로 셋 다 만족한다.
정확한 서술은 이것이다.

> **"이 조합을 제공하는 것은 로그 기반 브로커 계열이며, 현업에서는 Kafka와 Kinesis다."**

### 그럼 왜 Kinesis가 아니라 Kafka인가

| 근거 | |
|---|---|
| **벤더 중립** | Kinesis는 AWS 종속. Kafka는 온프렘·모든 클라우드에서 동일하게 동작 |
| **생태계** | Connect · Streams · **Debezium(CDC)** · Schema Registry. Kinesis에는 이만한 것이 없다 |
| **참고 자료** | 운영 사례·문서·커뮤니티가 가장 많다. 막혔을 때 참고할 곳이 많다는 것은 실질적 차이다 |
| **자체 호스팅** | 이 프로젝트처럼 **로컬에서 전부 돌려볼 수 있다** |

**기능이 아니라 생태계와 중립성이 이유다.** AWS만 쓰는 조직이고 운영 인력이 없다면
Kinesis가 합리적인 선택일 수 있다.

### 표에 넣지 않은 것들

Apache Pulsar · Azure Event Hubs · NATS JetStream · Google Pub/Sub 도
정도의 차이는 있지만 셋을 대체로 만족한다. **국내 현업에서 마주칠 확률이 낮아** 표에서 뺐다.

> 특히 **Pulsar의 `Key_Shared` 구독**은 이 유스케이스에 Kafka보다 나을 수 있다.
> 파티션이 아니라 **키 단위로 배분**하므로, "컨슈머를 파티션 수보다 늘려도 소용없다"는
> 제약([KS-19](../issues/KS-19-worker-scale-out.md))이 없다.
>
> **Kafka의 파티션 단위 배분은 구조적 선택이지 메시징의 본질이 아니다.**

## 7. 눈으로 확인하는 실험

문서가 아니라 **화면의 숫자**로 확인한다.

### 실험 A — 순서가 깨지면 잔액이 틀린다 😱 *(4단계)*

파티션 키를 `userId` 대신 **랜덤**으로 바꿔 발행한다.
→ 같은 사용자의 거래가 여러 파티션에 흩어진다
→ 병렬 워커가 순서를 뒤바꿔 처리한다
→ **화면의 잔액이 실제와 달라진다**

키를 `userId`로 되돌리면 **정확해진다.**

> 파티션 키가 왜 존재하는지를 **틀린 숫자로** 배운다. 설정 한 줄이면 재현되므로 비용이 거의 없다.

### 실험 B — 워커를 죽여도 잔액이 정확하다 *(4단계)*

워커 3개 중 하나를 종료한다.
→ 화면의 **파티션 배정 현황**에서 재배정이 일어나는 것이 보인다
→ 처리는 계속되고 최종 잔액은 정확하다

### 실험 C — 원장 재구축 *(5단계)*

잔액 계산 로직에 버그를 넣었다가 고친 뒤 전체 재생 → 원장이 정확히 복원된다.
**단, 잔액을 비우지 않고 재생하면 포인트가 두 배가 된다.** 😱 → 멱등성.

### 실험 D — 부정탐지 서비스 최초 기동 *(6단계)*

거래가 쌓인 뒤 처음 켠다 → 과거 전부를 읽어 자체 상태를 만든다.
**잔액 워커는 전혀 영향받지 않는다** (다른 컨슈머 그룹).

### 실험 E — 권장 패턴이 오히려 원장을 깨뜨린다 😱 *(7단계)*

Spring Kafka의 표준 권장은 **non-blocking retry**다. 실패하면 `retry topic`으로 보내고 메인 파티션은 계속 진행한다.

원장에서 이걸 쓰면:

```
② 실패 → retry-topic으로 이동 (메인은 계속 진행)
③ 처리됨            ← ②보다 먼저!
② 나중에 재시도 성공
→ ③② 순서로 적용 → 잔액이 틀린다
```

**일반적으로 "정답"인 패턴이 이 도메인에서는 독이 된다.**
blocking retry(같은 스레드에서 재시도, 파티션 정지)로 바꿔야 정확해진다.

> **"파티션은 순서의 단위이자 블로킹의 단위"** 라는 Kafka의 구조가 여기서 몸에 박힌다.

### 실험 F — 파티션 블로킹의 대가 *(7단계)*

한 사용자의 거래가 계속 실패하면 → **그 파티션 전체가 막힌다**
→ 같은 파티션에 배정된 **무관한 사용자들도 처리가 멈춘다**

파티션 수와 키 분포 설계가 왜 중요한지, "한 명의 문제가 몇 명에게 번지는가"로 체감한다.
그리고 **영구 실패는 빠르게 DLT로 빼야 하는 이유**가 여기서 나온다.

## 8. 단계별 학습 로드맵

**1차 목표는 5단계까지.** 여기까지가 1절의 한 문장에 답하는 구간이다.
세부 작업 분해는 [04. 작업 로드맵](04-roadmap.md) 참조.

| 구간 | 단계 | 내용 |
|---|---|---|
| | 0단계 | Kafka 인프라 + CLI 실습 |
| | 1단계 | 프로젝트 뼈대 + PostgreSQL |
| | 2단계 | `ledger-api` — 거래 발행 + 실시간 피드 화면 |
| | 3단계 | `balance-worker` 1개 — 잔액 계산 |
| **1차** | **4단계 ★** | **워커 여러 개 — 순서 깨짐 목격 → 파티션 키로 해결 → 리밸런싱** |
| **1차** | **5단계 ★** | **원장 재구축 & 멱등성** |
| 2차 | 6단계 | `fraud-service` 나중에 합류 — 다중 독립 소비자 |
| 2차 | 7단계 | 실패 처리 — blocking retry, 파티션 블로킹, DLT |

**4단계가 이 프로젝트의 목적지다.** 0~3단계는 4단계를 성립시키기 위한 준비다.
5단계 완료 시 `main` 머지 + `step-5` 태그로 1차 완결.

## 9. 왜 서비스를 3개로 쪼개는가

"컨슈머 그룹만 다르게 하면 되니 앱 하나에 `@KafkaListener` 두 개를 두면 되지 않나?" — 안 된다.
**핵심 실험이 프로세스 분리를 요구하기 때문이다.**

| 실험 | 요구사항 |
|---|---|
| 4단계 — `balance-worker` **인스턴스만 여러 개** 띄운다 | 워커가 별도 프로세스여야 함 |
| 6단계 — `fraud-service`를 **나중에 처음 켠다** | fraud가 별도 프로세스여야 함 |

3개 분리는 MSA를 흉내내기 위한 장식이 아니라 **실험 조건 자체**다.

## 10. 범위에서 제외한 것

| 제외 항목 | 이유 |
|---|---|
| **DB 큐를 직접 구현해보기** | 고통을 겪는 학습법이지만 시간 비용이 크다. [05. 문서](05-why-not-diy.md)로 대신한다 |
| Kubernetes | Kafka 학습이 쿠버 학습에 묻힌다 |
| Avro + Schema Registry | 기초 단계에선 JSON으로 충분. 스키마 진화는 별도 심화 주제 |
| Kafka Streams | 진입장벽이 높고 이 프로젝트의 핵심과 별개 |
| 인증/인가 (SASL/SSL) | 로컬 학습 환경에서는 불필요 |
| Exactly-once (트랜잭션) | 5단계에서 멱등성으로 다루는 것이 더 실용적 |
| 실서비스급 프론트 | Kafka가 주인공. 프론트는 흐름을 눈으로 보는 창 |
